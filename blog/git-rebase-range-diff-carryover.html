git range-diff で全行 = なら rebase 後のテストは省略できるか ── 検証済み状態を引き継ぐ 3 条件と境界設計

長時間の統合テストや AI エージェントによる検収ゲートを含むブランチ開発では、main の最新コミットを取り込むために git rebase を実行するたびにコミット SHA が新しくなります。「前の SHA で通った検証記録と現在の HEAD が一致しなければ最初からテストをやり直す」という単純な規律は安全ですが、作業ブランチの変更と無関係な上流コミットを取り込んだだけの rebase でも重いテストスイートが毎回再実行される構造的な無駄を生みます。

私自身が自社で運用している AI エージェント開発支援パイプライン（非公開、以下「支援パイプラインA」）で作業していた 2026年10月29日にも、まさにこの状況に直面しました1。作業ブランチへ main 側の無関係な 2 コミット（設定ファイルと監視定義ファイルの計 3 ファイル）を取り込む rebase が起きた際、当時の 10 並列テストで最長クラスだけで 673.8 秒〜730.9 秒（約 11〜12 分、全クラスの所要合計 5,499 秒〜5,772 秒、共有資源の排他ロック保持も約 12 分続く状態）かかる再検証が始まろうとしていたのです1。そこで私は、rebase 前後で git range-diff が同一であり、作業側の変更 3 ファイルとの重複が 0 件、かつ新 base の CI が成功（completed/success）していることを確かめ、手動で 1 回だけ検証済み状態を引き継ぐ判断を下しました1。なお、当時の約 11〜12 分という所要時間には共有資源競合による遅延が含まれており、並列テストの悪化原因を解析して 217.95 秒へ回復させた記事 で解説した対策後のテストスイート全体（wall-time）は 217.95 秒へ下がっています（その後の短縮経緯と前提の変化は後半で扱います）1。

rebase 後の検証済み状態引き継ぎとは、git rebase によってコミット SHA が書き換わった後も、「パッチ内容の同一性」「取り込んだ上流変更との変更ファイル非重複」「新 base での CI 成功」を機械的に確認できた場合に限り、前の HEAD で完了した検証結果を新しい HEAD へ継承してテスト再実行を省略する品質ゲート機構です。

ただし、git range-diff で全コミットが = と表示されるからといって安易にテストを省略すると、改名（rename）されたファイルの上流衝突や不完全な CI 状態を見落とします。支援パイプラインA では、3 条件の判定を人の目視や呼び出し元の事前判断に委ねず、検証の前段で無条件に実行する決定論的スクリプトへ切り出し、和文境界や複数ワークフローなどの境界バグを単体テストで塞いで安全側に倒す形を作りました1。

rebase 後の検証済み状態の引き継ぎに 3 条件とスクリプト判定を選んだ理由

無関係な main 更新を取り込む rebase 後に検証済み状態を引き継ぐには、git range-diff の一致を単独で信じるのではなく、上流変更との非重複と新 base の CI 成功を束ねた 3 条件を機械的に判定する必要があります。本節では支援パイプラインA の実装を題材に、なぜこの 3 条件を揃えたのか、そしてなぜ人の目視や AI の判断ではなく検証前段で無条件に呼ぶスクリプトへ切り出したのかを順に整理します。

git range-diff で全コミット = だけでは足りない 3 条件

git range-diff は Git 2.19（2018年9月）で導入されたコマンドであり、git rebase や amend 前後の 2 つのコミット範囲を比較して各コミットの対応関係を中央の記号で示します23。まず、公式ドキュメントに掲載されている出力例を確認します。

次の引用は、git range-diff が出力する 4 種類の状態記号（>・=・!・<）の並び方を示すためのものです3。

引用元: Git 公式ドキュメント git-range-diff（https://git-scm.com/docs/git-range-diff）

-:  ------- > 1:  0ddba11 Prepare for the inevitable!
1:  c0debee = 2:  cab005e Add a helpful message at the start
2:  f00dbal ! 3:  decafe1 Describe a bug
    @@ -1,3 +1,3 @@
     Author: A U Thor <author@example.com>

    -TODO: Describe a bug
    +Describe a bug
    @@ -324,5 +324,6
      This is expected.

    -+What is unexpected is that it will also crash.
    ++Unexpectedly, it also crashes. This is a bug, and the jury is
    ++still out there how to fix it best. See ticket #314 for details.

      Contact
3:  bedead < -:  ------- TO-UNDO

1: c0debee = 2: cab005e のように中央に = が並ぶ行は、前後でパッチ差分・コミットメッセージ・著者情報に変化がない対応（perfect match）を表します3。1 行目の >（追加）、3 行目の !（diff またはコミットメッセージ等が変更）、末尾行の <（削除）が 1 行でも混じる場合は rebase 前後で中身や構成が変わっています3。なお、公式例中の 2: f00dbal は非 16 進文字 l を含む説明用の擬似 ID であり、実機コマンドが出力するコミット ID は 16 進の短縮 SHA です。

この git range-diff の仕組みを踏まえた上で、rebase 後の検証済み状態を引き継ぐには次の 3 条件をすべて満たす必要があります1。

  1. 条件 1: git range-diff --no-color の対応行が 1 行以上あり、すべて = であること !・<・> が 1 行でも混ざれば同一ではないため引き継ぎを拒否します13。さらに、range-diff が空出力を返した場合（対応行が存在しない状態）を誤って「= 以外の記号が 0 件だから一致」と通過させないよう、対応行が 1 行以上存在することを必須にします1。

  2. 条件 2: git diff --name-only --no-renames -z で改名を含め変更ファイルが非重複であること 自分のブランチのパッチがすべて = であっても、main 側が同じファイルや共通テスト設定を変更していれば rebase 後の挙動は変わりえます。そのため、「旧 base〜新 base の main 側変更ファイル」と「作業ブランチ側の変更ファイル」の共通集合が空であることを確かめます1。

    ここで --no-renames と -z の 2 オプションが欠かせません1。Git 2.9（2016年6月）以降、diff.renames がデフォルトで有効（true）になっており45、git diff --name-only は通常 post-image ツリー側の変更ファイル名だけを出力します4。つまり、main 側でファイル改名（旧パスから新パスへの変更）が起きたときに --no-renames を付けないと、出力には新パスしか現れず、作業ブランチ側が旧パスを変更している衝突を見落とします14。--no-renames で改名検出を無効化して旧パスの削除と新パスの追加の双方を出力させ、さらに -z で core.quotePath によるエスケープを抑止しつつ NUL 文字区切りでパスを安全に分割します4。

  3. 条件 3: 新 base の headSha に一致する全 CI ワークフローが成功していること 単にブランチの最新 CI 結果を見るのではなく、gh run list --commit <新baseのSHA> -L 100 --json headSha,status,conclusion,workflowName を実行して戻り値の headSha が新 base の 40 桁 SHA と一致する実行だけを抽出します16。そのうえで、対象コミットの CI 実行が 1 件以上存在し、すべてが status == "completed" かつ conclusion == "success" であることを確認します16。

なぜ目視や AI ではなく、検証前段で無条件に呼ぶスクリプトにしたか

git range-diff の公式ドキュメントは OUTPUT STABILITY 節において、この出力は人間向けの porcelain 出力であり、Git のバージョン間でテキスト的な安定性は保証されず、機械可読（machine-readable）を意図していないと明記しています3。また、従来の解説でも git range-diff は主に PR の fixup や interactive rebase の後に人間のレビュアーが差分意図を追う（interdiff review）用途で扱われてきました7。

それでも支援パイプラインA でスクリプト判定を選んだのは、実装時の記録に「判定を目で読ませると range-diff の ! 行や改名の見落としが起きるのでスクリプトにした」と残したとおり、見落としの実務リスクを抑えるためです1。柔軟な文脈判断を要する工程を AI に任せる設計であっても、再検証を省略できるかどうかの前提判定は 1 行の ! や 1 ファイルの改名を見落としただけで不具合が素通りします。この線引きは、「生成」と「転記」で AI への委譲を切り分ける設計 と同じ考え方であり、厳密な突合を決定論的コードへ閉じ込めました。

さらに、初版を実装した 2026年11月3日当日だけでオーケストレーション手順書に 3 回の連続改訂が入り、呼び出し設計として 「無条件呼び出し」かつ「初回検証の前段への配置」 が必須だと判明しました1。

  • 1 回目の改訂（無条件化）: 当初は「無関係な変更だけのとき呼ぶ」と呼び出し側（AI エージェント）に事前判断を委ねていましたが、呼び出し側が判断を省いてスクリプト実行自体を飛ばし全再実行に倒れてしまう問題が起きたため、「SHA が一致しないときは無条件にスクリプトを実行する」へ改めました1。AI への条件付きプロンプト指示は守られないリスクが常に伴うため、呼び出し条件を排して決定論的パスへ寄せています。
  • 2 回目の改訂（初回検証の前段へ移動）: 初版では後半の最終検収ステップに呼び出しを置いていましたが、前段の初回検証ステップで SHA 不一致のままテストが先に走ってしまうと、引き継ぎ判定に到達する経路そのものがなくなります1。そこで呼び出し位置を初回検証ステップの直前へ移しました1。
  • 3 回目の改訂（停止上限カウントからの除外）: パイプラインの「同一文言の停止出力が累積 2 回出たら強制停止する」ガードの数え方から引き継ぎ不可通知を外し、通常の再テスト分岐を通るだけで強制停止に達してしまう干渉を取り除きました1。

なお、スクリプト化と無条件化・前段への移動は同日に連続して投入されたため、各変更が実運用に与えた個別の寄与までは切り分けていません1。また、目視のまま運用した場合に何件の見落としが起きるかの比較計測も行っておらず、あくまで構造的な見落とし経路を塞ぐための設計選択です1。

以上の 3 条件（range-diff 全 =、--no-renames -z による非重複、gh run list の headSha 一致全 run 成功）と Fail-Closed のエラー終了をまとめた完結スクリプトを以下に示します。実行前提は Python 3.9 以上（標準ライブラリのみ使用、外部パッケージ不要）、git、および認証済みの gh CLI であり、たとえば python3 scripts/verify_carryover.py --old-base <old_base> --old-head <old_head> --new-base origin/main として実行します（本コードは読者が手元で動かせるよう書き起こした説明用の実装であり、実機出力ログは持たないため実行結果の掲載は省きます）。なお、--old-base には前回の検証記録時に --old-head と対で保存しておいた旧 base SHA を渡すか、main が fast-forward で前進する前提であれば git merge-base <old_head> <new_base> で共通祖先から旧 base を取得して渡します。

ファイル: scripts/verify_carryover.py

#!/usr/bin/env python3
"""Verify 3 carryover conditions after rebasing a branch onto a new base."""

import argparse
import json
import re
import subprocess
import sys

ROW_RE = re.compile(
    r"^\s*(?:\d+|-):\s+(?:[0-9a-f]+|-+)\s+([=!<>])\s+(?:\d+|-+):\s+(?:[0-9a-f]+|-+)(?:\s|$)"
)


def run_cmd(cmd: list[str]) -> str:
    proc = subprocess.run(cmd, capture_output=True, text=True, encoding="utf-8")
    if proc.returncode != 0:
        detail = proc.stderr.strip() or proc.stdout.strip() or f"exit {proc.returncode}"
        raise RuntimeError(f"{' '.join(cmd)}: {detail}")
    return proc.stdout


def changed_files(rev_range: str) -> set[str]:
    out = run_cmd(["git", "diff", "--name-only", "--no-renames", "-z", rev_range])
    return {f for f in out.split("\0") if f}


def check_carryover(
    old_base: str, old_head: str, new_base: str, head: str = "HEAD"
) -> tuple[bool, str]:
    # 0. 新 base の 40 桁 SHA を解決し、現在の HEAD が rebase 済みか確認する
    new_base_sha = run_cmd(
        ["git", "rev-parse", "--verify", f"{new_base}^{{commit}}"]
    ).strip()
    is_rebased = subprocess.run(
        ["git", "merge-base", "--is-ancestor", new_base_sha, head],
        capture_output=True,
        text=True,
    )
    if is_rebased.returncode != 0:
        return False, "現在の HEAD に新 base が取り込まれていません。"

    # 1. git range-diff --no-color が 1 行以上かつ全非空行が = であること
    rd_out = run_cmd(
        [
            "git",
            "range-diff",
            "--no-color",
            f"{old_base}..{old_head}",
            f"{new_base_sha}..{head}",
        ]
    )
    lines = [line for line in rd_out.splitlines() if line.strip()]
    if not lines:
        return False, "range-diff の出力が空のため引き継げません。"

    for line in lines:
        match = ROW_RE.match(line)
        if not match:
            return False, f"解釈できない range-diff 行を検出しました: {line}"
        if match.group(1) != "=":
            return False, f"range-diff に '=' 以外の変更が含まれています: {line}"

    # 2. main 側の更新と作業ブランチ側の変更ファイルが改名を含めて重ならないこと
    main_files = changed_files(f"{old_base}..{new_base_sha}")
    branch_files = changed_files(f"{new_base_sha}..{head}") | changed_files(
        f"{old_base}..{old_head}"
    )
    overlap = sorted(main_files & branch_files)
    if overlap:
        return False, f"変更ファイルが重複しています: {', '.join(overlap)}"

    # 3. 新 base の headSha に一致する全 CI ワークフローが completed/success であること
    ci_raw = run_cmd(
        [
            "gh",
            "run",
            "list",
            "--commit",
            new_base_sha,
            "-L",
            "100",
            "--json",
            "headSha,status,conclusion,workflowName",
        ]
    )
    all_runs = json.loads(ci_raw)
    runs = [r for r in all_runs if r.get("headSha") == new_base_sha]
    if not runs:
        return False, f"新 base ({new_base_sha}) の CI 実行が見つかりません。"

    bad = [
        r
        for r in runs
        if r.get("status") != "completed" or r.get("conclusion") != "success"
    ]
    if bad:
        names = ", ".join(r.get("workflowName") or "unknown" for r in bad)
        return False, f"新 base の CI が完了・成功していません: {names}"

    return True, f"引き継ぎ可能です（{len(lines)} コミット一致、重複 0 件、CI {len(runs)} 件成功）。"


def main() -> int:
    parser = argparse.ArgumentParser(
        description="rebase 後に既存の検証済み状態を引き継げるか 3 条件を判定する"
    )
    parser.add_argument("--old-base", required=True, help="rebase 前の base SHA")
    parser.add_argument("--old-head", required=True, help="検証済みだった旧 HEAD SHA")
    parser.add_argument("--new-base", required=True, help="rebase 先の新 base 参照")
    parser.add_argument("--head", default="HEAD", help="現在の HEAD 参照（既定: HEAD）")
    args = parser.parse_args()

    try:
        ok, message = check_carryover(
            args.old_base, args.old_head, args.new_base, args.head
        )
    except (RuntimeError, json.JSONDecodeError) as exc:
        print(
            f"引き継ぎ判定に失敗したため、通常のテストを再実行してください: {exc}",
            file=sys.stderr,
        )
        return 1

    if not ok:
        print(
            f"引き継ぎ不可のため、通常のテストを再実行してください: {message}",
            file=sys.stderr,
        )
        return 1

    print(message)
    return 0


if __name__ == "__main__":
    sys.exit(main())

実装上の要点は以下の 5 点です。

  • ROW_RE 先頭の \s* と全非空行の厳密照合: git range-diff はコミット数が 10 件以上になると番号列の右詰め空白パディングが入るため先頭に \s* を許容しています。また、ROW_RE に一致しない非空行を黙って読み飛ばすと将来の書式変更時に危険な素通りを招くため、1 行でも解釈できなければ即座に引き継ぎ不可とします。
  • changed_files での {f for f in out.split("\0") if f}: -z オプションは各パスの末尾を NUL 文字で終端するため、split("\0") の末尾に生じる空文字列を if f で除外しています。
  • git merge-base --is-ancestor と old_base の取得・branch_files の和集合: rebase 未実施の HEAD を通さないよう祖先関係を先に確認したうえで、main が fast-forward で前進する前提で old_base..new_base_sha の変更を取り出しています。--old-base 自体もこの fast-forward 前提のもとでは git merge-base <old_head> <new_base_sha> から復元できるため、後述する作業メモのように前回の検証済み HEAD の 40 桁 SHA だけを 1 つ記録しておく運用でも呼び出し可能です（もちろん、記録時点で旧 base と旧 HEAD を対で保存して渡しても構いません）。また、branch_files で new_base_sha..head と old_base..old_head の和集合を取っているのは、万一 rebase 時にファイル集合の差異が紛れた場合にも衝突側を確実に拾う二重の安全策です。
  • gh run list の -L 100 と headSha 直接照合: gh run list の取得上限は既定で 20 件であるため -L 100（取得上限 100 件）へ引き上げつつ、戻り値配列を headSha == new_base_sha で明示的に絞り込んでいます6。1 コミットあたりの実行数が上限 100 件に達する大規模リポジトリでは、--branch による絞り込みなどで取得対象をさらに限定する設計が必要です。なお、この説明用実装ではトリガー種別（push・schedule 等）を絞らず対象 SHA の全実行を検査するため、無関係なトリガーの失敗や実行開始直前の 0 件状態もすべて安全側（再テスト）に倒れます。
  • Fail-Closed のエラー処理: git や gh のコマンド実行が失敗したり JSON 解析に失敗したりした場合も終了コード 1 を返し、通常のテスト再実行へ倒します。

境界の穴と「安全側への過剰拒否」というトレードオフ

3 条件をスクリプトへ切り出しただけでは、実運用の境界ケースは塞ぎきれません。導入翌日のコードレビューで見つかった 3 つの境界バグの修正内容と、安全側（Fail-Closed）に倒した運用で実際に記録された停止事例・残余リスクを整理します。

レビューで見つかり塞いだ 3 つの境界と単体テスト 23 本

スクリプト導入翌日の 2026年11月4日、コードレビューで指摘された 3 つの境界バグを修正し、単体テストを初版 19 本に 4 本追加して計 23 本へ拡張しました1。この 23 本の単体テストは、検証日である 2026年11月16日時点でもすべて通過しています（実行時間 29.480 秒）1。

修正した境界の 1 つ目は、前段で作業メモから検証済み SHA を読み取る正規表現で、40 桁 SHA に日本語が直結すると \b が一致しない罠 です1。Python 3 の re モジュールはデフォルトで Unicode モードが有効であるため、単語境界 \b が参照する \w には ASCII 英数字だけでなく str.isalnum() が真となる全 Unicode 文字（ひらがな・カタカナ・漢字を含む）が含まれます8。そのため、作業メモの検証済み記録が「<接頭辞> verified <40桁SHA>の検証で」のように SHA の直後に日本語が続く表記になると、英数字と日本語の両側が \w と判定されて \b がマッチしません18。

次のスクリプトは、40 桁 SHA の直後に日本語が続く文字列で \b が失敗し、ASCII 文字のみを除外する否定先読み（negative lookahead）(?![0-9A-Za-z]) で正しくマッチすることを手元で確かめる例です（実行コマンドは python3 check_sha_boundary.py、Python 3 標準ライブラリ re のみ使用、実機出力の掲載は省きます）。

ファイル: check_sha_boundary.py

#!/usr/bin/env python3
"""Demonstrate why \\b fails when Japanese text follows a 40-char SHA."""

import re


def main() -> None:
    sha = "a" * 40
    samples = [
        f"verified {sha} passed",
        f"verified {sha}の検証で",
    ]

    old_re = re.compile(r"^verified ([0-9a-f]{40})\b")
    new_re = re.compile(r"^verified ([0-9a-f]{40})(?![0-9A-Za-z])")

    for text in samples:
        old_hit = old_re.search(text) is not None
        new_hit = new_re.search(text) is not None
        print(f"{text!r} -> old(\\b)={old_hit}, new(lookaround)={new_hit}")

    assert old_re.search(samples[0]) is not None
    assert old_re.search(samples[1]) is None
    assert new_re.search(samples[0]) is not None
    assert new_re.search(samples[1]) is not None


if __name__ == "__main__":
    main()

re.ASCII フラグをパターン全体へ付けて \b を ASCII 境界に制限する方法もありますが8、同一パターン内に日本語ラベル等を混在させたくなった場合に意図しない影響が及びます。SHA の末尾だけを (?![0-9A-Za-z]) で切る形にすれば、日本語ラベル等を混在させる場合にも影響範囲を局所化できます。

修正した境界の 2 つ目は、runs[0] の 1 本判定が複数ワークフローの失敗を見逃す穴 です1。初版では gh run list の結果配列から先頭 1 件（runs[0]）だけを見て成功判定をしていましたが、テスト・Linter・ビルドなど複数ワークフローが並列稼働する環境では、先頭 1 件が成功でも別ワークフローが失敗または実行中である場合に誤通過を許します1。そこで -L 100 で得た新 base の headSha に一致する全 run について、status != "completed" または conclusion != "success" に該当する run が 1 件でもあれば拒否する実装へ改めました16。

修正した境界の 3 つ目は、取得失敗時に誤った条件番号を出さないエラー設計 です1。git diff・git range-diff・gh run list のコマンド実行自体が失敗する 3 箇所では、引き継ぎ 3 条件の番号を紐づけて出力していたのを外し、すべて「引き継がずに通常の検証手段（テスト）を再実行する」という同一の次の一手へ統一しました（未コミット変更が残っている場合のみ先にコミットを促す例外を維持しています）1。

なお、これら 3 件はレビュー指摘に基づく予防的な修正であり、修正前の実運用で \b 不一致や runs[0] 問題が実際に何回発生したかの記録は残っていません（当時の課題記録上も実害や誤引き継ぎは起きていなかったとされています）1。また、3 件とも同一リリースで投入されたため、個々の修正がエラー率へ与えた単独の寄与は切り分けられません1。

安全側に倒した運用の現実 ── 停止事例 10 件と微修正拒否の課題・残余リスク

導入後の運用集計（集計対象期間 2026年10月27日〜11月10日、導入日 11月3日以降 11月10日までの実運用期間を含む）において、引き継ぎ不可で停止したケースが日次エラー集計で 10 件 記録されています（発生日は 11月3日: 2 件、11月4日: 3 件、11月5日: 1 件、11月9日: 4 件）1。

このとき副次的に見つかったのが、スクリプトが出力する停止メッセージを後段の日次監視が行頭一致で集計していた仕組みの漏れ でした。10 件のうち 5 件 は、作業メモ更新ログ（3 件）や状態出力行（2 件）といった前置き出力が停止メッセージの前に挟まっていたため、行頭一致を前提にしていた日次の監視署名から漏れていたのです（既存署名一致 4 件、別の監視機構での捕捉 1 件、前置きによる漏れ 5 件）1。2026年11月11日に監視側の正規表現を修正して漏れを 0 件にしましたが1、前置き出力が先頭一致ガードをすり抜ける構造は、承認ログと成果物検収を分離する記事 で扱った「応答の先頭に 1 行前置きが入るだけで先頭文字列一致のチェックが素通りする罠」と同型でした。

さらに運用で見えてきたのが、厳格さと手間のトレードオフ です。判定がパッチ差分の完全一致を求めるため、停止ログの署名注記で引用されている改善メモには「レビュー指摘の文言 2 語を直しただけでも引き継ぎは拒否され、全体テストの再実行が要った」という趣旨の課題が記されています（該当コミットの実物は未確認であり、改善メモからの引用記録として参照しています）1。このように、意味が変わらないコメントやドキュメント文言だけの軽微な修正であっても直前コミットの差分が変わる限り git range-diff は ! を出すため3、安全側（再テスト）へ倒れます。

ここで「コメントやドキュメントの微修正ぐらいは通せるように例外ルールを足すべきではないか」という反論が成り立ちます。しかし、特定拡張子やコメント差分を除外するルールを増やせば、テスト入力に使われるテキストファイルや設定ファイルを見誤って素通りさせる危険が同時に増えます。テストの所要時間が許容範囲に収まっているなら、「迷ったら引き継がずにテストを回す」という Fail-Closed の原則を崩さない方が品質ゲートとしては健全です。

反対側の懸念として、「3 条件を揃えてもマージ後と同じ動作が完全に保証されるのか」という残余リスク も明確にしておく必要があります。変更ファイルが非重複であっても、上流の main 側が別ファイル上の公開関数シグネチャや共有定数を変更していれば作業ブランチの挙動は壊れえます。また、条件 3 が確認しているのは「rebase 前の新 base 単体の CI」であり、マージ後の統合状態（たとえば GitHub Merge Queue が一時ブランチで検証する結合 CI）そのものではありません9。したがって、この引き継ぎ機構は「ファイル非重複と型・結合テストが統合破損を拾える前提のもとで、開発途中の重い再テストコストを抑える」場面に限定し、最終マージ前のゲートには統合テストや Merge Queue 等を併用する役割分担とします。

加えて、実運用の記録上の線引きも明示します。上記 10 件が条件 1〜3 のどれで発生したかという条件別内訳は集計に含まれておらず、また記録として残っているのは拒否された停止側 10 件のみであり、導入後の引き継ぎ成立回数や累計で何分のテスト時間を削減できたかは計測されていません（一次記録として確認できている成立事例は、導入前の手動引き継ぎ 1 回と過去履歴に対する動作検証 1 回のみです）1。

代替手法との位置づけ比較と前提が変わるときの見直し軸

git range-diff による 3 条件判定は万能の仕組みではなく、Git 本来のパッチ比較コマンドやサーバー側の CI 最適化機能とは守備範囲が異なります。関連する手法とレイヤーを並べたうえで、前提条件が変わったときの引き際を整理します。

git patch-id・GitHub Merge Queue・skip-duplicate-actions との比較

ローカルの作業ブランチで git rebase 直後に再テストを省きたい場合、本稿の 3 条件判定は単一コミット比較の git patch-id、サーバー側キューの GitHub Merge Queue（以下 Merge Queue）、ジョブキャッシュ系の skip-duplicate-actions と守備範囲が異なるため、目的と実行レイヤーに応じて使い分ける必要があります。

前提が変われば結論はどう変わるか

3 条件による引き継ぎ機構は、次の 2 つの前提が変われば見直しの対象になります。

  1. テスト実行時間自体が短縮された場合（投資対効果の変化） 支援パイプラインA でも、発端となった 2026年10月29日時点は共有資源競合により 10 並列の最長クラスが 673.8 秒〜730.9 秒（全クラス所要合計 5,499 秒〜5,772 秒）かかっていましたが、競合対策後の全体 wall-time は 217.95 秒へ下がり、2026年11月3日時点では 69.2 秒、2026年11月11日時点では 85.9 秒で完了していました1。もしテストスイート全体が数秒〜数十秒で安定して完了する環境であれば、引き継ぎ判定スクリプトの保守や境界ケースのケアに労力を割くより、「rebase したら毎回愚直に全テストを回す」方がシンプルで安全です。引き継ぎ機構がペイするかどうかは、対象テストの所要時間と rebase 頻度の釣り合いで決まります。

  2. Git バージョンアップで git range-diff の出力書式が変わった場合 公式ドキュメントの OUTPUT STABILITY 節のとおり、git range-diff の出力書式は将来のバージョンで変わりえます3。この前提に対しては、「空出力だけでなく、1 行でも書式解釈できない行や未知の記号が混じれば必ず引き継ぎ不可（再テスト）へ倒す」という Fail-Closed 設計と単体テストを維持していれば、書式変更時に一部の行を読み飛ばしたままテストをスキップする事故を防ぎやすく、安全側に退避したうえでパーサーを更新できます。将来的により安定した機械可読な比較手段や差分ハッシュ比較へ置き換える選択肢も開かれています。

よくある質問（FAQ）

Q. git range-diff で全コミットが = なら、rebase 後のテストは省略してよいのですか？

A. git range-diff が全コミット = であっても、それだけではテストを省略できません。= は自分の各コミットが導入するパッチ差分が変わっていないことしか示しません。取り込んだ main 側の変更が自分の変更ファイルと衝突している場合や、新 base 自体の CI が失敗している場合は挙動が壊れうるため、range-diff の全コミット = に加えて、--no-renames を含むファイル非重複確認と新 base の CI 成功確認の 3 条件を揃える必要があります（なお、3 条件は別ファイル間の公開 API シグネチャ変更や統合後の最終挙動までを完全に保証するものではないため、開発途中の再実行抑制とマージ前統合ゲートを併用する前提で運用します）。

Q. git diff —name-only に —no-renames を付ける必要があるのはなぜですか？

A. Git 2.9 以降はファイル改名（rename）検出がデフォルトで有効になっており、--no-renames を付けずに --name-only を実行すると post-image ツリーのファイル名（新パス側）だけが出力され、旧パス側が出力から落ちるためです。上流でファイルが改名された際に、作業ブランチ側が旧パスを変更している重複を見落とさないよう、--no-renames と -z を指定して旧パス・新パスの両方を確実に突き合わせます。

Q. Git 公式が「機械可読を意図していない」とする git range-diff をスクリプトで解析して大丈夫ですか？

A. 解釈に失敗した場合や想定外の出力を得た場合に、必ず引き継ぎを拒否して通常テストへフォールバックする「安全側（Fail-Closed）」の設計を徹底できるなら実務で運用できます。公式の OUTPUT STABILITY 節の注記どおりテキスト形式の将来保証はないため、「空出力だけでなく、1 行でも書式解釈できない行が混じれば不可」「= 以外の記号や取得エラー時は再テスト」という条件と単体テストを組み合わせて誤通過を防ぎます。

まとめ

  • git rebase 後に検証済み状態を安全に引き継ぐには、パッチ同一性・改名を含む非重複・新 base CI 成功の 3 条件を揃えて確認する必要があります。具体的には、git range-diff --no-color の全非空行が解釈可能で 1 行以上かつすべて = であることに加え、git diff --name-only --no-renames -z による変更ファイル非重複と、新 base の headSha に一致する CI ワークフロー（-L 100 等で取得上限を引き上げて確認）の全 completed/success を機械的に突き合わせます。
  • 引き継ぎ判定は人の目視や AI の裁量に任せず、初回検証の前段で無条件に実行する決定論的スクリプトへ切り出す設計が有効です。range-diff の ! 行やファイル改名の見落とし、および呼び出し元の事前判断によるスキップを防げます。
  • 正規表現や取得上限といった境界の穴は、境界ケースを単体テストで固定して塞ぐ必要があります。40 桁 SHA の直後に日本語が続く文字列に \b が一致しない問題（(?![0-9A-Za-z]) で回避）や、先頭 1 件 runs[0] のみを見て別ワークフローの失敗を見逃す穴は、境界ケースを単体テスト（支援パイプラインA では 23 本）で固定することで塞げます。
  • 判定を安全側（Fail-Closed）に倒す運用には、微修正でも再テストへ倒れる厳格さとのトレードオフがあり、マージ前統合ゲートとの役割分担が前提になります。支援パイプラインA の集計期間（2026年10月27日〜11月10日、導入日 11月3日以降）でも 10 件の引き継ぎ不可停止が記録され、停止ログ中の改善メモ引用にあるような文言 2 語の修正でも再テストが走りました。また、別ファイル間の公開 API 変更までは見切れない限界も前提に置く必要があります。
  • テスト時間自体が短縮されたりスクリプトの保守負担が見合わなくなったりした場合は、引き継ぎ機構に固執せず毎回全テストを回す運用へ切り替える判断が合理的です。数秒〜数十秒帯で完了する環境なら、判定ロジックを維持するより愚直な再テストの方がシンプルで安全です。
