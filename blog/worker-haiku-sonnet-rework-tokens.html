Claude Code 実装 worker で Haiku と Sonnet を実測比較 ── 差し戻し込みの総トークンは Sonnet が少なかった

Claude Code などのコーディングエージェントで実装タスクをサブエージェントや自律ワーカー（worker）に委任するとき、API のトークン単価が安い小型モデル（Claude Haiku 5.5 等）を選べば総コストを抑えられると考えがちです。しかし、レビューやテストによる「検収」と差し戻しを伴う開発パイプラインでは、トークンの総消費量でも、司令塔や人の確認を含めたタスク完了までの負担でも、単価表の見た目どおりの差が出ないことがあります。

ここで重要になるのが、1 回の API 呼び出し単価（Price per Million Tokens）ではなく、やり直しや差し戻し往復を含めてタスクを完了させるまでに消費した総トークン量とコストで評価する Cost-Per-Task（タスク完了あたりのコスト） という指標です123。とくに実装タスクを担う AI エージェントでは、レビュー指摘に伴う修正セッションの継続や再実行によって会話履歴が毎ターン再送信されるため、差し戻し往復が増えるほど追加のトークン負荷と確認側の負荷が積み上がります。

私が管理している当ブログの運営リポジトリ（非公開）の自社開発パイプラインにおいて、実装タスク 14 件の worker セッション消費トークンを実測したところ、worker に Claude Haiku 5.5（設定表記: haiku/medium）を用いた 9 件は、リポジトリ内の運用ガイド文書や要約の更新漏れなどによる差し戻し（平均 0.78 往復）を含め 1 件あたり平均 3.69M トークン（3,694,069 トークン）を消費しました。これに対し、Claude Sonnet 5.5（設定表記: sonnet/high）を用いた 5 件は平均 0.20 往復・1 件あたり平均 1.26M トークン（1,255,070 トークン）にとどまり、総消費トークンでも差し戻し回数でも Sonnet 群の方が少なくなりました4。なお、本実測で直接比較した一次指標は worker 単体の総トークン数と差し戻し往復数であり、実際の API 課金額（USD）や司令塔（opus/low）の消費分は未計測です4。その上で、トークン総量が約 2.9 倍に膨らみ差し戻しが重なる構図が、なぜ単価表の差を縮めて運用コストを圧迫するのかを一次ログから解剖します。

単発のテスト試行で手応えがあっても、検収を挟む実務運用では差し戻しによるターン数の増加が総消費を押し上げます。既刊の サブエージェント3モデルの実測記事 で扱った狭く閉じた事実抽出タスク（Haiku 5.5 が高精度・低コストを示した例）や、親設定の透過課金が原因だった advisor 設定波及の検証記事 とは異なり、本記事では実装 worker における「差し戻しと総トークン逆転」の一次ログを解剖し、用途別のモデル選定基準とログ監査の具体的なやり方を整理します。

検証環境と調査スコープ

今回の実測は、当ブログの運営リポジトリ（非公開）にて 2026 年 10 月 31 日〜11 月 1 日（UTC 2026-10-31T18:49:26Z〜2026-11-01T03:22:07Z、日本時間 2026 年 11 月 1 日 03:49〜12:22）に自律実装パイプラインで連続実行した実装タスク 14 件を対象としています4。

パイプライン構成と計測単位

パイプラインは、仕様確認とコードレビューを担当する司令塔（オーケストレーター）と、隔離された git worktree 内で実装および修正コミットを行う実装 worker の 2 役で構成されています4。

  • 司令塔（オーケストレーター・レビュー担当）: Claude Opus 5.5（設定: opus/low）4
  • 実装 worker（前半 9 件）: Claude Haiku 5.5（モデル ID: claude-haiku-5-55、設定: haiku/medium）46
  • 実装 worker（後半 5 件）: Claude Sonnet 5.5（モデル ID: claude-sonnet-5-57、設定: sonnet/high）48

計測対象は 実装 worker 単体のセッション消費トークン（以下、worker_tokens）と、司令塔とのレビュー差し戻し往復数、修正指示の送信回数（send）、検証失敗回数、中断回数（halt）です4。14 件すべてにおいて worker 自身がさらに子サブエージェントを起動した回数は 0 回でした4。なお、API 上の既定 effort は Claude Haiku 5.5（2026 年 10 月 7 日リリース）が medium6、Claude Sonnet 5.5（2026 年 9 月 28 日リリース）が high である一方、Claude Code およびアプリ上の Sonnet 5.5 の既定 effort は medium に設定されています78。effort パラメータは推論の深さだけでなく、読むファイル数や検証回数にも影響します9。

計測の経緯と既定切り替えの時系列

もともとこの連続実行は「細かく指示を出せば Haiku 5.5 でも高い再現性が出るのでは」という期待から、性能確認を兼ねて開始しました4。隔離 worktree を片付けると内部の作業用設定ファイルが消えて使用モデル名が失われるため、1 件完了するごとにタスク管理の計測メモへモデル名・往復数・総トークンを手元で記録し、あとから各 worker セッションの生トランスクリプト（.jsonl）を全件再集計して突き合わせています4。

経過としては、当時の既定設定である haiku/medium で 9 件を実行したあと、比較対象として haiku/high による effort 単独検証は挟まず、sonnet/high を明示指定して先行 3 件を実行しました4。2026 年 11 月 1 日 00:52Z（日本時間 09:52）時点でこの途中集計（haiku/medium 9 件 vs sonnet/high 3 件）を比較した流れでローカルの既定設定を sonnet/high へ切り替えており（切替時にどの指標を最重視したかの内訳まではログに残っていません）、同セッション後半（03:09Z〜03:22Z）に既定設定のまま追加 2 件を実行して計 14 件の記録が揃いました4。

調査スコープの境界（書けること・書けないこと）

実務ログに基づく調査であるため、以下の 3 つの境界（交絡要因と未計測事項）を明確に置いた上でデータを解釈します。

  1. 非対照実験によるタスク規模・条件差: 2 群は同一課題を両モデルに解かせた A/B テストではなく、実務で積まれていたタスク列を順に処理した記録です4。haiku/medium 期（9 件）と sonnet/high 期（5 件）では変更ファイル数や作業規模、詳細仕様メモの有無（haiku/medium 期の 1 件のみ仕様メモなし）が揃っていません4。実際、sonnet/high 後半の 1 件は公開記事の軽微な訂正のみで 792,107 トークンにとどまり、平均値を押し下げています4。
  2. モデル差と effort 差の同時変更: 前半は haiku/medium、後半は sonnet/high であり、モデル（Haiku 5.5 vs Sonnet 5.5）と effort 設定（medium vs high）が同時に変わっています49。したがって、観測された差がモデル能力のみに由来するのか、high effort による探索・検証の徹底度の影響を含むのかは、このログ単独では切り分けられません4。
  3. 未計測事項（USD 金額・司令塔消費・ターン別分布）: 集計はトランスクリプト記録に基づく実トークン数のみであり、モデル別 API 料金（USD）の実支払額比較、司令塔（opus/low）側のトークン消費比較、および各リクエスト単体で 100K トークンを超過した回数の分布は計測・集計していません4。

なぜ単価が安くても総トークンが膨らむのか：エージェントのターン蓄積構造

モデル単価では大きな開きがあるにもかかわらず、なぜ実装タスク全体の消費トークンや実効コストで逆転が起き得るのでしょうか。その背景には、コーディングエージェントのターン蓄積構造と、Claude Haiku 5.5 の価格仕様の 2 点があります。

毎ターン会話全体を再送信するターン蓄積構造

LLM API はステートレスであるため、Claude Code のようなエージェントがファイルを読み込み、編集し、テストを実行するたびに 1 回の API リクエスト（1 ターン / req）が発生します。各リクエストでは、システムプロンプト、ツール定義、プロジェクトのガイド設定（CLAUDE.md 等）、それまでの会話履歴とツール出力のすべてをプレフィックスとして再送信し、末尾に新しいメッセージを追加します1011。

Anthropic の Addy Osmani による試算例でも、20K トークンから 120K トークンへ文脈が成長するタスクは、40 ターン（1 ターン平均 70K 想定）で累積入力が約 2.8M トークンに達するのに対し、25 ターンで終えられれば約 1.75M トークンに収まります1。1 ターン増えるごとに増加分だけでなく過去の履歴全体を再送するため、「最も安いターンは不要なターンである」という構造になります1。Honeycomb のエンジニアリングブログも、LLM コスト浪費の代表パターンとして「結果改善に寄与しない入力の反復送信」と「無制限のリトライ・修正ループ」を挙げ、単発のトークン総量ではなく「成功結果あたりのコスト（cost per successful outcome）」で計測する重要性を指摘しています3。

総トークンの 88.6%〜97.4% を占めたキャッシュ読出の正体

再送されたプレフィックスを低遅延・低単価で再利用するのがプロンプトキャッシュ（Prompt Caching）です。API レスポンスの usage オブジェクトには、未キャッシュ入力の input_tokens、キャッシュ書込の cache_creation_input_tokens、キャッシュ読出の cache_read_input_tokens が、出力の output_tokens とは別に記録されます10。拡張思考（thinking）が有効な場合、前ターンの思考ブロックも次ターンではキャッシュ読出として入力トークンに算入されます10。

今回の実装 worker 14 件の実測でも、総消費トークンの大半はキャッシュ読出が占めていました4。最多となったタスク 3（8,200,207 トークン）では 97.4%（7,987,239 トークン）、Sonnet 群で最多となったタスク 14（1,650,174 トークン）でも 93.5%（1,542,352 トークン）、全 14 件を通じた範囲でも 88.6%〜97.4% に達しています4。つまり、修正や差し戻しでターン数（req）が伸びるほど、膨らんだ履歴をキャッシュから読み直す回数が掛け算で増えていきます。

料金体系の背景構造と Haiku 5.5 の 100K トークン境界

API 料金は改定によって変わり得るため、本記事の比較の主軸は不変の実測指標であるトークン数と差し戻し往復数に置きます。その上で、なぜ単価表の差ほど実効コストが開きにくいかという背景構造を、2026 年 11 月時点の Anthropic 公式料金表（100 万トークンあたり）で確認しておきます12。

  • Claude Sonnet 5.5: 基本入力 $2、出力 $10、5 分キャッシュ書込 $2.50、キャッシュ読出 $0.10（基本入力の 0.05 倍。Haiku 5.5 発表同日の 2026 年 10 月 7 日に $0.20 から半額化）512
  • Claude Haiku 5.5（100K トークン以下）: 基本入力 $0.10、出力 $0.50、5 分キャッシュ書込 $0.125、キャッシュ読出 $0.01（基本入力の 0.1 倍）12
  • Claude Haiku 5.5（100K トークン超）: 基本入力 $0.50、出力 $2.50、5 分キャッシュ書込 $0.625、キャッシュ読出 $0.05（基本入力の 0.1 倍）12

ここで見落としやすいのが、Haiku 5.5 の 100K トークン境界は未キャッシュ入力だけでなく cache_read_input_tokens と cache_creation_input_tokens を含む全入力トークンの合計で判定される という仕様です12。リクエスト単位で 100,000 トークンを超えると、そのリクエストの入力・出力・キャッシュ書込・キャッシュ読出すべてに 5 倍の上位ティア単価が適用されます212。

キャッシュ読出が消費の大部分を占める実装セッションでは、100K 以下でも Haiku と Sonnet のキャッシュ読出単価差は 10 倍（$0.01 vs $0.10）、100K を超えると わずか 2 倍（$0.05 vs $0.10） まで縮まります12。さらに、公式ベンチマーク Terminal-Bench 4.0 の medium effort における 1 試行あたりコスト比較では、Haiku 5.5（$0.68・スコア 20.3%）と Sonnet 5.5（$0.68・スコア 28.8%）が同額に並び、Sonnet がスコアで 8.5 ポイント上回る結果も公表されています5。

ここを切り分けて整理すると、仮に worker 単体の総トークン差が後述の実測どおり約 2.9 倍にとどまる場合、100K 以下の単価帯（キャッシュ読出 10 倍差・出力 20 倍差）が保たれていれば worker だけの API 課金額はなお Haiku 側が低く収まる計算になります。しかし実務の Cost-Per-Task では、第 1 にセッションが長引いて 100K トークン超の価格帯に入るとキャッシュ読出の単価差が 2 倍（出力・キャッシュ書込も 4 倍）まで縮まる点12、第 2 に差し戻し 1 往復ごとに最上位モデル（本構成では opus/low）の司令塔による再レビューと人の確認・待機負荷が上乗せされる点4が、単価表上の優位を削る方向に働きます。

一方、サブエージェント自体は親と独立したコンテキスト・ツール構成で起動するため、セッション途中でモデルを切り替えるようなキャッシュ無効化（コールドスタート）の損失を構造的に受けにくい利点があります211。したがって、Haiku 5.5 の二重価格は直感的に把握しづらいものの、サブエージェントのように 1 指示で小さく動かして 100K 以下で完結させる用途であれば高い費用対効果を期待できます。反対に、検収を伴うパイプラインで差し戻しが発生し、同じセッションの続きで修正を重ねてトークン量が膨らみ 100K トークン超の価格帯へ入ってしまうリスクを避けるには、最初からリトライを減らせる上位モデルを選ぶ設計が適しています（なお今回の実測 14 件では、個別リクエスト単位で 100K を超えた回数そのものは集計対象外としています4）。

実測データ比較：Haiku 9件と Sonnet 5件の往復数・総トークン数

途中集計・丸め差の訂正履歴

既定値を切り替えた時点（先行 3 件完了時）に残した備忘メモには、当時の途中集計である「Sonnet 3 件・0 往復・1.28M」と、セッション内報告の丸め表記「Haiku 3.70M」「最多 8.2M」が記されていました4。その後、同セッション後半の追加 2 件を含めた全 14 件の生トランスクリプトとタスク管理記録を 1 トークン単位で再集計した結果、Sonnet 全 5 件では「平均 0.20 往復・1.26M（1,255,070）」、Haiku 9 件の実数平均は 3,694,069.33 を小数第 2 位で丸めた「3.69M」、最多案件の実数は「8.20M（8,200,207）」であることを確定しました4。途中集計と全件集計は時点の異なる実測値であり、本記事では全件実数を基準に扱います。

公平を期すと、sonnet/high のタスク 11（1,030,149）とタスク 13（792,107）は変更範囲が 1 ファイルかつ軽微であり、これらが Sonnet 平均を押し下げている点は割り引く必要があります4。一方で、設計書 8 本・18 箇所の一括修正と関連手順・抽出コードの同期を含むタスク 12（1,367,975 トークン / 14 req / 0 往復）を基準に、haiku/medium のタスク 8（3,565,409 / 31 req / 1 往復）およびタスク 9（6,192,316 / 50 req / 1 往復）と比べても、Haiku 側はそれぞれ約 2.6 倍〜約 4.5 倍（3,565,409 / 1,367,975 ≒ 2.61、6,192,316 / 1,367,975 ≒ 4.53）のトークンを消費しています4。複数文書の同期を含む複合改修となったタスク 3（8,200,207 / 59 req / 2 往復）では差がさらに開きました（ただしタスク間の変更複雑度は完全には揃っていません）4。

なお、最多のタスク 3（8,200,207 トークン）の 4 分類内訳は、未キャッシュ入力 118 + 出力 63,468 + キャッシュ書込 149,382 + キャッシュ読出 7,987,239（97.4%） でした4。Sonnet で唯一差し戻されたタスク 14（1,650,174 トークン）でも、未キャッシュ入力 32 + 出力 11,697 + キャッシュ書込 96,093 + キャッシュ読出 1,542,352（93.5%） という内訳であり、総消費の大部分がキャッシュ読出で膨らむ構造は両モデルで共通しています4。

haiku/medium で観測された「失敗の型」と sonnet/high の挙動差

単にトークン消費量に差が出ただけでなく、差し戻しが発生したタスクで何が起きていたかを解剖すると、モデルと effort の組み合わせごとに特徴的な傾向が見えてきます。

haiku/medium 差し戻し 6 件の内訳

haiku/medium 9 件のうち差し戻しが発生したのは 6 件（1 往復 5 件＋2 往復 1 件）でした4。指摘内容を一次ログから整理すると、大きく 2 つの型に分かれます。

  1. 同じ変更を他の参照箇所・周辺文書・要約へ反映し忘れる型（6 件中 4 件）
    • タスク 3・タスク 6・タスク 9 の 3 件では、スクリプトやルール本体を変更したにもかかわらず、リポジトリ内の運用ガイド文書の更新が漏れて差し戻されました4。
    • タスク 5 では、執筆支援手順書 2 件に置かれていた同一ルールの要約箇所だけ更新を取り残しました4。
    • 当時のセッション記録では、9 件を通じた総括として「要求の読み違いは出ておらず、要求解釈の面では見立てどおりだった一方、関連箇所まで同時に直す部分は司令塔のレビューに依存した」と振り返っています4。また、詳細な実装仕様書を与えたタスク 3 については「条文に書かれていない細部を取りこぼしており、細かく指示すれば再現性が高いという見立ての反例寄り」と記録されており、タスク 6 でも運用ガイドの更新漏れに加えて「終了コード説明の誤記述」という周辺同期以外の誤りが混入していました4。
  2. 挿入位置の誤りと実データ形状の取りこぼし（6 件中 2 件）
    • タスク 7 では、共通前処理の既存説明段落 2 つを分断する位置に新手順を差し込んでしまい、位置移動の差し戻しが発生しました4。
    • タスク 8 では、単体テストは通過したものの、実データに現れる 2 つの形状（同じキーが複数回並ぶケースと、出典注記内の「の意見」という語尾の有無や番号前の空白の有無による書式揺れ）を取りこぼして 1 往復しました4。

sonnet/high 5 件の対照的な挙動

一方、sonnet/high の 5 件には対照的な長所と、やはりゼロではない限界の両面が表れました。

  • 仕様書誤記の自律訂正（タスク 12）: 既存の設計書 8 本・18 箇所への一括反映を含むタスク 12 では、実は親セッション側が作成した仕様書に 2 件の誤り（参照番号の取り違えと、先行マージでずれていた台帳行番号）が含まれていました4。sonnet/high の worker は仕様書を鵜呑みにせず実データと照合して誤記 2 件を自ら訂正し、表外の注記まで揃えて 0 往復（1,367,975 トークン）で完了しました4。
  • Sonnet でも差し戻しはゼロではない（タスク 14）: 後半のタスク 14 では、引用照合コードの挙動（欠損識別子の扱い）とルール条文の表現が食い違ったため 1 往復（1,650,174 トークン）の差し戻しが発生しました4。修正規模を含めても 1.65M トークンに収まっていますが、上位モデルでも条文とコードの微細な整合ずれは起こり得ます。

外部知見との構造的一致と、本ログの解釈限界

こうした観測傾向は、Anthropic 公式および外部エンジニアリングブログの知見とも構造的に一致する部分があります。

Anthropic 公式の『Prompting Claude Haiku 5.5』は、low および medium effort において Haiku 5.5 が検証チェックを実行せずにコード変更を完了と報告する場合があることを明記しています13。また Addy Osmani の解説でも、medium effort では API ハンドラとテストだけ直して呼び出し元クライアントの更新を見落としやすい（「求められたことはやったが、2 つ目の呼び出し元を見つけるほど先まで読まなかった」）一方、high effort では編集前に呼び出し箇所まで読みに行って 1 パスで両レイヤーを直し切る傾向があると説明されています1。

Lydia Hallie によるモデル・effort 選定ガイドは、ファイル読み飛ばしやテスト未実行は effort 不足のシグナルであり、十分な文脈を与えて試行しても誤るならモデル引き上げのシグナルであるとした上で、難易度の高い複数ステップ作業では小型モデルが試行回数を消費するため、上位モデルの方がタスク総コストが低くなり得ると述べています9。さらに、対象は異なるものの、MindStudio によるオープンウェイトモデル（Kimi K2 等）とフロンティア Claude 構成の比較でも、短期・局所タスクでは軽量モデルが機能する一方、複数制約を保持する長期作業で「drift（ルール逸脱・制約忘れ）」による差し戻しループが起きる傾向が報告されています14。2026 年 7 月時点の旧世代モデル（Haiku 4.5 対 Sonnet 5）を対象とした Explore Agentic の整理でも、失敗や再試行を含めた Cost-Per-Task 評価と、小型モデルが中盤のターン以降で制約保持や自己修正を落としやすい劣化パターンが分析されています15。

ただし、今回の実測ログの解釈には明確な限界があります。2 群では「haiku/medium 対 sonnet/high」とモデルと effort を同時に変えており、どのタスクで本来運用ガイド更新が必要だったか（分母）や、haiku/medium 群が周辺文書を落とした内部要因（モデル能力の限界か、medium effort の影響か、プロンプト後半の読み落としか）はトランスクリプトから切り分けられません4。前述のとおり本セッションでは haiku/high を試す中間ステップを置いていないため、medium effort 固有の挙動がどの程度影響していたかは未検証であり、本データは「haiku/medium と sonnet/high の各条件下で観測された失敗パターンの傾向」として捉える必要があります。

「調査」と「実装」で評価が分かれる理由と、監視コストへの波及

既刊の サブエージェント3モデルの実測記事 では、狭く閉じた原典抽出や調査タスクにおいて Haiku 5.5 が高い忠実度と低コストを示しました。しかし今回の実装 worker では、複数ファイルや周辺文書との整合維持で差し戻しが多発しました4。

この対比を振り返ると、小型モデル（Haiku 5.5）が機能するかどうかは結局のところ状況次第であり、狭く範囲を切った調査タスクについては司令塔の指示だけで回るように見える一方、複数箇所の整合維持など少し難易度が上がると急に精度が落ちる何らかの臨界点があるようにも感じます（※これは私の体感に基づく仮説であり、定量的な閾値として確証されたものではありません）。

さらに、差し戻し 1 往復が増やすのは worker 単体のトークンだけではありません。司令塔（opus/low）の再レビュー・指示送信コストに加え、結果を確認する人間の待機・監視負荷も膨らみます。この構造は、上流での手抜きが下流の巨大な手戻りと人間の監視負荷（Botsitting）へ跳ね返ることを実測した 監視コストの実測記事 と同じ力学の上にあります（なお今回の 14 件では、司令塔側のトークン消費の群間比較は未計測です4）。

実装 worker のモデル選定基準とログ監査のやり方

ここまでの実測と公式仕様を踏まえ、開発パイプラインでサブエージェントや実装 worker のモデル・effort を使い分け、実ログで監査する具体的な手順を整理します。

作業の型と検収の有無による使い分け基準

テスト環境で単発の成功を確認できても、検収ゲートを持つ実務パイプラインでは差し戻しの有無や作業範囲によって最適なモデルが入れ替わります。タスクが「1 指示で閉じた抽出・変換」か「複数ファイルと周辺文書の整合を保つ実装」かでモデルと effort を切り分けるのが現実的です。

タスクの型特徴・失敗時の戻り方推奨モデル / effort の目安既刊記事との位置づけ
1 指示で閉じた事実抽出・定型チェック対象範囲が狭い。検収が機械的・安価で 100K トークン以下で完結しやすいHaiku 5.5（model: haiku / effort: medium）3モデル比較記事（狭く深い抽出の実測） / 検証系サブエージェント記事（Haiku 4.5 時代の損益試算・設計仮説）
複数ファイル・周辺文書同期を含む実装コード変更と合わせて運用ガイド・要約・テストの整合維持が必要。差し戻しやターン増加で消費が膨らみやすいSonnet 5.5（model: sonnet / effort: high を検討）本記事の一次実測（平均 1.26M・0.20 往復）

Haiku 5.5 は 1 指示で小さく動かすサブエージェント的な使い方に最も費用対効果を発揮する一方5、検収と差し戻しが発生する実装 worker では、リトライ自体を減らせる上位モデル（Sonnet 5.5 等）を選ぶ設計が適しています。

モデル切り替え時の既定値確認と切り分け規律

モデルを切り替える際は、提供者が設定した既定値（モデルごとのデフォルト effort 等）が自分のパイプラインに合うとは限らないため、既定値の確認までを切り替え作業に含めるべきです。実際、Sonnet 5.5 は API 上の既定 effort が high であるのに対し、Claude Code 上の既定は medium です78。

もし小型モデルで失敗が起きたときは、Honeycomb が推奨するようにコンテキスト・モデル・出力制限を一度に変えず、1 回に 1 変数ずつ変更して品質ガードレールと合わせて効果を切り分ける のが安全です3。Lydia Hallie の判断基準に沿って、ファイルの読み飛ばしや検証漏れが原因ならまず effort を引き上げ、十分な文脈を与えても誤るならモデルを引き上げます9。今回の連続実行では比較対象として直接 sonnet/high を選んで既定を切り替えたため effort 単独の効果は未検証のまま残りましたが、自環境で原因を切り分けながら調整する場合は、この 1 変数ずつの手順を踏むのが安全です。なお、サブエージェント側でモデルを指定しても親セッション側の設定（/advisor 等）が子プロセスへ波及する経路もあるため、独立プロセスの呼び出し設定は advisor 設定波及の検証記事 の対策も併せて確認してください。

実装例 1（最小例）: 1 指示で閉じる抽出用サブエージェント定義

1 指示で完結する狭く閉じた事実抽出・要約タスク向けに、model: haiku と effort: medium を明示し、ファイル編集ツールを禁止した最小のカスタムサブエージェント定義を示します。

ファイル: .claude/agents/bounded-extractor.md

---
name: bounded-extractor
description: 1指示で完結する限定範囲の事実抽出・要約タスクを実行する
model: haiku
effort: medium
tools: Read, Glob, Grep
disallowedTools: Edit, Write, Bash
---

指定されたファイルまたは範囲のみを読み込み、事実を抽出して簡潔に要約してください。

- 対象外のファイルへの広域探索や、ファイルの編集・コマンド実行は行わない
- 指定範囲に該当する記述が見当たらない場合は推測で補わず、「該当なし」と明記する
- 根拠となるファイル名・見出し・行番号を併記し、1回の応答で簡潔に返す

公式ドキュメントでサポートされている frontmatter キー（name, description, model, effort, tools, disallowedTools）のみを使い、先頭行から YAML の --- 区切りで記述しています16。書き込みツールを disallowedTools で遮断した上で model: haiku・effort: medium に固定し、未確認事項を推測で埋めない指示を加えています。なお、設定だけで入力長が自動的に 100K 以下に抑えられるわけではないため、1 指示あたりの読み込み対象を小さく絞る呼び出し設計と組み合わせてこそ、100K トークン以下の低単価ティアに収まりやすい短命サブエージェントとして機能します12。稼働中のサブエージェントがどのモデルと effort で動いているかは、実行中に /tasks コマンドで確認できます16。

実装例 2（実践例）: 検収パイプライン向け実装 worker 定義と起動コマンド

複数ファイルの変更や周辺ガイド文書の同期を伴う実装タスク向けに、model: sonnet と effort: high を指定し、完了報告前の実際のチェック実行と関連文書の同期確認をシステムプロンプトに組み込んだ定義と CLI 起動例を示します。

ファイル: .claude/agents/implementer.md

---
name: implementer
description: 複数ファイル変更や周辺文書の整合維持を伴う実装タスクを実行する
model: sonnet
effort: high
tools: Read, Glob, Grep, Edit, Write, Bash
isolation: worktree
---

与えられた実装仕様に基づき、対象コードと関連文書を一貫して更新してください。

1. 変更前に関連箇所・呼び出し元・運用ガイド文書・スキル要約を検索し、同期が必要な参照先を特定する
2. コードと関連文書・コメントの整合を保ったまま編集する
3. 完了を報告する前に、テスト・型チェック・ビルド等の検証コマンドを実際に実行し、終了コードと出力を確認する（未実行のまま完了と報告しない）

ファイルを作成せず 1 回限りの検証用として CLI から直接定義して起動する場合は、--agents フラグに JSON を渡して実行できます16。

claude --agents '{
  "implementer": {
    "description": "複数ファイル変更や周辺文書の整合維持を伴う実装タスクを実行する",
    "prompt": "与えられた実装仕様に基づき、対象コードと関連文書を一貫して更新してください。編集前に呼び出し元や関連ガイド文書を検索し、完了報告前に必ずテスト等の検証コマンドを実走して出力を確認してください。",
    "tools": ["Read", "Glob", "Grep", "Edit", "Write", "Bash"],
    "model": "sonnet",
    "effort": "high",
    "isolation": "worktree"
  }
}'

Claude Code 上では Sonnet 5.5 の既定 effort が medium になるため78、周辺参照の見落としを防ぐ目的で意図的に effort: high を明示しています。また、tools には実装と検証に必要な Read, Glob, Grep, Edit, Write, Bash を許可し、作業の安全性を確保するため一時的な隔離環境で実行する isolation: worktree を指定しました16。完了報告前に実際のチェック実行を指示に明記しているのは、公式プロンプティングガイドが示す「検証なしでの完了報告」を防ぐためです13。

実装例 3（事後監査スクリプト）: .jsonl から実トークンを集計する

今回の計測で得た実務上の重要な教訓は、タスク管理記録に worker のモデル名が残らず、外部オーケストレーターが隔離 worktree 内に置く設定・状態ファイルは片付け時に消える という点でした4。Claude Code のセッショントランスクリプト（.jsonl）自体はローカルに保存されますが（カスタムサブエージェントの場合は ~/.claude/projects/{project}/{sessionId}/subagents/agent-{agentId}.jsonl に格納され、cleanupPeriodDays 既定 30 日で自動削除されます16）、どのタスクで何往復差し戻したかと使用モデル・effort の対応は、片付け前にタスク管理側へ明示的に記録しておかないと後から比較・検証できません4。

また、公式の /usage コマンドでも Usage by model や Prompt cache (main) 統計を確認できますが、公式ドキュメントが明記するとおり Prompt cache (main) 行はメイン会話のみを対象としておりサブエージェント分は含まれません17。独立セッションで動く worker やサブエージェントを評価するには、OpenTelemetry エクスポート17を利用するか、ローカルの .jsonl ファイルから API usage フィールドとターン数を集計する仕組みが必要になります410。

以下のスクリプトは、外部パッケージを追加せず Node.js 標準モジュール（node:fs）のみで、独立 worker の .jsonl またはサブエージェントの subagents/agent-<id>.jsonl から、実際に使用されたモデル名、リクエスト数（ターン数）、API トークン 4 分類、総トークン数、キャッシュ読出比率を集計します。

ファイル: audit-worker-tokens.mjs

import fs from 'node:fs';

const filePath = process.argv[2];
if (!filePath) {
  console.error('Usage: node audit-worker-tokens.mjs <path-to-transcript.jsonl>');
  process.exit(2);
}

const byModel = new Map();
const seenRequests = new Set();

for (const line of fs.readFileSync(filePath, 'utf-8').split('\n')) {
  if (!line.trim()) continue;
  let record;
  try {
    record = JSON.parse(line);
  } catch {
    continue;
  }

  if (record.type !== 'assistant') continue;
  const usage = record.message?.usage;
  if (!usage) continue;

  if (record.requestId) {
    if (seenRequests.has(record.requestId)) continue;
    seenRequests.add(record.requestId);
  }

  const model = record.message?.model ?? 'unknown';
  const counter = byModel.get(model) ?? {
    requests: 0,
    input: 0,
    output: 0,
    cacheWrite: 0,
    cacheRead: 0,
  };

  counter.requests += 1;
  counter.input += usage.input_tokens ?? 0;
  counter.output += usage.output_tokens ?? 0;
  counter.cacheWrite += usage.cache_creation_input_tokens ?? 0;
  counter.cacheRead += usage.cache_read_input_tokens ?? 0;
  byModel.set(model, counter);
}

for (const [model, c] of byModel) {
  const total = c.input + c.output + c.cacheWrite + c.cacheRead;
  const cacheReadRatio = total > 0 ? ((c.cacheRead / total) * 100).toFixed(1) : '0.0';
  console.log(`${model}: total=${total.toLocaleString('en-US')} (req=${c.requests}, cacheRead=${cacheReadRatio}%)`);
  console.log(`  input=${c.input} output=${c.output} cacheWrite=${c.cacheWrite} cacheRead=${c.cacheRead}`);
}

保存したスクリプトに対し、対象の .jsonl ファイルを引数に指定して実行します。

node audit-worker-tokens.mjs "$HOME/.claude/projects/-workspace-app/00000000-0000-0000-0000-000000000000/subagents/agent-a1b2c3d.jsonl"

実装上のポイントは 3 つあります。第 1 に、ローカルの実ログ観測上、同一の requestId がストリーミングや複数ブロック記録により複数行に分かれて出力されることがあるため、seenRequests で重複を除外しないとトークン数とリクエスト数が二重計上されます4。第 2 に、実装例 2 のようにカスタムサブエージェントとして隔離実行した場合は、親セッションの .jsonl ではなく subagents/agent-*.jsonl 側を指定して監査します16。第 3 に、トランスクリプトの assistant 行にはリクエスト別の金額フィールドは記録されないため、金額換算に頼らず「総トークン数と req 数」を一次指標として取り出し、タスク管理側の差し戻し往復数と突き合わせて運用改善に活かします4。

よくある質問（FAQ）

Q. 単価表では Haiku 5.5 の方が大幅に安いのに、なぜ総トークン数に注目して Sonnet に切り替えたのですか？

A. エージェントの実装ループでは毎ターン会話履歴全体を再送信するため、差し戻しやターン数が増えると総消費トークンの大半（今回の 14 件では 88.6%〜97.4%）を占めるキャッシュ読出が膨らみ、単価差以上の総量差が生じ得るためです。当ブログの実測 14 件では、1 件あたり平均トークンが haiku/medium 9 件で 3.69M（平均 0.78 往復）、sonnet/high 5 件で 1.26M（平均 0.20 往復）でした4。さらに Haiku 5.5 はキャッシュを含む全入力の合計が 100K トークンを超えたリクエストで単価が 5 倍に跳ね上がる価格ティアを持つため12、差し戻しでセッションが長引くほど単価面の優位性も縮まります。

Q. 差し戻しを防ぐために指示書（プロンプト）をもっと詳しく書けば、実装 worker でも Haiku で補えますか？

A. 要求の基本的な読み取り精度は高められても、コード変更に付随する周辺文書や他参照箇所の同期漏れまでを指示書だけで完全に防ぐのは難しい場面があります。実際、今回の haiku/medium 9 件で最多の 8,200,207 トークン（2 往復・59 リクエスト）を消費したタスクは詳細な実装仕様書を与えた案件であり、条文に書き切られていない細部やリポジトリ内の運用ガイド文書の更新漏れで差し戻しが発生しました4。検収ゲートを持つ実装タスクでは、プロンプトの補強だけでなくリトライ回数を減らせるモデル・effort 選定を併用する方が安定します。

Q. すべてのサブエージェントや自動化タスクで Haiku 5.5 の利用はやめるべきですか？

A. いいえ、作業の型が「1 指示で小さく完結し、100K トークン以内で収まるタスク」であれば Haiku 5.5 は依然として有効な選択肢です。Anthropic 公式も Haiku 5.5 を要約・分類・狭くスコープされたサブエージェント向けと位置づけており5、当ブログの別の実測でも原典からの狭く深い事実抽出では Haiku 5.5 が高精度かつ低コストでした。一方で、複数ファイル間の整合維持や厳格なルール同期が求められ、検収による差し戻しが発生し得る実装 worker には Sonnet 5.5 などの上位モデルを割り当てる使い分けが合理的です。

まとめ

  • 実装 worker は単価だけでなく「差し戻し込みの総トークンと確認往復（Cost-Per-Task の視点）」で選ぶ: 毎ターン履歴全体を再送するエージェント構造では、差し戻し（平均 0.78 往復）とターン増加が重なった haiku/medium 9 件の平均消費（3.69M）が、sonnet/high 5 件（平均 0.20 往復・1.26M）の約 2.9 倍に達する事例が実際に観測されました4。worker 単体の USD 課金額は未計測であるものの、100K 超ティアでの単価差縮小（キャッシュ読出 2 倍差）12に加え、差し戻しごとに司令塔の再レビューと人の確認負荷が積み上がるため、単価表の倍率どおりのコスト削減は期待できません。
  • 小型モデルの落とし穴は「周辺参照の更新漏れ」に現れやすい: 今回の haiku/medium 差し戻し 6 件のうち 4 件は、主変更はできていながら運用ガイド文書や要約など周辺箇所の同期を落とす型であり、詳細な仕様書を与えても条文外の細部で発生しました4。
  • 同じモデルでも「1 指示の局所抽出」と「検収付きの多箇所実装」で役割を分ける: Haiku 5.5 は 100K トークン以下で完結する単発の抽出・調査サブエージェントに向く一方5、差し戻し時にセッション継続で長引きやすい検収付き実装 worker には Sonnet 5.5 などのリトライを抑えられる構成を充てます。
  • モデル・effort 変更時は既定値を確認し、worktree 消滅前に実測ログを残す: Claude Code のモデルごとの既定 effort やサブエージェント設定を確認した上で7816、トランスクリプトとタスク管理記録からモデル名・往復数・worker_tokens・req 数をタスク単位で突合・記録し、1 変数ずつ実測で検証します34。
