Claude Code の Bash ツールでは見える環境変数が fish 起動の hook に届かない原因と確認手順

「Bash ツールで env を確認したら値が入っているのに、なぜ SessionStart hook は環境変数がないと言って止まるのか」。macOS 上の fish から Claude Code（claude）を起動し、環境変数の定義を ~/.zshenv にだけ置いていた環境で、この食い違いに直面しました。

Claude Code の hook は、親の claude プロセスの環境を引き継いで動きます1。一方、Bash ツールは各コマンドを別プロセスとして zsh か bash で実行するため23、zsh の読み込み経路を通る ~/.zshenv の定義が、Bash ツールの中でだけ見えることがあります4。つまり、hook と Bash ツールは、同じセッションの中でも別の経路で環境を受け取っています。

本記事では、この観測経路の罠によってエージェント自身が「環境には入っている」と誤って報告した一次記録と、親 claude プロセスの系譜 6 段を ps eww で辿った実測結果を示します。環境変数が hook に届いているかを確かめるには、Bash ツールの env ではなく ps eww で親 claude プロセスの環境を確認し、定義は起動シェル側（fish なら ~/.config/fish/config.fish）にも置きます5。さらに、環境変数の不在で黙って skip する処理に気づきやすくするための出力設計も整理します。

起きたこと：hook の skip に 17 時間あまり気づかなかった

セッション開始時に過去の会話を振り返る自作の SessionStart hook（以下、振り返り hook）は、自作の自動化が参照するディレクトリを指す環境変数 COMPANY_HUB を前提に動作し、値がなければ処理を飛ばしてログファイルに 1 行だけ残して終わる設計になっていました6。

2026-10-28T16:59:37+09:00 から 2026-10-29T01:28:23+09:00 の間に、この環境変数不在による skip が計 5 回記録されました6。最初の skip からタスク管理の作業で異変を確認し始める（2026-10-29T10:20:35+09:00）までの約 17 時間 21 分（17 時間 20 分 58 秒）、ログファイル以外には通知が出ないまま処理が止まり続けていました6。

当時の検証環境と条件は次のとおりです（計測日: 2026-10-29）6。

  • OS: macOS
  • 端末シェル: Homebrew 版の fish（fish -l で起動）
  • ログインシェル設定: dscl で確認した UserShell および Bash ツール内で測った $SHELL は /bin/zsh（親 claude プロセス側の $SHELL 値は未計測）
  • 環境変数の定義場所: ~/.zshenv のみに COMPANY_HUB を定義（~/.claude/settings.json、~/.zprofile、~/.zshrc、プロジェクト直下の .envrc には定義なし）

実際に振り返り hook のログファイルへ残っていた記録を確認するため、該当時間帯のログを抜粋します。

前半の 4 回は hook: spawn の直後に子プロセス側が run: skip (COMPANY_HUB が無い。ウォーターマークは進めない) を出力しており、hook 自体は起動したものの COMPANY_HUB がないために本体処理へ進めませんでした6。最後の 1 回（01:28:23）だけ hook: skip へ表記が変わっているのは、対象期間中に hook 側の実装が更新され、子プロセスを起動する前に hook 自身が環境変数の有無をチェックする仕様へ変わったためです6。なお、ログファイルにしか残らず画面には何も出ず停止する構造は、launchd の自動ジョブが起動前に失敗してログに異常が表れなかった事例 と通じる面がありますが、該当事例の起動前失敗に対し、本件は起動後の意図的な skip が無通知で積み上がった点に違いがあります。

なぜ Bash ツールでは「入っている」と見えてしまったのか

原因を調べる途中、エージェントが Bash ツールで echo "env=${COMPANY_HUB:-<unset>}" を実行したところ、COMPANY_HUB のパスが返ってきました6。これを見たエージェントは、いったん「このセッションの環境には COMPANY_HUB が入っており、hook が起動するときの環境にだけ入っていない見込み」と誤って報告しました6。

しかしユーザーがこの仮説で打ち切らず、同じセッション内で原因を掘り下げる指示を出したことで状況が覆ります6。調査を進めると、COMPANY_HUB の定義は ~/.zshenv の 1 箇所だけにあり、~/.claude/settings.json や ~/.zprofile、~/.zshrc などには存在しませんでした6。エージェントの誤認と原因判明の直後、エージェントは次のように報告を訂正しています6。

前回の報告で「このセッションには入っている」と書いたのは誤りでした。Bash ツールが zsh で .zshenv を読み込むので、そこでだけ見えていました。hook は claude 本体の環境を引き継ぐので、こちらは変数無しです

さらに皮肉だったのは、~/.zshenv の定義の直前に置かれていたコメントの文面です6。そこには「.zshrc ではなく .zshenv に置く: エージェントの非インタラクティブシェルにも効かせるため」と記されていました6。つまり、エージェントの非インタラクティブシェルに効かせる意図で選んだ設定場所が、Bash ツールの中でだけ変数を可視化し、観測経路の罠として誤認を生んだことになります。また、同じ調査中に zsh 特有の挙動（「マッチしない glob は zsh で no matches found になる」）を警告する自作の PreToolUse hook が発火していたことも、Bash ツールが zsh として動いていた傍証でした6。

この食い違いが起きる理由は、zsh と Claude Code の Bash ツールの仕様にあります。

  • zsh の起動ファイル読み込み順: zsh は起動時に /etc/zshenv に続いて（RCS オプションが有効な限り）対話シェルかログインシェルかを問わずすべての起動で $ZDOTDIR/.zshenv を読み込みます。一方、.zprofile はログインシェルのみ、.zshrc は対話シェルのみで読まれます4。
  • Bash ツールのシェル選択: Claude Code の環境変数 CLAUDE_CODE_SHELL が未設定のとき、自動検出は $SHELL が bash または zsh を指していればそれを使い、そうでなければ最初に見つかった zsh、次いで bash を選びます。fish などの他シェルはサポート対象外です3。
  • セッション開始時の環境取り込み: Bash ツールは各コマンドを別個のプロセスで実行しつつ、セッション開始時に ~/.zshrc や ~/.bashrc、~/.profile などを読み込んでエイリアス・関数・シェルオプションを取り込み、以後の各 Bash コマンドに適用します2。

本件では UserShell と Bash ツール内で測った $SHELL の双方が /bin/zsh でしたが、Bash ツールがどの分岐で zsh を選んだのか、また COMPANY_HUB が見えたのが毎回の非対話 zsh 起動で ~/.zshenv が読まれたためかセッション開始時の取り込みを経由したためかは、当時のセッションログからは切り分けていません6。しかし、いずれの経路を経由したとしても、Bash ツールは zsh の読み込み経路を通っており、fish から起動された claude 本体とは経路が別である点に変わりはありません。

なお、macOS で fish から Claude Code を起動しても Bash ツールが zsh を使う現象や、親プロセスの $SHELL が fish でも .zshrc の存在などをきっかけに zsh が選ばれる事例は公式リポジトリでも報告されています78。逆に、環境やバージョンによっては Bash ツールの zsh 起動時にも ~/.zshenv の PATH などが反映されない報告もあり9、Bash ツール上で変数が見えるかどうか自体が環境に左右されます。したがって、Bash ツールでの echo や env の出力は、hook に環境変数が届いている根拠にはなりません。

ps eww でプロセス系譜を辿ると、6 段すべてに変数がなかった

Bash ツールの出力に頼らず実態を確かめるため、起動中の全 claude プロセスと、調査を行っていたセッションの親プロセス系譜を ps eww で直接実測しました6。

まず、起動中の claude プロセス群に COMPANY_HUB が渡っているか、また ~/.config/fish 配下に定義があるかを調べたコマンドと結果です。

この系譜のどこにも、~/.zshenv を読み込む zsh は現れません。fish が起動時に読み込む設定ファイルは ~/.config/fish/config.fish などであり、そこに定義がない状態では claude 本体にも、本体の環境を引き継ぐ hook にも環境変数は届きません156。

ここで確認に ps eww を使ったのには、macOS（BSD 系）の ps の仕様上の理由があります。ps の -E（旧来書式の e）オプションは「プロセスの環境も併せて表示するが、プロセス起動後の環境変更は反映しない（Display the environment as well. This does not reflect changes in the environment after process launch.）」と定義されており、ww は端末幅で切り詰めずに全幅を出力する指定です10。先頭にハイフンを付けない eww は kludge_oldps_options によって旧来の書式として解釈され、e が環境表示として機能します（ハイフンを付けた -e は全プロセス表示を意味する別オプションになります）11。起動時の環境をそのまま表示する性質を持つため、子プロセスである hook に受け継がれる環境を確かめる道具に適しています。

hook・Claude Code 本体・Bash ツールはどこから環境を受け取るか

ここまでの仕様と実測を踏まえると、~/.zshenv の定義が効くのは Bash ツールだけであり、claude 本体と hook には届きません。3 者の環境変数の受け取り方を対比すると次のようになります。

対象環境の出どころ起動するシェル~/.zshenv の定義が効くか（本件）
Claude Code 本体（claude）起動した端末シェル（本件は fish）から受け継ぐなし効かない（ps eww で 6 段すべてなし）

このように、起動シェルから受け継いだ変数の到達確認は、hook の直接の出どころである親 claude プロセスの環境で行います。なお、ログインシェルの設定ファイルを経由しない起動経路で環境変数が欠落する構造自体は、launchd の環境で PATH が届かなかったケースの検証 と同型です。

到達確認と対策のやり方：ps eww と config.fish への設定

原因が切り分けられたところで、正しい確認手順と起動シェル側の対策、および他の設定手段との位置づけを整理します。

親 claude プロセスの環境を確かめる

先ほど実測に使った 2 本のコマンドで、親プロセスの環境を確かめられます。まず pgrep -x claude で対象となる claude プロセスの PID を調べ、系譜を辿るワンライナーの p=8688 を自分の PID に、COMPANY_HUB を確かめたい環境変数名に置き換えて実行します。

このコマンドは、Bash ツールの中から実行しても構いません。Bash ツール内のシェルが zsh であっても、ps eww -p <PID> が参照するのは指定した PID のプロセスが起動時に受け取っていた環境であり、コマンドを実行した Bash ツール自身の環境ではないためです10。

fish なら config.fish に set -gx で定義する

fish から起動した claude 本体と hook に環境変数を渡すには、fish が起動時に読み込むユーザー設定ファイル ~/.config/fish/config.fish へ変数を追加します5。set コマンドの -g（--global）はグローバルスコープ、-x（--export）は子プロセスへ環境変数としてエクスポートする指定です12。

目的: fish 起動のセッションから claude 本体および sh -c で起動される hook へ環境変数を引き継ぐため、~/.config/fish/config.fish にグローバルかつエクスポート付きで定義を追加します。

# zsh 側（~/.zshenv）と同じ値を、fish から起動するプロセスにも export する
set -gx COMPANY_HUB $HOME/path/to/hub

上記の記述を実際の対象パスで ~/.config/fish/config.fish に追記したうえで、新しく起動した fish -l で値が展開されて該当ディレクトリが実在すること（isdir）、およびその配下で動かした sh -c 子プロセスでも値が見えることを実測で確認しました6。

ただし、すでに起動している端末や claude セッションには反映されません。ps eww が起動後の環境変更を反映しないのと同じプロセス環境の仕組みによるもので10、反映を確かめるには端末と claude を起動し直したうえで再確認します。実際、修正後には正常完了した実行ログが記録される一方、約 1 週間後のログにも同じ理由の skip が 1 行だけ記録されていました（どの経路から起動されたセッションかは特定できていませんが、修正前から開いていた端末や別の起動経路が残っていれば、そこから起動したセッションには届かない可能性があります）6。

なお、zsh と fish の両方から読み込める共通の設定ファイルを用意する方法もありますが、シェルを一度乗り換えると特別な理由がない限り元に戻さないため、本件では設定を共通化せず config.fish に同じ定義を追記する運用を選びました。

ほかの選択肢との位置づけ

Claude Code で環境変数を扱う手段には、起動シェル以外に settings.json の env キーや CLAUDE_CODE_SHELL があります。hook に変数を届けたいなら起動シェル側か settings.json の env を使い、CLAUDE_CODE_SHELL は Bash ツールのシェルを切り替える設定であって hook には効きません。

settings.json の env は使用するシェルを問わずに適用される一方で、Claude Code の外側で動かすツールやスクリプトには届きません。どちらを採るかは、その環境変数を Claude Code 以外でも使うかどうかで選び分けるのが実用的です。

なお、settings.json の env を選んだ場合は注意点があります。Claude Code は settings.json の env をプロセスの起動時および実行中の設定変更時に自ら適用するため13、OS から受け取った起動時の環境だけを表示する ps eww には現れないと読めます10。したがって、settings.json の env を使う構成では ps eww による到達確認は使えません。また、類似の変数として CLAUDE_ENV_FILE がありますが、こちらは SessionStart などの hook から後続の Bash コマンドへ変数を渡す仕組みであり1、親環境から SessionStart hook へ渡す本件とは向きが逆になります。

黙って skip する hook に気づくには

今回のケースで発見まで約 17 時間 21 分かかった直接の要因は、振り返り hook が環境変数不在のときにログファイルへ 1 行書き出すだけで終了していたことにあります6。

Claude Code の仕様上、hook が exit code 0 で何も出力せずに終了すると、セッション画面上には何も表示されません。一方、SessionStart hook は exit code 2 を返してもセッションの開始自体はブロックせず（Can block? が No）、stderr の内容を <hook name> hook error の通知としてトランスクリプト上へユーザー向けに表示します1。逆に exit code 0 のまま stderr へ出力しても、その内容はデバッグログにしか書かれずトランスクリプトには現れません1。動作の詳細を追うには Ctrl+O でトランスクリプトを展開するか、claude --debug（セッション中なら /debug、出力先指定なら --debug-file）でデバッグログを確認する手順が案内されています14。

前提となる環境変数が欠けて処理を飛ばす場合は、サイレントスキップにせず stderr に理由を 1 行出力して exit code 2 で終了する ようにすると、セッション開始を止めないまま画面上で異変に気づきやすくなります（ただし、それによって何時間早く気づけたかといった短縮効果は計測していません）。

よくある質問（FAQ）

Q. Claude Code の Bash ツールでは環境変数が見えるのに、SessionStart hook には渡らないのはなぜですか？

A. hook は親の claude プロセスの環境を引き継ぎ、Bash ツールはコマンドごとに zsh か bash を起動するからです123。Bash ツールは zsh の読み込み経路を通るため ~/.zshenv の定義が見えることがありますが4、fish など別のシェルから claude を起動していると、本体と hook には届きません5。

Q. fish から起動した Claude Code 本体（親の claude プロセス）に環境変数が渡っているか確かめる方法は？

A. pgrep -x claude で PID を調べ、ps eww -o command= -p <PID> の出力に該当の変数名が含まれるかを見ます。ps eww は各プロセスが起動したときの環境を表示するため、起動シェルから受け継いだ変数が hook の出どころである claude 本体まで届いているかを確かめられます10（settings.json の env で渡した変数は表示されません）。

Q. .zshenv に書いた環境変数を fish から起動したツールにも渡すには？

A. ~/.config/fish/config.fish に set -gx 変数名 値 で同じ定義を追加します512。fish が起動時に読み込む設定ファイルは config.fish などであり、~/.zshenv は読まれないためです。Claude Code の中だけで使う変数であれば、~/.claude/settings.json の env に書く方法もあります13。

まとめ

  • Claude Code の hook は親の claude プロセスの環境を引き継ぎます1。fish から起動した claude には ~/.zshenv の定義は届きません5。
  • Bash ツールは zsh か bash で動くため、~/.zshenv の定義が見えることがあります34。Bash ツールで値が見えても、hook に届いている証拠にはなりません。
  • 起動シェルから渡す変数の到達確認は、ps eww で親 claude プロセスの起動時の環境を見ます10。系譜を上へ辿れば、どの段で変数が欠落しているかも特定できます6。
  • 環境変数は、claude を起動するシェルの設定（fish なら ~/.config/fish/config.fish の set -gx）に置きます512。すでに起動しているセッションには反映されないため、端末と claude を起動し直して確かめます10。
  • 前提が欠けて skip する SessionStart hook は、stderr に 1 行出して exit code 2 で終えるとトランスクリプトに通知を出せます1。exit code 0 のままでは画面に出ず、本件ではログにしか残らず約 17 時間 21 分気づけませんでした6。
