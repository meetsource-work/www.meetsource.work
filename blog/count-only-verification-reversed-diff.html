件数チェックと実文字列照合の違い：git diff の向きが7件中6件逆のまま7工程を通過した記録と両側照合のやり方

計測ログや git diff の出力を根拠に技術記事や障害報告書を書く際、対象ファイル数や変更行数を検証コマンドで確かめ、「再現できた」と判断して先へ進める運用は珍しくありません。しかし、Martin Fowler が Assertion Free Testing の議論で指摘しているとおり、すべてのテストが通過して緑のバーや 100% のコードカバレッジが揃っていても、アサーションが欠けていればカバレッジなどの数値の解釈には注意が必要です1。同じように、差分の集計値が一致することと、変更前後の向きや内容が一致することはまったく別の検査です。

件数検算（件数チェック） とは、対象ファイル数・変更行数・hunk（変更箇所の塊）数などの集計値の一致を確かめる検査です。これに対し 両側の実文字列照合 とは、git diff の unified diff 形式や変更前後比較表において、削除・変更前を表す - 側と追加・変更後を表す + 側それぞれの具体的な文字列と対応関係を一次資料と突き合わせる検査を指します。

私が運用する当ブログの執筆パイプライン（非公開）では、まさにこの切り分けが抜けていたことで大きな手戻りが発生しました。件数一致だけを確かめる検証コマンドが全件合格して一次記録に「検証済み」のラベルが付いた結果、diff の「変更前（- 側）／変更後（+ 側）」が 7 件中 6 件で逆転した記録が後続の 7 工程（事前調査・企画・調査・設計・設計検証・執筆・挿絵）をすべて通過したのです。最終的に、最終校閲での差し戻しを経て企画の結論（看板）からやり直す事態になりました。

本記事では、この実測記録と再検算で組み直した検証手順をもとに、件数検算がなぜ向きの逆転を通過させたのかを解剖し、向きや対応関係のある記録で左右の取り違えを防ぐ両側照合コマンドの設計とトレードオフを整理します。

「2ファイル・7行・6 hunk」の件数検算が向きの逆転を通した背景

件数の集計値が完全に一致していても、変更前と変更後の向きが逆になったまま後続工程を通過してしまう構造は、1 回目の検証コマンドが見ていた範囲と、パイプライン各工程の参照関係を追うと見えてきます。

7件中6件が逆転した3段の差分と、件数のみの検算が見ていた範囲

発端は、プロンプトを否定形から肯定形へ書き換えたときの適用範囲ドリフトを扱った 先行記事 の一次計測ログ（hands-on-log.md）でした。この記録では、私が運用する別リポジトリ（非公開、以下リポジトリA）で実施されたセルフレビューの修正差分（2 ファイル・置換された行数 7・diff hunk 数 6）を根拠にしていました。

リポジトリAの改訂作業は、「元の文面（否定形） → 肯定形への書き換え → セルフレビュー後の修正」という 3 段で構成されていました。Git のパッチ出力では、通常、変更前の行が -、変更後の行が +、未変更のコンテキスト行が空白で表されます2。unified diff の仕様上も、2 つのファイル A と B を比較するとき、- は「A に現れ B で削除された行」、+ は「A には無く B で追加された行」を示します3。したがって、セルフレビューのコミット差分では - 側が「肯定形化後の文面」、+ 側が「セルフレビュー後の文面」でした。

ところが、一次記録の 1 回目の検証コマンドは「対象ファイル数が 2」「削除・置換された行数が 7」「hunk 数が 6」という件数の一致しか見ていませんでした。集計値そのものは実際のコミットと完全に一致していたため、検算は全件合格となり、一次計測ログには status: 検証済み が付きました。

実際には、全 7 件のうち向きが正しかったのは 1 件だけで、残る 6 件（7 件中 6 件）で「変更前（- 側、肯定形化後）」と「変更後（+ 側、セルフレビュー後）」が逆に記録されていました。以下は、リポジトリAの実際の改訂差分から抜き出した 4 行です。

コードの目的: 7 件中 6 件の向き逆転が起きた対象差分から、- 側（肯定形化側）と + 側（セルフレビュー後）の実際の文面対照を示します。

引用元: リポジトリA（筆者が運用する非公開リポジトリ）の改訂差分

-    *   **検証用のテストは、標準ライブラリだけの純粋な Go（`go test`）で書く。** 時計・乱数の種・実行順は注入して固定し、テスト自体を毎回同じ結果にする
+    *   **検証用のテストは、`go test` だけで動く純粋な Go で書く**（delve・rr 等の道具が無くても通る）。 時計・乱数の種・実行順は注入して固定し、テスト自体を毎回同じ結果にする
-    *   第4幕の終わり方（「再現テストを書いて終わる」形は、回ごとに別の終わり方と入れ替える）
+    *   第4幕の終わり方（「再現テストを書いて終わる」は使う回を選び、ほかの回は別の終わり方にする）

重要箇所の解説: - 側に「標準ライブラリだけの純粋な Go」「回ごとに別の終わり方と入れ替える」があり、+ 側に「go test だけで動く純粋な Go」「使う回を選び、ほかの回は別の終わり方にする」が並んでいます。差し戻し前の記録はこの - と + を逆に取り違え、「セルフレビューで『だけの』が脱落した」「義務が任意化した」と正反対に記述していました。

最終校閲時の照合表で確認された代表 4 項目を「元の文面 → 肯定形化後（- 側） → セルフレビュー後（+ 側）」の 3 段で並べると、取り違えによる意味の反転がより明確になります。

なぜ 1 回目の検証コマンドがこのような逆転を素通りさせたのかは、件数一致のみを検査する最小スクリプトの構造を見るとはっきりします。

コードの目的: ファイル数・置換行数・hunk 数の一致だけを確かめる検算パターンが、- と + を取り違えた記録に対しても合格（終了コード 0）になる構造を再現します。

ファイル: verify-count-only.sh

#!/usr/bin/env bash
set -euo pipefail

COMMIT="${1:-HEAD}"
EXPECTED_FILES=2
EXPECTED_MINUS=7
EXPECTED_HUNKS=6

patch="$(git show --format= --patch "$COMMIT")"
body="$(printf '%s\n' "$patch" | grep -vE '^(---|\+\+\+) ' || true)"

actual_files="$(printf '%s\n' "$patch" | grep -c '^diff --git ' || true)"
actual_minus="$(printf '%s\n' "$body" | grep -c '^-' || true)"
actual_hunks="$(printf '%s\n' "$body" | grep -c '^@@' || true)"

if [[ "$actual_files" -ne "$EXPECTED_FILES" || "$actual_minus" -ne "$EXPECTED_MINUS" || "$actual_hunks" -ne "$EXPECTED_HUNKS" ]]; then
  echo "NG: files=${actual_files}/${EXPECTED_FILES}, minus=${actual_minus}/${EXPECTED_MINUS}, hunks=${actual_hunks}/${EXPECTED_HUNKS}" >&2
  exit 1
fi

echo "OK: files=${actual_files}, minus=${actual_minus}, hunks=${actual_hunks}"

実行コマンド:

bash verify-count-only.sh HEAD

重要箇所の解説: git show --format= --patch でコミットメッセージを除いたパッチ本体を取り出し4、grep -vE '^(---|\+\+\+) ' でファイルヘッダを落とした上で、^diff --git ・^-・^@@ の各行数を期待値と比較しています。ここでは 1 行置換を前提に ^- の行数を置換行数として数えており、純粋な追加や削除が混ざる差分では + 行数（^\+）も併せて比較する必要があります。また、grep -c は一致が 0 件のとき終了コード 1 を返すため、set -euo pipefail 下で途中終了しないよう || true を付けています。この構造では、対象コミットのファイル数・- 行数・hunk 数さえ一致すれば常に合格となるため、記録上で - 側と + 側が丸ごと入れ替わっていても原理的に検出できません。

設計検証でも「高」が出ながら、7工程を通って看板改訂まで戻った経緯

誤った一次記録に status: 検証済み が付いたあと、企画は後続の 7 工程（事前調査 → 企画 → 調査 → 設計 → 設計検証 → 執筆 → 挿絵）をすべて通過し、最終校閲まで到達しました。

注目すべき点は、設計検証が一次記録（hands-on-log.md）を正本として設計書との整合性を確かめる工程であるにもかかわらず、誤りが下流へ流れたことです。途中の設計検証（1 周目）では同じ節に対して重要度「高」の指摘が出され、設計書の該当箇所を修正して「その場で解消」と記録されていました。しかし正本である hands-on-log.md 自体が「検証済み」の印付きで逆向きの記録を持っていたため、設計書を一次記録に合わせ直しても誤りは解消されず、そのまま執筆と挿絵へ進みました。

さらに影響が大きかったのは、誤った向きが記事全体の結論（看板）に組み込まれていた点です。差し戻し前のドラフトは、「上限・排他（〜だけ）は否定形で残せ」という結論を掲げ、第 2 章の解説から第 3 章の比較表・FAQ・まとめまでを一貫して構成していました。しかし実際の向きでは「〜だけ」は肯定形化の側でも入っており、最終校閲の読者レビューが「-/+ の向きが本文の説明と照合できない」と重要度「高」を出し、一次記録との照合を経て記事が差し戻された時点で、局所修正だけでは閉じなくなりました。

結果として、一次計測ログ（hands-on-log.md）の向き訂正 → 企画書（plan.md）の看板改訂 → 調査改訂 → 設計・設計検証（2 周目）→ 執筆 → 挿絵という工程をやり直し、差し戻しと同日（2026年11月10日）に公開まで至りました。なお、この追加 1 周にかかった時間やトークン数は振り返りの記録で「記録なし」とされており、定量的な追加コストの算出は行えません。また、この 1 事例だけでは、別の作業者や別工程での発見率や、一次記録の訂正と看板改訂のどちらが後続の修正量に効いたかまでは切り分けられません。

この経過は、検査設計における 2 つの教訓を示しています。1 つは、予防は無限に起こり得る原因の空間に対して組むため漏れが生じやすいのに対し、出力側の検査は守りたい結果の性質の数だけ条件を書けば閉じられるという点です。もう 1 つは、検査が合格（緑）であることをそのまま仕様遵守の証拠とみなさず、検査自体が弱い条件しか見ていない可能性を疑う姿勢が必要だという点です。今回の件数検算は「規模の一致」という 1 つの性質しか見ておらず、「向きの正しさ」という守りたい性質を事後の検査条件に入れていませんでした。

なお、当ブログではこれまでにも、一次計測ログを検証する工程自体がパイプラインに存在しなかった構造的盲点を扱った 生データ検証の盲点に関する記事 や、人手の集計表で矢印数を 2 セル数え間違えた経験から静的検査スクリプトへ移行した Mermaid 要素数上限の記事 を公開しています。さらに、文章レビューと一次ソース再集計の違いを扱った 検算の役割に関する記事 や、本件と同じ元事象の言い換え手順側を扱った 肯定形書き換えのドリフト記事 もあります。本事例はこれらと異なり、自動検算コマンドを実行して「検証済み」まで付いていたにもかかわらず、検算コマンド自体の検査軸から向きが抜けていたという別の死角を示しています。

git diff の追加行（+）と削除行（-）の向きをコマンドで自動検証するやり方

2026年11月10日の再検算では、向きを見るコマンドを追加して検証コマンド一式を全件実走し、代表項目（肯定形化側 - 3 件、セルフレビュー後 + 3 件、元の文面 4 件）それぞれの実文字列を grep -E で照合して、7 件の記録を 3 段の比較へ訂正しました。

テストフレームワークの世界でも、総数や長さだけを見る検査と中身・順序まで見る検査は明確に区別されています。Python の unittest では、順序を無視して各要素の出現回数の一致を確かめる assertCountEqual と、順序の対応を含めてシーケンスの一致を確かめる assertSequenceEqual が別メソッドとして用意されています5。Jest でも同様に、オブジェクトの .length プロパティが指定数値に等しいかを確認する .toHaveLength と、全プロパティや要素を再帰的に比較する .toEqual が分けられています6。さらに XUnit Patterns では、実行後の状態を期待値と比べる State Verification に対し、実行前後の状態差分に基づいてアサーションを書くパターンを Delta Assertion として区別しています7。

当ブログの 行単位照合スクリプトの設計記事 では、本文中のコード抜粋が一次資料に実在するかどうかだけを調べるため、一次資料側の +/- 接頭辞を 1 段外して照合する設計を採りました。これとは逆に、向きの取り違えを防ぐ検算では接頭辞 - と + を剥がさずに保持したまま、- 行集合と + 行集合を左右別々に照合する のが設計の核になります。

集計値（合計数）だけを確かめても要素間の入れ替わりはすり抜けるため、確認したい要素ごとの検査を切り出す必要があります。さらに、バグ修正後などに後から検算コマンドを追加する場合は最初から合格しやすいため、わざと左右の期待文字列を入れ替えたときに失敗（赤）になるかを確かめる逆検証を入れておくと、弱い条件しか見ていない見落としを防げます。

以下は、先ほどの引用例を題材に、件数確認に加えて - 側と + 側の代表文字列、および逆側への非混入を一括で確かめる最小の実装例です。実務で使う際は、一次記録（hands-on-log.md 等）や記事の比較表に書き起こした「変更前」と「変更後」の表現そのものを、それぞれ OLD_PATTERNS と NEW_PATTERNS に転記して実行します。こうすることで、記録上の向きと一次資料の -／+ 行の向きが食い違った瞬間にコマンドが失敗し、逆転を下流へ流す前に止められます。

コードの目的: ファイル数・置換行数・hunk 数の集計値一致に加え、- 側に旧表現があり + 側に旧表現が混入していないこと、かつ + 側に新表現があり - 側に新表現が混入していないことを検証するスクリプトを示します。冒頭の変数と配列を差し替えれば他リポジトリでも流用できます。

ファイル: verify-diff-direction.sh

#!/usr/bin/env bash
set -euo pipefail

COMMIT="${1:-HEAD}"
EXPECTED_FILES=2
EXPECTED_MINUS=7
EXPECTED_HUNKS=6
# 純粋な追加や削除が混ざる場合は EXPECTED_PLUS も定義し、^\+ 行数と併せて比較する

# 変更前（- 側）に存在するはずの代表表現
OLD_PATTERNS=(
  '標準ライブラリだけの純粋な Go'
  '回ごとに別の終わり方と入れ替える'
)

# 変更後（+ 側）に存在するはずの代表表現
# バッククォートを含むパターンはコマンド置換を防ぐため必ずシングルクォートで定義する
NEW_PATTERNS=(
  '`go test` だけで動く'
  '使う回を選び'
)

patch="$(git show --format= --patch "$COMMIT")"
body="$(printf '%s\n' "$patch" | grep -vE '^(---|\+\+\+) ' || true)"

actual_files="$(printf '%s\n' "$patch" | grep -c '^diff --git ' || true)"
actual_minus="$(printf '%s\n' "$body" | grep -c '^-' || true)"
actual_hunks="$(printf '%s\n' "$body" | grep -c '^@@' || true)"

if [[ "$actual_files" -ne "$EXPECTED_FILES" || "$actual_minus" -ne "$EXPECTED_MINUS" || "$actual_hunks" -ne "$EXPECTED_HUNKS" ]]; then
  echo "NG (count): files=${actual_files}/${EXPECTED_FILES}, minus=${actual_minus}/${EXPECTED_MINUS}, hunks=${actual_hunks}/${EXPECTED_HUNKS}" >&2
  exit 1
fi

minus_lines="$(printf '%s\n' "$body" | grep '^-' || true)"
plus_lines="$(printf '%s\n' "$body" | grep '^\+' || true)"

for pat in "${OLD_PATTERNS[@]}"; do
  if ! printf '%s\n' "$minus_lines" | grep -E -- "$pat" >/dev/null; then
    echo "NG (direction): '-' 側に旧表現が見つかりません: $pat" >&2
    exit 1
  fi
  if printf '%s\n' "$plus_lines" | grep -E -- "$pat" >/dev/null; then
    echo "NG (direction): '+' 側に旧表現が混入しています: $pat" >&2
    exit 1
  fi
done

for pat in "${NEW_PATTERNS[@]}"; do
  if ! printf '%s\n' "$plus_lines" | grep -E -- "$pat" >/dev/null; then
    echo "NG (direction): '+' 側に新表現が見つかりません: $pat" >&2
    exit 1
  fi
  if printf '%s\n' "$minus_lines" | grep -E -- "$pat" >/dev/null; then
    echo "NG (direction): '-' 側に新表現が混入しています: $pat" >&2
    exit 1
  fi
done

echo "OK: files=${actual_files}, minus=${actual_minus}, hunks=${actual_hunks} (direction verified)"

実行コマンド:

chmod +x verify-diff-direction.sh && ./verify-diff-direction.sh HEAD

特定の過去コミットを対象にする場合は、引数にコミット指定を渡します。

bash verify-diff-direction.sh <commit>

重要箇所の解説: まず git show --format= --patch でコミットメッセージ本文を除外し4、メッセージ内の箇条書き - による誤検出を防ぎます。続いて grep -vE '^(---|\+\+\+) ' でファイルヘッダを除いた上で、^- と ^\+ に分離して検査します。特に `go test` だけで動く のようにバッククォートを含む文字列は、ダブルクォートで囲むとシェルがコマンド置換として解釈してしまうため、配列定義でも grep -E '...' を直接書く場合でも必ずシングルクォートで囲みます。また、括弧 ( ) や * など正規表現のメタ文字を含む文字列をそのまま照合したい場合は、grep -E の代わりに固定文字列検索の grep -F を使うとエスケープ漏れによる誤判定を防げます。今回のように「元の文面 → 肯定形化 → セルフレビュー後」という 3 段に跨る変更を検算する場合は、それぞれの段に対応するコミットに対しても同様に - 側と + 側の代表文字列を当てます。

全行を照合すべきか、代表文字列に絞るか：トレードオフと適用限界

差分記録をコマンドで検算する設計には主に 3 つの方式があり、誤りの検出力と保守コストのバランスは「何を照合対象にするか」で決まります。

検算パターン検証対象検出できる誤り見逃す誤り記述・保守コスト
件数のみの検算ファイル数・変更行数・hunk 数対象ファイル漏れ・行数の増減ミス- と + の向き逆転・記述内容の取り違え低い（数値比較のみ）
接頭辞除去または片側のみの確認-/+ を剥がした行、または片側だけの語句記録した文字列が差分内に全く存在しない誤り- 側と + 側の左右入れ替わり・役割の逆転中（片側の語句指定）
件数＋両側（-/+）の実文字列照合集計値＋ - 側・+ 側の代表文字列件数ズレと選定した代表項目の向き逆転代表文字列外の取り違え・同コミット内の別 hunk 間移動・左右同一文字列・combined diff・文脈妥当性中〜高（左右の代表文字列選定が必要）

向きの逆転を防ぎつつ過剰な保守コストを避けるには、「件数＋両側（-/+）の代表文字列照合」を採り、照合する文字列を結論に直結する代表例へ絞るのが実務上の有効な均衡点になります。

ここで、「変更された全行を検証コマンドに書くと冗長で壊れやすくならないか」という反論が考えられます。Google Testing Blog でも指摘されているとおり、複雑な対象全体を丸ごと比較する広いアサーション（broad assertions）は、無関係な変更でも失敗して頻繁な修正を強いられる脆いテスト（brittle tests）を生みやすいため、テストしたい振る舞いに関係する部分だけを確認する狭いアサーション（narrow assertions）が推奨されています8。同記事では、検証対象を必要な部分集合に絞る手段として、Java の .comparingExpectedFieldsOnly() や Go（protocmp）の protocmp.FilterField が挙げられています8。

diff の検算も同様で、変更行すべてを固定文字列として列挙する必要はありません。「左右が入れ替われば記事や報告書の結論・主張が成立しなくなる代表文字列」を - 側・+ 側から 1〜数件ずつ選んで照合すれば、無関係な周辺表現の微調整による脆さを避けつつ、選定した代表項目について向きの逆転を検知できます。なお、同一行の一部だけが書き換わる箇所では、変更前後で共通する語句を含めると反対側の非混入検査が失敗するため、差異が表れる固有のフレーズ（たとえば「標準ライブラリだけ」と「go test だけで動く」）を代表文字列に選びます。

一方で、この手法には以下の適用限界と一次情報上の留保があります。

  • 1 事例からの過度な一般化はできない: 本実測 1 件のみから「件数検算一般が無効である」「件数検算が誤りを引き起こした」とまでは言えません。件数一致は対象漏れや行数ズレを素早く弾く一次検査として有用であり、向き照合と組み合わせて使うものです。
  • マージコミットの combined diff 形式にはそのまま使えない: マージコミットに対する git show は単一列の -/+ ではなく、複数の親コミットに対する複数列の combined diff（@@@ チャンクヘッダや ++・-- 列など）を出力します34。単純な ^- / ^\+ 照合をマージコミットへ当てると意図どおりに動かないため、比較対象を通常コミットに絞るか、2 点間を比較する git diff コマンドで単一列の差分を取得する必要があります。
  • 代表外の変更行・同コミット内の移動・部分一致は拾い切れない: 全行照合ではなく代表文字列に絞る以上、選ばなかった変更行の取り違えは検出できません。また、同じコミット内の別 hunk 間で文言が移動した場合は旧表現が + 側にも現れるため、反対側の非存在確認が偽陽性を起こし得ます。識別力の弱い短い部分文字列を指定した場合も、左右の対応関係が崩れた別箇所の一致までは切り分けられません。
  • 意味的妥当性までは判定できない: - 側と + 側の文字列が仕様どおりに実在していても、それを根拠に執筆者が組み立てた因果推論や解釈が妥当かどうかまでは、文字列照合コマンドでは判定できません。

前提が変われば結論はどう変わるか

将来的に、差分の記録を git diff のテキストから正規表現で読み解くのではなく、変更前・変更後の構造を before / after といった明示的なキーを持つ構造化データ（AST 差分やスキーマ付き JSON 等）として自動生成し、そのまま比較表や検証テストへ流し込めるツールチェーンが整えば、シェルスクリプトで ^- や ^\+ を手書きで照合する工程の比重は下がります。

ただし、ツールがテキスト差分から構造化データや AI エージェントによる自動抽出に置き換わったとしても、「件数・総数といった集計値の一致」と「変更前後の対応関係（写像の向き）の一致」が別の検査軸であるという設計原則自体は変わりません。どれほど高度な仕組みを使っても、集計値が一致しただけで中身と向きまで合っているとみなす検算設計を採る限り、同じ盲点が残り続けます。

よくある質問（FAQ）

Q. git diff のファイル数・行数・hunk 数が一致していれば、差分に基づく記録は正しいと言えますか？

A. いいえ、件数の一致だけでは差分に基づく記録の正しさは保証されません。ファイル数や変更行数、hunk 数は差分の規模が一致していることしか示さないため、変更前（- 側）と変更後（+ 側）を取り違えて記録していても件数は一致し、検算は通過してしまいます。向きや対応関係を根拠にする記録では、件数確認に加えて両側の実文字列を照合する必要があります。

Q. diff や変更前後比較表の検算コマンドで、向きの取り違えを防ぐには何を確認すればよいですか？

A. コミットメッセージやファイルヘッダ（--- / +++）を除いたパッチ本文に対して、変更前を示す ^- 行に旧表現があることと、変更後を示す ^\+ 行に新表現があることを左右別々に照合します。さらに旧表現が + 側に、新表現が - 側に混入していないことも併せて確認すると、選定した代表項目における左右の入れ替わりを防げます。変更前後比較表の記述を検算する場合も、表の「変更前」「変更後」それぞれの列に書いた表現を一次資料の ^- 行集合と ^\+ 行集合へ対応づけて照合します。

Q. 変更された全行を検証コマンドに含めると保守が重くなりませんか？

A. 全行を含める必要はありません。広いアサーションは周辺の軽微な編集でも壊れやすくなるため、結論や主張を左右する「左右が入れ替われば前提が崩れる代表文字列」だけを - 側と + 側から 1〜数件ずつ選んで照合します。これにより、保守コストを抑えつつ向きの逆転を防げます。

まとめ

  • 件数一致と向き一致は別の検査である: ファイル数・行数・hunk 数の集計値が一致しても、差分の向き（変更前と変更後の対応関係）が正しいことは保証されません。
  • 「検証済み」の誤った一次記録は下流の検証も素通りし得る: 一次記録自体に検証済みの印が付いて逆向きのまま残ると、設計検証を含む後続工程も誤った正本を参照するため、最終校閲での差し戻しや企画の看板からのやり直しにつながります。
  • 件数に加えて - 側と + 側の実文字列を別々に照合する: 向きや対応関係を持つ記録を検算する際は、集計値だけでなく、行頭記号 - と + を保持したまま両側の具体的な文字列を独立して照合するコマンドを組みます。
  • 全行ではなく結論を左右する代表文字列に絞る: 変更行すべてを列挙するのではなく、左右が入れ替われば主張が成立しなくなる代表的な文字列を両側で 1〜数件ずつ照合することで、保守負荷を抑えつつ向きの逆転を防げます。
