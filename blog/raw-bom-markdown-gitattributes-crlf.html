BOM（U+FEFF）とテストデータの CRLF 保護 ── .gitattributes の -text 指定と行番号付き公開前機械検査

UTF-8 の BOM（Byte Order Mark）や改行コードの CRLF が原因で起きる不具合を再現するテストデータと解説記事を、私が個人で運営している技術ブログ用リポジトリ（非公開、以下「リポジトリA」）において AI コーディングエージェントおよび執筆サブエージェントに作成させていたとき、二重の不可視文字トラブルに直面しました1。再現用の CSV テストデータに入れたはずの CRLF が git add 時に環境設定 core.autocrlf=input（チェックイン時に CRLF を LF へ変換し、チェックアウト時は出力変換しない設定）によって LF へ書き換わり12、一方で解説記事の Markdown 本文には、エスケープ表記を書くはずのインラインコードに本物の生 U+FEFF が 1 文字混入していたのです1。

UTF-8 の BOM（Byte Order Mark、U+FEFF、UTF-8 バイト列 0xEF 0xBB 0xBF）や改行コードの CRLF（\r\n）とは、文字コードの識別や行末の制御のためにファイルへ埋め込まれ、テキスト上の視認が難しく通常のエディタ表示では見落とされやすい不可視のバイト列です34。

当初のコミットメッセージには「生の BOM が混じり、ビルドも全レビューも通過した」と記録されていました1。しかし後に私が一次計測ログとコミット履歴の時刻を突き合わせて検算したところ、生 U+FEFF は独立査読やサイトビルドより前の自己チェック（通し読み直後の grep）で偶然見つかって除去されており、混入状態のまま本番ビルドと独立査読を通過したわけではありませんでした1。

それでも、混入中の本文が既存の文章・コードブロック検査 4 種をエラーなしで通過し、当時の公開前検査スクリプトにも U+FEFF の検出項目が無かった事実は変わりません1。目に見えないバイト列に対して偶然の自己チェックに頼り続ける危うさを断つため、リポジトリA では 再現用のテストデータを .gitattributes の -text で改行正規化から保護し、記事やスクリプト側への混入は編集ツール呼び出し経由の再混入リスクも織り込んで行番号付きの公開前機械検査で止める二段の仕組み を導入しました。本稿ではその実測データと設計判断を詳しく整理します。

なぜテストデータは .gitattributes で守り、本文は行番号付き検査で止めるのか

同じ不可視のバイト列であっても、受け取る処理系が「どこで止めるか」「どこを素通りさせるか」はレイヤーによって正反対になります。リポジトリA での作業過程を整理すると、まず処理系ごとの振る舞いの違いを把握する必要がありました。

処理レイヤーごとに異なる「不可視バイト列」の通過と停止

私がリポジトリA で実測した範囲では、Go ツールチェーンはファイル途中の生 U+FEFF を即座にエラーで止める一方、Git の設定や Markdown 処理系、記事公開前検査スクリプトの初期版は、意図しない変換や素通りを起こしていました。

Go ツールチェーンが先頭以外の生 U+FEFF を止める仕組み

AI エージェントが検証用コードおよび再現テストを作成した際、main_test.go（12 行目）、reproduce_test.go（63 行目）、equivalence_test.go（14 行目）の 3 ファイルで文字列リテラルに生 U+FEFF を含めたところ、Go 1.27.3（darwin/arm64）の go test セットアップ段階および go vet / gofmt 解析段階はいずれも illegal byte order mark で処理を停止しました1。

以下の出力は、テスト用ソースの文字列リテラルに生 U+FEFF が含まれた状態で go test を実行した際の出力（リポジトリA の検証記録より）です1。

go version go1.27.3 darwin/arm64
# bomcheck
main_test.go:12:9: illegal byte order mark
FAIL	bomcheck [setup failed]
FAIL

Go 言語仕様ではソース先頭の UTF-8 BOM のみ実装制限として無視を許し、それ以外の位置の BOM は禁止できると定められており5、標準字句解析器 go/scanner の実装（53 行目で bom = 0xFEFF と定義）でも、88〜90 行目でオフセット 0 より後ろ（s.offset > 0）の bom に対して illegal byte order mark エラーを返す仕組みになっています6。\xef\xbb\xbf や \uFEFF に直した後は、単体検証（main_test.go: 0.446s）、等価性テスト（equivalence_test.go: 0.262s）、修正後版の再現テスト（reproduce_test.go: 0.309s）がいずれも PASS し、修正前版の reproduce_test.go のみバグ再現テストとして期待どおり失敗（0.263s）することを確認できました1。

したがって、Go ソースコード内に BOM を扱う文字列リテラルを書くときは、生のバイト列を埋め込まず、次のようなエスケープ表記で安全に記述します。外部ライブラリは不要で Go 標準ライブラリのみで動作します。

ファイル: bom_escape_test.go

package bomcheck

import (
	"strings"
	"testing"
)

func TestTrimSpaceDoesNotStripBOM(t *testing.T) {
	const bom = "\uFEFF"
	input := bom + "氏名"

	got := strings.TrimSpace(input)
	if got == "氏名" {
		t.Fatalf("TrimSpace should not strip U+FEFF, got %q", got)
	}
	if !strings.HasPrefix(got, bom) {
		t.Fatalf("expected prefix U+FEFF to remain, got %q", got)
	}
}

モジュールを初期化して実行するコマンドは次のとおりです。

go mod init bomcheck && go test -v .

このコードでは const bom = "\uFEFF" として ASCII 文字のみでコードポイントを表現しているため、字句解析器に弾かれません。また、strings.TrimSpace が空白文字ではなくフォーマット文字である U+FEFF を取り除かない点も、コンパイルエラーではなくテストの論理検証として実行できます。

Markdown 本文が生 U+FEFF を素通りさせる理由

一方、記事執筆サブエージェントが初回ファイル書き出しを行った時点で、展開後 681 行目の `"\uFEFF"` を解説する文脈のインラインコードに、生 U+FEFF が 1 文字入り込みました1。

CommonMark Spec 0.31.2 §2.1 では、あらゆる Unicode コードポイントの並びが有効な文書とされ、Unicode 空白文字も一般カテゴリ Zs またはタブ・改行系（U+0009、U+000A、U+000C、U+000D）に限定されるため、U+FEFF は構文エラーにも空白区切りにもなりません8。Unicode Consortium の FAQ でも、マークアップやプロトコル側で制限を置かない限り、ストリーム途中の U+FEFF はそのまま文字列内容の一部として扱われると整理されています（通常発生すべきではなく、後継としては U+2060 が推奨されています）3。実際にリポジトリA では、681 行目に生 U+FEFF を抱えた本文が、コードブロック一致検査（code-blocks-match.py）、文体検査（style.py）、重複表現スキャン（repetition-scan.pl）、英字語彙抽出（latin-in-japanese.pl）の既存機械チェック 4 種をエラーなしで通過しました1。

1段目: テストデータの CRLF を .gitattributes（*.csv -text）で守る

再現テスト用の CSV ファイルをエディタ経由ではなくバイト列のまま生成するため、AI エージェントは Python スクリプト（gen_testdata.py）の Path.write_bytes を使い、修正前・修正後の比較用ディレクトリ 2 系統に各 3 種・計 6 ファイルを作成しました1。内訳は excel-saved.csv（BOM ef bb bf あり、CRLF 4 箇所、146 バイト）、exported.csv（BOM なし、CRLF 4 箇所、143 バイト）、support-masked.csv（BOM なし、LF 4 箇所、139 バイト）です1。

以下は、エディタや文字列正規化の影響を受けずに BOM と CRLF を持つ再現 CSV を生成したスクリプトです。

ファイル: gen_testdata.py 引用元: リポジトリA（非公開）の gen_testdata.py

#!/usr/bin/env python3
"""testdata を、エディタを通さずバイト列で書き出す。before と after に同じものを置く。"""
from pathlib import Path

root = Path(__file__).resolve().parent
BOM = b"\xef\xbb\xbf"
body = ["氏名,金額,メール", "見本 一郎,3000,ichiro@example.org", "見本 二葉,5000,futaba@example.org", "見本 三郎,10000,saburo@example.org"]
def make(nl, bom):
    return (BOM if bom else b"") + (nl.join(body) + nl).encode()
files = {"excel-saved.csv": make("\r\n", True), "exported.csv": make("\r\n", False), "support-masked.csv": make("\n", False)}
for d in ("before", "after"):
    for name, data in files.items():
        (root / d / "donorimport/testdata" / name).write_bytes(data)

Path.write_bytes で \r\n と先頭バイト b"\xef\xbb\xbf" を直接書き出しているため、生成直後のファイル自体は意図したバイト列になっていました。ところが、この環境の Git 設定 core.autocrlf が input（チェックアウト時は変換せず、チェックイン時に正規化する設定）だったため2、git add 実行時に CRLF will be replaced by LF the next time Git touches it という警告が 4 件出力されました1。実際にコミットされたツリーを確認すると、CRLF を持つ 4 ファイルはすべて crlf=0, lf_only=4（142 バイト / 139 バイト）へ変換されていました1。一方、excel-saved.csv の先頭 BOM（ef bb bf）自体は Git の改行変換では消えずに残っていました1。

core.autocrlf は開発者個人の環境設定に依存します。リポジトリに .gitattributes をコミットすれば各環境の core.autocrlf 設定より属性指定が優先され、環境を問わず同じ改行コードを維持できます47。さらに、このテストデータには CRLF のファイル（excel-saved.csv、exported.csv）と元から LF のファイル（support-masked.csv）が混在するため、text eol=crlf のように一律 CRLF へ揃える属性ではなく、チェックイン・チェックアウト双方の改行変換を行わない -text（*.csv -text）をテストコード群のルートディレクトリ（対象テストデータディレクトリの親階層）に配置しました17。

テストコード群のルートディレクトリに配置した実際の属性設定は次のとおりです。

ファイル: .gitattributes 引用元: リポジトリA（非公開）のテストデータ保護用 .gitattributes

# 再現条件（BOM・CRLF）をバイトのまま保つ
*.csv -text

この設定により、ディレクトリ配下のすべての .csv ファイルに対して Git の改行コード変換が無効化されます。

ただし、.gitattributes を追加しただけでは、すでにインデックスやコミットに誤った LF で格納されたファイルの改行は自動では戻りません49。.gitattributes を追加・更新した後に既存の追跡ファイルへ反映してインデックスの状態を確かめるには、次のコマンドを実行します。

git add .gitattributes && git add --renormalize . && git status

git add --renormalize を実行すると、すべての追跡済みファイルに clean 処理が強制的に再適用されます9。リポジトリA ではこの操作により、LF へ変換されていた対象 4 ファイルが元の crlf=4, lf_only=0（146 バイト / 143 バイト）へ復元され、support-masked.csv は lf_only=4（139 バイト）のまま保たれました1。なお、今回は .gitattributes の追加と git add --renormalize を連続して同時に適用して復元を確認した範囲での記録であり、新規作成時に最初から .gitattributes だけを置いて git add した場合の単独挙動は切り分けて測定していません1。

2段目: 偶然の自己チェックを脱し、行番号と修正ガイドを返す公開前検査を足す

解説記事の本文 681 行目に紛れ込んだ生 U+FEFF は、執筆後の自己チェックで通し読み画面上に "" のように見えた箇所をエージェントが grep -n $'\xef\xbb\xbf' で叩いて発見し、`"\uFEFF"` へ直しました1。これが独立査読（約 20 秒後〜）およびサイトビルド＋公開前チェック（約 41 分後）の 前 に起きていたため、本番ビルドまで生 U+FEFF が残ったわけではありませんでした1。しかし、もし自己チェックの通し読みで目に留まらなければ、既存のチェック 4 種をすでに素通りしており、当時の publish-ready.py にも止める項目が存在しませんでした1。

UTF-8 の BOM が混入しているかどうかといった機械的に定まる条件は、人間の目視や対話的なレビューでは見落としやすく、一方でプログラムで走査すれば確実かつ安価に全行を見つけられます。適材適所として、プログラムによる機械検査に委ねるべき領域です。さらに、その場限りの grep や即席スクリプトで毎回同じ確認をやり直すのではなく、2 回以上同じ用途の検査を書くなら共通のツールへ組み込んで再利用する運用にすることで、過去の失敗を仕組みの学習として定着させられます。

CommonMark 上で構文エラーにならない崩れを専用の決定論的 Python スクリプトで止める設計は Markdown のコードスパン崩れを Linter で検出した過去記事 と同じアプローチであり、入力の破損を数値やステータスでなく実内容の機械検査で止める点は 文字化けテキストの取得ゲート通過を検証した過去記事 とも通底します。

そこで、公開前の最終チェックから呼ばれる publish-ready.py に U+FEFF 検査を組み込みました1。「ただ存在を数えるだけ」ではなく、どのファイルの何行目に混入しているか と 「見えない文字。`\uFEFF` と書く」という修正方針 を標準エラー出力へ出して exit 1 で止める形にしています1。

以下は、publish-ready.py に追加した行番号・修正ガイド付き U+FEFF 検査の抜粋です（同スクリプトには他に連載記事のヘッダ画像の有無や HTML コメント内の退避 Mermaid を調べる判定項目も含まれており、記事全体の最終チェックとして動きます）。

ファイル: publish-ready.py（該当検査部の抜粋） 引用元: リポジトリA（非公開）の publish-ready.py

    for c in re.finditer('\ufeff', text):
        line = text.count('\n', 0, c.start()) + 1
        found.append(f'{line}行目: U+FEFF（BOM）が混じっている（見えない文字。`\\uFEFF` と書く）')

リポジトリA の既存公開記事全体に対して実行して 0 件（exit 0）を確かめたうえで、4 行目に生 BOM を仕込んだ検証用ダミーファイルに対して実行したところ、次の出力を返して exit 1 で停止しました（リポジトリA の検証記録より。なおリポジトリA の既存公開記事全体で exit 0 となることは 2026年11月16日時点でも再確認済みです）1。

/tmp/bomt/x.md: 4行目: U+FEFF（BOM）が混じっている（見えない文字。`\uFEFF` と書く）

正常終了時は標準エラー出力を出さず exit 0 を返し、生 U+FEFF を検出したときだけ標準エラー出力へ行番号と直し方を出して exit 1 で止まります1。

読者がご自身の CI や公開前チェックへそのまま持ち帰れるよう、Python 3 標準ライブラリのみ（外部ライブラリ不要）で動作し、指定ディレクトリ配下の Markdown だけでなく 検査スクリプト自身 も走査対象に含める自己完結型のスクリプトを次に示します。

ファイル: check_bom.py

#!/usr/bin/env python3
"""Markdown やスクリプト本体に含まれる生の U+FEFF（BOM）を行番号付きで検出する。"""
import pathlib
import sys

BOM = chr(0xFEFF)
ESCAPE_HINT = chr(92) + "uFEFF"


def find_bom_lines(path: pathlib.Path) -> list[str]:
    text = path.read_text(encoding="utf-8")
    errors = []
    for lineno, line in enumerate(text.splitlines(), start=1):
        if BOM in line:
            errors.append(
                f"{path}: {lineno}行目: U+FEFF（BOM）が混じっている（見えない文字。`{ESCAPE_HINT}` と書く）"
            )
    return errors


def collect_targets(args: list[str]) -> list[pathlib.Path]:
    if not args:
        targets = sorted(pathlib.Path(".").rglob("*.md"))
        self_path = pathlib.Path(__file__).resolve()
        if self_path not in {p.resolve() for p in targets}:
            targets.append(pathlib.Path(__file__))
        return targets

    targets: list[pathlib.Path] = []
    for raw in args:
        p = pathlib.Path(raw)
        if p.is_dir():
            targets.extend(sorted(p.rglob("*.md")))
        elif p.is_file():
            targets.append(p)
        else:
            print(f"{p}: 指定されたパスが見つかりません", file=sys.stderr)
    return targets


def main(args: list[str]) -> int:
    targets = collect_targets(args)
    status = 0
    for path in targets:
        for msg in find_bom_lines(path):
            print(msg, file=sys.stderr)
            status = 1
    return status


if __name__ == "__main__":
    sys.exit(main(sys.argv[1:]))

対象ディレクトリと検査スクリプト自身を指定して実行するには、次のコマンドを実行します。

python3 check_bom.py docs/ check_bom.py

コード内では \ufeff や \uFEFF という \uXXXX 形式の文字列リテラルを直接書かず、BOM = chr(0xFEFF) と ESCAPE_HINT = chr(92) + "uFEFF" によって文字を組み立てています。さらに、引数未指定時にも pathlib.Path(__file__) を対象へ加えることで、後述する「検査ツール自身への再混入」に対しても自身を点検できるようにしています。

検査ツールの死角と、.gitattributes・既存 Linter とのトレードオフ

仕組みを入れて一件落着に見えた直後、今度はその検査スクリプト自体に生の U+FEFF が混入する事象が起きました。ここでは一次記録から見えた編集時の死角と、設定・ツール選定上のトレードオフを整理します。

検査を追加した直後に起きた「ツール自身への再混入」と被覆の穴

publish-ready.py に U+FEFF 検査を追加した直後、コードレビューで「行番号計算（text.count('\n', 0, c.start()) + 1）が既存の別チェックと重複している」との指摘を受け、AI エージェントがリファクタリングを行いました1。その際、ファイル編集ツールの呼び出し引数に新しいチェック定義として re.compile('\ufeff') を渡したところ、publish-ready.py 自身の 24 行目に生の U+FEFF（0xEF 0xBB 0xBF）が 1 文字書き込まれました1。直後に失敗した別編集のエラーメッセージにも、同ツールが \uXXXX エスケープと実文字の相互入れ替えを試みた旨の注記が残っていました1。

しかも、publish-ready.py は既定で公開用記事ディレクトリ配下の Markdown のみを検査対象としており、検査スクリプト自身の .py ファイルは対象外でした1。記事本文の検査ばかりを厚くして周辺のツールや設定ファイルに目が届かない構造は、検査対象の「末端偏重」が招く死角を分析した過去記事 と同じ穴です。

セッション再開後の grep で 24 行目の生 U+FEFF に気づいたエージェントは、Python の chr(0xFEFF) と chr(92) + 'ufeff' を用いた置換で ASCII の \ufeff 表記へ戻し、ダミーファイルで既存チェックと BOM チェックの同時検出（exit 1）を確認しました1。この経験から得られる設計教訓は 2 つあります。

  1. 検査コード内で U+FEFF を扱う際は、編集ツール呼び出しの経路で \uXXXX が生文字へ変わる余地を断つため、chr(0xFEFF) のようにコードポイント数値から組み立てる（先の check_bom.py でこの形を採った理由です）。
  2. 検査対象を記事本文ディレクトリに閉じず、検査スクリプト自身やテストコードも走査対象に含める。

なお一次記録上、編集ツール呼び出し時の JSON 引数デコードと編集ツール内部の \uXXXX 置換仕様のどちらが直接生バイトを生んだかまでは、両者が同じ編集操作で重なっているため切り分けられていません1。また、セッション再開直後にエージェントが最初にツール自身の生 BOM を疑って grep した内部判断の動機までは記録から特定できません（直前の編集失敗エラーが契機となった可能性はありますが断定はできません）1。

.gitattributes の -text と binary の違い ── なぜテストデータには -text を選ぶか

テストデータの改行を固定する属性指定には -text と binary がありますが、差分レビューやマージの可読性を保てるかどうかで明確な違いがあります。

属性指定改行コード変換git diff のテキスト表示3-way マージ適したファイル
*.csv -text無効化（チェックイン・チェックアウトとも変換しない）7有効（テキスト差分を表示）有効中身の行差分を PR で確認したいテスト用 CSV・テキスト fixture
*.csv binary無効化（組み込みマクロ [attr]binary -diff -merge -text 相当）7無効化（Binary files differ 表示）無効化画像・アーカイブ等の非テキストバイナリ、または巨大な自動生成データ

CSV のテストデータは改行バイトが壊れてほしくない一方で、列やダミー行の変更内容はテキストの差分として確認したいため、改行変換だけを止める -text の方が目的に合います。また、.gitattributes はリポジトリのルートだけでなくサブディレクトリ内にも置け、深い階層の設定が優先されます7。リポジトリ全体の他ファイルへ影響を出さないよう、対象テストコード群のルートディレクトリ（テストデータの親階層）に閉じて置く方が安全です。なお、今回の実測では *.csv binary を実際に当てた際の差分挙動までは試しておらず、上記の比較は Git 公式仕様に基づく整理です。

先頭 BOM 型 Linter・GitHub 警告と、行番号付き独自検査の違い

既存の主要 Linter や GitHub の警告機能は導入が容易な反面、記事やコードの「途中」に混入した生 U+FEFF をローカルや CI で即座にブロックする用途には空白が残ります。

手段検査対象の位置実行タイミング自動ブロック主な用途と死角
汎用 Linter の BOM ルール（Biome useConsistentUnicodeBom / ESLint・Bun unicode-bom）ファイル 先頭 での U+FEFF の有無を検査（Biome 仕様は先頭以外の文字を検査対象外と明記10、ESLint・Bun もファイル先頭が対象1112）ローカル・CI可ファイル先頭 BOM の統一には有効だが、インラインコードや文書途中の 1 文字は素通りする
GitHub Web UI の隠し Unicode 警告ファイル内容に含まれる隠し Unicode テキスト13github.com での画面表示時不可（警告表示のみ）PR やファイル閲覧時の目視喚起には役立つが、ローカル作業や CI ビルドを自動停止はしない
行番号付き公開前機械検査（自前スクリプト等）ファイル全体（1 行目〜末尾まで全文字）公開前テスト・CI可（exit 1）文中・コード中の 1 文字を行番号付きで止められるが、検査スクリプト自身の再混入や対象ディレクトリ外は走査範囲の設計が別途要る

つまり、先頭 BOM 用 Linter を入れていても文中の生 U+FEFF 混入は止まらず、GitHub の画面警告だけではローカル変更や CI を止められないため、文書と周辺スクリプトには全文字走査の機械検査を重ねる価値があります。

「エディタの不可視文字ハイライト設定で足りるのでは」という反論も考えられます。確かに人間が Visual Studio Code 等で常にファイルを直接開いて編集するなら、視覚的ハイライトが効きます13。しかし、AI コーディングエージェントがファイル生成ツールや編集ツールを通じて大量の Markdown・テスト・スクリプトを直接書き換える運用では、エディタの描画画面を経由せずにコミット・レビュー工程へ進むことが多くなります。実際、リポジトリA でも導入前の確認では既存公開記事全体の生 U+FEFF が 0 件であり1、別リポジトリである当ブログの 公開記事55本の外形痕跡をスキャンした過去記事 でも 2026年8月21日時点で不可視文字 0 件を確かめていましたが、そのように既刊が清浄な環境であっても、個別の執筆・編集工程では混入が起こり得ます。人間の目視前提の補助設定と、機械的に exit 1 で止めるゲートは競合ではなく役割が異なります。

前提が変われば結論はどう変わるか

今回の設計は、実ファイルのテストデータと現行のエージェント編集ツールを前提にしています。前提が次のように変われば、採るべき手段も変わります。

  1. テストデータを外部ファイルとして持たない設計が採れる場合: 再現テストの入力を外部の .csv ファイルではなく、テストコード内のバイト配列リテラル（Go の []byte{0xEF, 0xBB, 0xBF} や Python のバイト列生成）だけで完結させられるなら、Git の改行正規化による破損リスク自体が無くなり、.gitattributes の維持は不要になります。ただし「表計算ソフト等で作った実ファイルそのものを回帰テストの証拠として残す」要件がある場合は、.gitattributes による保護が引き続き必要になります。
  2. エディタ・編集ツール・プラットフォーム側で不可視文字の遮断が標準化された場合: AI コーディングエージェントの編集ツールが \uXXXX の暗黙展開を起こさない実装へ変わる、あるいは汎用 Markdown Linter や CI プラットフォームがファイル途中の U+FEFF やゼロ幅文字をデフォルトでエラーとしてブロックする環境が整えば、自前で Python スクリプトを書く必要性は薄れます。それでも「意図的に残すテストデータは正規化対象から外す」「検査対象の一覧から検査ツール自身や設定ファイルを落とさない」という境界設計の原則は変わりません。

よくある質問（FAQ）

Q. Git で CRLF を含むテストデータが自動的に LF へ変換されるのを防ぐには、.gitattributes に何を書けばよいですか？

A. 対象テストコード群のルートディレクトリまたはリポジトリの .gitattributes に *.csv -text のように -text 属性を指定します。-text はチェックイン・チェックアウト双方での改行変換を無効化しつつ、テキスト差分（diff）と 3-way マージの機能は維持するため、CRLF と LF が混在するテストデータの検証とレビューを両立できます7。

Q. .gitattributes を追加しただけでは、既にコミットされたテストデータの CRLF が戻らないのはなぜですか？

A. .gitattributes の変更はすでにインデックスやリポジトリへ格納済みのファイル内容を自動では再処理しないため、追加後に git add --renormalize . を実行してインデックスへ再適用する必要があります49。私の検証でも、.gitattributes の設定後に --renormalize を走らせることで、LF へ変換されていた 4 つの CSV ファイルが元の CRLF 4 箇所（146 バイト / 143 バイト）へ復元されました1。

Q. UTF-8 の BOM（U+FEFF）がコードや Markdown の途中に混入すると何が起き、どう検出すれば防げますか？

A. Go 1.27.3 のような字句解析・言語処理系では先頭以外の U+FEFF で illegal byte order mark エラーになりますが56、Markdown パーサーやファイル先頭のみを見る汎用 Linter（Biome 仕様は先頭以外を検査対象外と明記）は本文途中の 1 文字をエラーにせず素通りさせるため810、ファイル全体を対象に行番号を出力して停止する機械検査を CI や公開前チェックに組み込む必要があります1。本稿で示したように、検査スクリプト自身の中でも chr(0xFEFF) で文字を組み立て、検査ツール自身も走査対象に含めることで再混入リスクにも備えられます。

まとめ

  • core.autocrlf=input の環境ではテスト用 CSV の CRLF がコミット時に LF へ変換されるため、対象テストコード群のルートディレクトリの .gitattributes（*.csv -text）と git add --renormalize を組み合わせて、テキスト差分を維持したまま再現条件を保護する。
  • Go 1.27.3 の字句解析（go/scanner）が 3 ファイルすべてで先頭以外の生 U+FEFF を illegal byte order mark として停止したのに対し、CommonMark 仕様と先頭 BOM 型の汎用 Linter は本文途中の U+FEFF を止めないため、ファイル全体を対象に行番号と修正方針を返して exit 1 で止める公開前検査を組み込む。
  • ファイル編集ツールの呼び出しを経由して検査スクリプト自身の 24 行目にも生 U+FEFF が再混入した実例が示すように、検査スクリプト内では検出対象文字を chr(0xFEFF) で組み立て、案内メッセージの表記にも chr(92) + 'uFEFF' 等を用いてリテラルの \uXXXX 記述を避け、公開記事だけでなく検査スクリプト自身も走査範囲に含める。
  • 当初の「ビルドも全レビューも通過した」という記録が時系列検算で誤認（自己チェックの偶然に救われたもの）と判明したとおり、既存チェックの通過や目視確認を不可視文字不在の証拠とみなさず、2 回以上行う確認は再利用可能な決定論的テストへ閉じる。
