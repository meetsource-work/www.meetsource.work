mise の設定から外したツールが消えない理由：tracked-configs に残る古い git worktree の設定と整理手順

mise（mise-en-place）の非推奨警告（ubi バックエンドは非推奨であり 2027.1.0 で削除予定）を受けて、グローバル設定 ~/.config/mise/config.toml の "ubi:joshrotenberg/adrs" を "github:joshrotenberg/adrs" へ書き換えました。ところが mise ls を実行すると、ubi: 側の版が選択元なし（グレー表示）のまま残り、最後の 1 版 0.11.0 が消えずに居座りました1。

mise の tracked-configs とは、mise がこれまでに読み込んだ設定ファイルを 1 件ずつ記録する ~/.local/state/mise/tracked-configs 配下の一覧です。mise prune は、ここに記録された設定ファイルと、実行した tool stub を記録する ~/.local/state/mise/tracked-stubs のどちらからも選ばれていないインストール済みの版を削除します2。つまり、どこかに残った設定ファイルが「この版を使う」と書いている限り、その版は消えません。なお「参照元」は mise の公式用語ではなく、本記事では版を要求し続けている設定ファイルを指す言葉として使います。

tracked-configs を逆引きしたところ、ubi: 側の版を指定していたのは dotfiles リポジトリの古い git worktree 2 件にある、古いコミット時点の設定ファイル（"ubi:joshrotenberg/adrs" = "0.11.0"）だけでした1。公式仕様と照らすと、この 2 件の設定ファイルが 0.11.0 を残していたと読めます。さらに、worktree のディレクトリが残っている限りその設定ファイルは実在するため、mise prune --configs を実行しても記録から外れません23。

本記事では、実際の観測記録と公式仕様・ソースコードをもとに、参照元を逆引きするコマンド、不要な worktree を片付けてから mise prune を実行する順序、そして git worktree prune と mise prune --configs の守備範囲の違いを整理します。

観測の範囲と記録の残り方

本記事で扱う実測データは、2026-11-05 のセッション記録と 2026-11-19 時点の環境確認に基づいています1。記録に残っている範囲と、記録に残っていない範囲の境界は以下のとおりです。

  • 2026-11-05 のセッション記録: Claude Code が実行した mise ls・grep・Python による逆引き・git worktree list のコマンドと出力1
  • dotfiles リポジトリの git 履歴: 古い worktree が指していたコミットの .config/mise/config.toml1
  • 2026-11-19 時点の環境確認: worktree の一覧、tracked-configs の件数、mise ls の表示1

一方で、ubi: 側の 0.12.1 と 0.13.0 を消したときのコマンド、および古い worktree を削除して mise prune を実行した手順と順序はセッション記録に残っておらず、当時の mise のバージョンも記録にありません1。CLI や Git の境界の外で筆者が行った操作はログに入らないため、後半で示す整理手順は観測した事実と公式仕様を組み合わせて導いたものです。

mise prune が版を残す仕組み：tracked-configs と —configs

mise は読み込んだ設定ファイルを ~/.local/state/mise/tracked-configs に、実行した tool stub を ~/.local/state/mise/tracked-stubs に記録し、mise prune はそのどちらからも選ばれていないインストール済みの版を削除します2。保存場所 ~/.local/state/mise は環境変数 MISE_STATE_DIR または XDG_STATE_HOME で変更でき、trust の決定と tracked config のパスが置かれます4。

mise prune にはもう一つ、「もう存在しない」tracked / trusted / ignored の設定ファイルの記録を忘れる役割があります。--configs フラグはこの記録の忘却だけを行い、--tools フラグは未使用の版の削除だけを行います2。

実装（src/config/tracking.rs）を確認すると、Tracker::track_in は設定ファイルのパスを hash_to_str でハッシュ化した名前で、Unix ではシンボリックリンクとして記録します3。Tracker::clean_in は各エントリのリンク先について path.is_file() を判定し、真なら保持して偽のときだけ削除します3。したがって、古い worktree 内の設定ファイルがディスク上に実在する限り、記録は消えません。

mise から見れば、古い worktree の設定ファイルも、いま使っている設定ファイルと同じ「実在する参照元」です。

何が起きたか：設定から外した ubi 版が mise ls に残った

バックエンドを切り替えた直後と約 10 分後に観測された mise ls の出力を、事実と留保を切り分けて確認します。

書き換え直後：ubi 側の 3 版が選択元なしで残った

~/.config/mise/config.toml を "ubi:joshrotenberg/adrs" から "github:joshrotenberg/adrs" へ書き換えた直後、Claude Code に mise ls | grep -i adrs を実行させて状態を確認しました1。

引用元: 筆者の環境で Claude Code が実行した mise ls の出力（2026-11-05 のセッション記録）

github:joshrotenberg/adrs  0.12.1
github:joshrotenberg/adrs  0.13.0                   ~/.config/mise/config.toml  0.13.0
ubi:joshrotenberg/adrs     0.11.0
ubi:joshrotenberg/adrs     0.12.1 (pruned in 15h)
ubi:joshrotenberg/adrs     0.13.0

5 行のうち github:joshrotenberg/adrs の 0.13.0 だけが ~/.config/mise/config.toml から選ばれており、ubi:joshrotenberg/adrs の 3 版（0.11.0・0.12.1・0.13.0）はいずれも選択元の列が空でした1。同じ時点で command -v adrs は ubi 側の 0.13.0 のバイナリ実体を指していましたが、その理由は記録から切り分けていません1。

なお 0.12.1 に付いている (pruned in 15h) は、mise ls の pruning_label 関数が remove_after までの残り時間を出力する書式と一致します5。このラベルが 0.12.1 にだけ付いた内部判定理由は特定していません。

約 10 分後：0.11.0 の 1 版だけが残った

約 10 分後、再び Claude Code に mise ls | grep -i adrs を実行させると、出力は次の 3 行に変わっていました1。

引用元: 同じセッションで約 10 分後に Claude Code が実行した mise ls の出力

github:joshrotenberg/adrs  0.12.1
github:joshrotenberg/adrs  0.13.0                 ~/.config/mise/config.toml  0.13.0
ubi:joshrotenberg/adrs     0.11.0

ubi: 側は 0.11.0 の 1 版だけが残り、インストール先ディレクトリ内の 0 と latest のシンボリックリンクが ./0.11.0 へ張り直されていました1。この約 10 分の間に 0.12.1 と 0.13.0 を消したコマンドは、記録に残っていません1。

参照元を逆引きする：古い worktree の config.toml が見つかった

残った 0.11.0 の参照元を突き止めるため、最初に Claude Code が grep -rn 'adrs' ~/.tool-versions ~/.config/mise/conf.d ~/.local/state/mise を実行しましたが、出力は空でした1。tracked-configs のエントリは設定ファイルのパスへのリンク（またはパス文字列）を持つだけで中身はリンク先にあるため3、参照元を調べるにはリンク先を開いて読む必要があります。

2026-11-05 時点の ~/.local/state/mise/tracked-configs にはハッシュ名のエントリが 28 件ありました1。Claude Code は os.path.realpath でリンク先を解決し、adrs を含む行を抽出する Python スクリプトを実行しました1。

引用元: 同じセッションで Claude Code が参照元を探すために実行したコマンド

python3 - <<'EOF'
import os,glob
for f in glob.glob(os.path.expanduser('~/.local/state/mise/tracked-configs/*')):
    t=os.path.realpath(f)
    try:
        s=open(t).read()
    except Exception as e:
        continue
    if 'adrs' in s:
        for i,l in enumerate(s.splitlines(),1):
            if 'adrs' in l: print(t,i,l)
EOF

生出力にはローカルのユーザー名や非公開リポジトリのパスが含まれるため、パスを一般化したうえでファイル単位に整理しました。出力 1 行を 1 件として集計すると、ユニークなパス 8 件から計 19 行が出力されていました1。

設定ファイル（一般化）出力行数指定
dotfiles リポジトリの .config/mise/config.toml（同じパスが 2 回出力）2"github:joshrotenberg/adrs" = "0.13.0"
古い worktree A の .config/mise/config.toml 9 行目1"ubi:joshrotenberg/adrs" = "0.11.0"
古い worktree B の .config/mise/config.toml 9 行目1"ubi:joshrotenberg/adrs" = "0.11.0"
他の設定ファイル 5 か所（各 3 行）15"github:joshrotenberg/adrs" = "0.12.1" ほかコメント行
合計19（ユニークなパス 8 件）

2026-11-05 時点の 28 件のうち、ubi: 側の版を要求していたのは古い worktree 2 件の設定ファイルだけでした。残った版 0.11.0 は、その 2 件が指定していた版と一致します1。

このスクリプトは glob で tracked-configs 配下の全エントリを取得し、os.path.realpath でリンク先の実ファイルを開いて adrs を含む行番号と行内容を表示しています。

さらに Claude Code が実行した git worktree list では、main を含む 4 件の worktree が見つかりました1。古い worktree A・B はリポジトリ内の .claude/worktrees/ 配下にあり、どちらも未コミットの変更がなく、main に取り込まれていないコミットもありませんでした1。

dotfiles リポジトリの git 履歴で A・B が指すコミットの .config/mise/config.toml 9 行目を確認すると "ubi:joshrotenberg/adrs" = "0.11.0" が実際に書かれていましたが、3 つ目の worktree C が指すコミットの同ファイルには adrs の記述がありませんでした1。worktree があるだけではツールは残らず、古い設定を持ったままの worktree が残っているときに参照元になります。

前述の仕様と照らすと、0.11.0 が残っていたのは、この 2 件の設定ファイルが実在し続けて mise prune の保持対象になっていたためと読めます（途中の操作記録がないため推測として留保します）。なお、git worktree は作業ディレクトリを分けても .git 配下の管理領域を共有する仕組みであり、linked worktree の共有境界の詳細は git worktree の分離境界を整理した記事 で解説しています。

逆引きと片付けのコマンド比較

Python スクリプトを書かなくても、公式コマンドだけで参照元の確認と片付けができます。手段ごとの守備範囲を 2 つの表で整理します。

参照元を逆引きする手段

何も変えずに参照元を調べるなら、mise ls --all-sources で要求の出どころを見て、mise prune --dry-run で消える版と残す側のファイルを確かめます。

手段何が分かるか根拠
mise config ls --tracked-configsmise がどのプロジェクトで読み込んだ設定ファイルも含めた一覧mise config ls 公式ドキュメント6
mise ls --all-sourcesいま読み込んでいる設定だけでなく、mise が見たことのあるすべての設定ファイルからの要求mise ls 公式ドキュメント7・PR #80198
mise prune --dry-run削除される版の予測と、その理由。同じツールの別の版が残る場合は、残る版とそれを要求しているファイルが出る（例: node is required at 20.19.5 by ~/src/app/mise.toml）mise prune 公式ドキュメント2・src/cli/prune.rs9

削除対象の一覧だけを見たいときは mise ls --prunable を使います27。

ただし mise prune --dry-run が残る版と要求元のファイルを出力するのは、実装上 to_delete に入った削除対象の版ごと（explain_removal）です9。そのため、対象のツールに削除予定の版が 1 つもないときはこの説明も出力されません9。

なお mise unuse <tool>@<version> も、他の tracked config や tool stub が版を必要とするときに保持しているファイルを表示しますが、設定ファイルを書き換えて prune まで実行する破壊的なコマンドのため10、参照元を調べるだけの用途には向きません。

片付けのコマンドと守備範囲

worktree ごと片付けるのは git worktree remove で、git worktree prune と mise prune --configs はどちらも、ディレクトリが残っている worktree には効きません。

コマンド片付けるもの古い worktree が残っているとき
git worktree remove <path>worktree のディレクトリとその Git 管理情報。未追跡ファイルや変更がある worktree は --force が要る11設定ファイルごと消える11
git worktree prune$GIT_DIR/worktrees 配下の、不要になった worktree の Git 側管理情報11対象外（ディレクトリが残っているため）11。mise の状態ファイルにも触れない
mise prune --configs実在しなくなった tracked / trusted / ignored 設定の記録2設定ファイルが実在するので記録は残る23
mise prune（--tools を含む）どの tracked config・stub からも選ばれていない版2古い設定が指定する版は残る2

順序は Git が先、mise が後になります。不要な worktree を消して設定ファイルがなくなってから mise prune を実行すると、記録の忘却と版の削除が 1 回で済みます2。

推奨手順：worktree を片付けてから mise prune する

2026-11-05 のセッションは、Claude Code が worktree A・B を git worktree remove で消し、mise prune を実行するコマンドを提案したところで終了しています1。その後、2026-11-19 時点の環境を確認すると、worktree A・B、それらを指す tracked-configs のエントリ、ubi:joshrotenberg/adrs のインストール実体はいずれもなくなっており、mise ls に ubi: 側は表示されなくなっていました1。一方、古い設定を持たなかった worktree C とそのエントリは残っています1。

どの順で作業したかの実行ログは残っていませんが、前述の仕様と比較表から導かれる整理手順を 1 本のコマンド列としてまとめます（以下は仕様に基づく推奨手順であり、筆者の環境で実行したログではありません）。mise と git が導入された環境で実行でき、<リポジトリ>・<古い worktree> および main..HEAD の main（既定ブランチ名）は手元の環境に合わせて置き換えてください。

# 1. どの設定ファイルがその版を要求しているかを見る
mise ls --all-sources
mise config ls --tracked-configs

# 2. 参照元になっている古い worktree を確認する
git -C <リポジトリ> worktree list
git -C <古い worktree> status -sb
git -C <古い worktree> log main..HEAD

# 3. 不要な worktree を消す（設定ファイルごと消える）
git -C <リポジトリ> worktree remove <古い worktree>

# 4. 消える版を確かめてから prune する
mise ls --prunable
mise prune --dry-run
mise prune

段 1 では mise ls --all-sources と mise config ls --tracked-configs で参照元のファイルパスを特定します。段 2 では、対象の worktree に未コミットの変更（status -sb）や既定ブランチに取り込まれていないコミット（log main..HEAD）がないかを確かめます。段 3 で git worktree remove を実行して不要な worktree を設定ファイルごと削除し、最後に段 4 で mise ls --prunable と mise prune --dry-run により消える版を確かめてから mise prune を実行します。git worktree prune はディレクトリが残っている worktree には効かないため、この手順には含めません。

worktree を量産する環境での注意

コーディングエージェントの並列実行などで worktree を頻繁に作成する環境では、tracked-configs のエントリが増えやすくなります。消し忘れた worktree 内の設定ファイルは実在するため、mise prune を実行してもリンク切れの記録は消える一方で、生きている設定ファイルへの記録は残ります2312。筆者の環境でも、tracked-configs のエントリ数は 2026-11-05 時点で 28 件、2026-11-19 時点で 48 件でした1（2 時点間の操作履歴は記録にないため、増え方の内訳は特定していません）。

tracked-configs の件数が増大すると、全記録を読み込む mise reshim が件数 N に対して O(N²·k) で遅くなる問題が Issue #15202 で報告されていました12。同 Issue のベンチマークでは、各設定約 30 ツール・N=2000 のときに mise reshim が 93.1 秒（macOS arm64）かかり、MISE_IGNORED_CONFIG_PATHS に一時ディレクトリを指定すると 0.15 秒まで短縮されています12。この性能劣化は 2026-10-30 にマージされた PR #15203 で修正され、v2026.10.25 に含まれました13。

worktree の中でその設定ファイルを使わない運用であれば、ignored_config_paths（環境変数 MISE_IGNORED_CONFIG_PATHS）に作業ディレクトリのパスを指定し、mise が設定ファイルを読み込まないようにする選択肢があります14。ただし、mise prune と mise ls --prunable が従うのは環境変数と global / system の miserc.toml の指定だけであり、プロジェクトの .miserc.toml での指定は効きません14。

よくある質問（FAQ）

Q. mise prune を実行しても、設定から外したツールの版が消えないのはなぜですか？

A. よくある原因は、別の設定ファイルがまだその版を指定していることです。mise prune は ~/.local/state/mise/tracked-configs と ~/.local/state/mise/tracked-stubs に記録されたどれからも選ばれていない版を削除するため、古い git worktree などに残った設定ファイルが指定している版は残ります。また、実行中のプロセスがその版から起動されている場合も保持されます2。

Q. mise prune —configs と git worktree prune は何が違いますか？

A. 片付ける対象が異なります。mise prune --configs は実在しなくなった tracked / trusted / ignored の設定ファイルの記録を mise から忘却し2、git worktree prune は $GIT_DIR/worktrees 配下で作業ディレクトリが失われた worktree の Git 側管理情報を掃除します11。どちらもディレクトリが残っている worktree の設定ファイル自体は消さないため、worktree ごと消すには git worktree remove を使います211。なお、git worktree prune は mise の状態ファイルには触れません。

Q. どの設定ファイルがツールの版を保持しているかを調べるには？

A. mise ls --all-sources で、いま読み込んでいる設定だけでなく mise が見たことのあるすべての設定ファイルからの要求を表示できます7。記録された設定ファイルの一覧を見たい場合は mise config ls --tracked-configs を使います6。mise prune --dry-run は、削除予定の版ごとに同じツールの残る版とそれを要求しているファイルを示します29。

まとめ

  • mise prune は ~/.local/state/mise/tracked-configs と ~/.local/state/mise/tracked-stubs に記録されたどれからも選ばれていない版を削除するため、設定から外した版が残るときは別の設定ファイルがまだ指定していないか（または実行中プロセスが使っていないか）を疑う。
  • 古い git worktree の設定ファイルも実在する限り参照元のままであり、mise prune --configs でも記録から外れない。
  • 参照元の逆引きは mise ls --all-sources と mise config ls --tracked-configs で行い、mise prune --dry-run で消える版と残す側のファイルを確かめる。
  • 片付けは git worktree remove で worktree を消してから mise prune を実行する。git worktree prune は Git 側の管理情報だけを扱い、mise の記録には触れない。
  • worktree を量産する環境でその設定を使わない運用なら、環境変数 MISE_IGNORED_CONFIG_PATHS（または global / system の miserc.toml）で読み込み対象から外す選択肢がある。
