「安いモデルは雑」は作業の型で逆転する ── Claude Code サブエージェント3モデルの実測比較

Claude Code におけるサブエージェント委任とは、メインセッションのコンテキスト肥大化を防ぎつつ、独立したコンテキストと制約されたツール群を持つ自律ワーカーに特定タスクを並列・集中的に実行させて要約結果のみを受け取る仕組みです1。この仕組みを活用して開発業務やパイプラインの自動化を進める際、多くのチームで「計画や設計は Claude Opus、コード実装は Claude Sonnet、雑用や補助作業は Claude Haiku」というピラミッド型のモデル構成が定着しています2。

しかし、この階層構造の根底には「安いモデル＝雑、高いモデル＝正確」という一律の思い込みが存在します。その結果、工程の性質を考慮せず漫然と Sonnet や Opus を一律に使い続け、API コストの急増やモデル利用枠の枯渇に悩まされるケースが後を絶ちません。

当ブログの運営リポジトリ（非公開）のブログ執筆パイプライン実務環境において、同一タスクを Claude Haiku 5.5、Claude Sonnet 5.5、Claude Opus 5.5 の 3 モデルに委任して実機検証を行いました。その結果、原典照合を伴う「狭く深い事実確認」では、最も安価な Haiku 5.5 が Sonnet 5.5 よりも届かない死んだ URL や原典外の数値を生成せず正確であり、空間全体を走査する「広域の網羅探索」では Opus 5.5 が不可欠であるという、作業の型による順位逆転が観測されました。

本記事では、この一次実測データをもとに、サブエージェントのモデル選定基準と、親セッションの透過課金やモデル解決仕様などのハーネス設定について解説します。

検証環境と調査スコープ

実測データの客観性と再現性を担保するため、検証環境および調査スコープの境界を定義します。

検証環境スペック

実機計測は、当ブログの運営リポジトリ（非公開）における自動執筆パイプラインの運用セッション内で実施しました。

  • CLI ツール: Claude Code 2.1.318
  • OS: macOS Sequoia 15.3（Apple Silicon）
  • 計測期間: 2026-11-06T02:31:13Z 〜 2026-11-06T04:21:12Z
  • 比較対象モデル: Claude Haiku 5.5（claude-haiku-5-5）、Claude Sonnet 5.5（claude-sonnet-5-5）、Claude Opus 5.5（claude-opus-5-5）

調査スコープの境界

本検証では、サブエージェントに課される典型的な作業を以下の 2 つの型に分類して実測を行いました。

  1. 狭く深い事実抽出・調査タスク: 原典キャッシュファイルからの情報抽出（本文抽出タスク）、および外部ドキュメントの Web 検索・取得（Web 調査タスク）の 2 企画における実測。
  2. 広域網羅の探索タスク: リポジトリ内の全公開記事（frontmatter および結論部）を横断走査し、未解決の課題やテーマの穴を洗い出す Explore タスク（源泉C）における実測。

交絡要因の排除

モデル単体での純粋なコストと挙動を評価するため、以下の交絡要因を実測により特定し、計測から排除しました。

  • 親セッションの advisor（Opus）透過課金の切り離し: 事前検証試行において、サブエージェント単体の呼び出し費用（$0.443）のうち 72%（$0.318）が親セッションで有効化されていた advisor（Opus 5.5）への課金であることが判明しました。そのため、モデル比較の実測セッションでは親の /advisor を無効化して計測を実施しています。
  • Explore サブエージェントの設定解決仕様の確認: Claude Code の組み込み Explore サブエージェントは、ユーザー設定（~/.claude/agents/Explore.md）等で上書きされている場合、デフォルトモデルがその指定（model: haiku など）に解決されます3。そのため、後述の広域探索タスクではプロンプトや呼び出しパラメータで model: opus を明示指定して実行条件を揃えました。

本記事で書けること・書けないことの境界

一次計測ログに基づき、事実として確認された範囲と解釈の境界を明確にします。

  • 書けること: 2026-11-06 に実施した 2 件の調査タスクにおいて Haiku 5.5 が Sonnet 5.5 よりも誤りが少なく正確であった事実、源泉C において Opus 5.5 が最多の候補数と逐語引用の改変ゼロを記録した事実、および advisor 透過課金や Explore モデル解決の仕様挙動。
  • 書けないこと: あらゆる調査タスクにおいて常に Haiku 5.5 が Sonnet 5.5 より正確であるという一般化（計測対象は 2 企画の局所タスクであり母数は 2 件）。また、Sonnet 5.5 がなぜ死んだ URL や原典外の数値を生成したのかという内部推論機序の断定、および Opus 5.5 を使わずに Sonnet 5.5 を複数回実行して合算した場合のコスト・品質に関する未計測の反実仮想。

評価基準と前提となるアーキテクチャ概念

サブエージェントのモデル選定を評価するにあたり、前提となるアーキテクチャ設計パターンと評価基準を整理します。

オーケストレーター・ワーカーパターンとコンテキスト分離

Anthropic のエージェント設計パターンにおいて、親エージェントが複雑なタスクを分割し、独立したサブワーカーに並列委任して結果を集約する「オーケストレーター・ワーカー」パターンが推奨されています4。

Claude Code のサブエージェント機能は、このパターンをコマンドライン環境で体現したものです。サブエージェントに独立したコンテキストウィンドウを与えて探索を行わせ、最終的な要約のみをメインセッションに返却させることで、メインコンテキストの消費を大幅に抑制します1。

比較する2つの「作業の型」

本記事では、サブエージェントに委任するタスクを以下の 2 つに大別して評価します。

  • 狭く深い事実抽出型: 限られた入力（原典ドキュメントや検索結果）から、正確な事実・数値・引用を抜き出し、未確認事項を漏れなく識別して報告するタスク。
  • 広域の網羅的洗い出し型: 多数のローカルファイルや広大な情報空間を横断走査し、全体の傾向を把握した上で、重複なく候補を構造化して抽出するタスク。

4つの評価基準

モデルの適性を判断するため、以下の 4 つの観点から観察を行いました。

  1. 事実一致率・ハルシネーション: 原典に存在しない数値の混入や、HTTP 404 / 410 などアクセス不能な死んだ URL の有無。
  2. 逐語引用の忠実度: 原文からの勝手な英単語への置き換えや、不要な語句の挿入などの改変の有無。
  3. 網羅度・安定性: 抽出された候補の件数、および複数回試行における起点データの重複安定性。
  4. 実行時間と API コスト: タスク完了までの所要秒数、トークン消費量、およびプロンプトキャッシュ適用後の実質費用。

出力トークンのコスト構造と逐語引用の特性

Claude の API 料金体系において、全てのモデルで出力トークン単価は入力トークン単価の 5 倍 に設定されています5。

モデル入力単価（/MTok）出力単価（/MTok）プロンプトキャッシュ読出（/MTok）
Claude Opus 5.5$4.00$20.00$0.20
Claude Sonnet 5.5$2.00$10.00$0.10
Claude Haiku 5.5（100K以下）$0.10$0.50$0.01

LLM のハルシネーションに関する研究では、外部コンテキストからの断片コピー率が高いほど文脈不整合ハルシネーションが減少するという負の相関が報告されています6。一方で、LLM に長大な文章の逐語コピーを行わせることは、出力トークン単価が 5 倍である観点から極めてコスト効率が悪くなります。そのため、後述するように「無理にコピペを強制せず、要約や意訳に徹するプロンプト設計」が重要となります。

狭く深い調査におけるモデル特性の観察

局所的なドキュメント抽出および Web 検索を伴うファクトチェックタスクにおいて、Haiku 5.5 と Sonnet 5.5 の実機挙動を比較しました7。

タスク1: 本文抽出タスク（原典キャッシュ約40KB）

手元のキャッシュファイル（6本・約40KB）から客観的事実の行のみを抽出するタスクでの実測結果です。

  • Haiku 5.5: 所要時間 70 秒、費用 $0.0147、抽出事実 60 行。原典との突き合わせ照合（抜き取り 26 点）を実施した結果、事実の誤りは 0 件 でした。また、草稿が前提としていたコミットハッシュや Issue 番号、夏時間表記が原典ドキュメント内に存在しないことも正確に注記しました。
  • Sonnet 5.5: 所要時間 51 秒、費用 $0.204、抽出事実 96 行。

Sonnet 5.5 は抽出行数が多く所要時間も短い傾向がありましたが、費用は Haiku 5.5 の約 14 倍 に達しました（※Sonnet 側は 26 点の抜き取り照合までは実施しておらず、このタスクで直接比較可能なのは主に所要時間と費用差です）。

タスク2: Web 調査タスク（WebSearch・WebFetch あり）

外部ドキュメントを検索し、技術的主張の裏付けとなる URL と事実を収集するタスクでの実測結果です。

  • Haiku 5.5: 所要時間 104 秒、費用 $0.124、収集 URL 11 本。URL の疎通確認では 11 本中 10 本が正常（HTTP 200）で、残る 1 本（HTTP 401 の Stack Overflow ミラーサイト）についても「二次情報」である旨を明記していました。また、Git 公式ドキュメントの記述を原典どおりに引用し、ボット遮断により本文を取得できなかったページは「検索結果のみ」と書き分けました。
  • Sonnet 5.5: 所要時間 65 秒、費用 $0.421、収集 URL 16 本。しかし、収集した URL のうち 2 本がアクセス不能な死んだ URL（HTTP 404 が 1 本、HTTP 410 が 1 本）であり、存在しない 410（Gone）の URL を receive.autogc の根拠として記載していました。また、事前検証試行では原典で裏付けられない数値を事実欄に記載する事象も確認されました。

局所タスクで観測された逆転現象

狭く深い事実抽出において、Haiku 5.5 は死んだ URL を根拠にせず、原典にない前提や読めなかったページを「未確認」「検索結果のみ」と正確に申告しました。Web 調査タスクでの費用は Haiku 5.5（$0.124）が Sonnet 5.5（$0.421）の約 3 分の 1 であり、本文抽出タスクでは約 14 分の 1 に抑えられました。

この要因として、Haiku 5.5 はプロンプトの制約に対する忠実度が高く、自身の知識ベースによる過度な補完を行わないため、結果としてハルシネーションが抑制された可能性が推測されます。また、情報が不足した際に無理に回答を埋めず、フォールバックとして「未確認」と正直に申告する挙動が機能したと考えられます。

ただし、この実測は母数 n=2 の局所観察に基づくものであり、すべての調査タスクで常に Haiku 5.5 が Sonnet 5.5 を上回ると無制限に一般化できるわけではありません。

広域網羅の洗い出しにおけるモデル特性の観察

次に、探索空間が広く網羅性と安定性が問われるタスクとして、リポジトリ内の全記事を横断走査する Explore タスクにおいて、Haiku 5.5、Sonnet 5.5、Opus 5.5 の 3 モデルを同一プロンプトで比較しました7。

3モデルの実測データ比較

全公開記事の frontmatter と結論部を走査し、未解決の課題やテーマの穴を洗い出すタスクにおける複数回試行の実測結果です。

各モデルの観察結果

各モデルの挙動には、明確な性質の違いが現れました。

  • Haiku 5.5 の網羅性不足: コストは平均 $0.082 と非常に安価で逐語引用の改変もありませんでしたが、候補件数が 2〜8 件にとどまりました。4 本の試行を合わせても起点となった記事は延べ 14 本（複数回出現したのは 3 本のみ）であり、空間全体の網羅性が著しく不足していました。
  • Sonnet 5.5 の引用改変: 所要時間 56〜71 秒と最速で、候補件数も 13〜16 件と一定の網羅性を示しました。しかし、逐語引用において以下の 2 件の勝手な改変 が発生しました。
    1. 過去の ROI 検証記事 からの引用において、原文の「平均コスト変化」を「平均コストchange」と一部英単語化して出力した。
    2. 過去の監視コスト検証記事 からの引用において、原文『「監視コスト」を人間の分単位で』という記述に対し、原文にない「ログ」という単語を挿入した。
  • Opus 5.5 の圧倒的な網羅性と忠実度: 候補件数は 23〜24 件と最も多く、2 回の試行で起点となった記事の重複も 17 本と高い安定性を示しました。また、29 行におよぶ逐語引用において改変は 0 件 でした。費用は 1 回あたり約 $1.10、所要時間は約 190 秒を要しました。

広域探索で観測された逆転現象

狭く深い調査とは一転して、広大な情報空間の探索ではモデルの順位が逆転しました。Haiku 5.5 では全体の網羅が困難であり、Sonnet 5.5 は速度と件数に優れるものの細部の言い換え癖による引用改変を引き起こしました。漏れのない洗い出しと厳密な引用の一致を両立するためには、Opus 5.5 の高度な文脈把握能力が必要となりました。

なお、試行回数は Haiku 4本、Sonnet 2本、Opus 2本に限られており、Sonnet 5.5 を複数回実行して合算した場合に $1.10 より低コストで同等の網羅性と正確性を得られたかという反実仮想については計測を行っていません。

共通点と相違点の比較（モデル選定マトリクス）

3 つのモデルを同一条件下で比較検証した結果、モデルの優劣は固定的なピラミッドではなく、タスクが求める「局所の忠実性（狭く深い事実確認）」か「広域の空間把握（網羅的な探索）」かという作業の型によって順位が逆転することが実測により裏付けられました。

ベストプラクティスと推奨実装

実測結果を踏まえ、Claude Code サブエージェントの実務的な選定手順と設定実装例を提示します。

作業の型によるモデル選定フロー

サブエージェントにタスクを委任する際は、以下の判定基準でモデルを決定します。

  1. 入力が局所的で事実確認が主目的か？
    → model: haiku を採用。ファイル書き込みツールを禁止し、低コストで忠実な抽出を行わせる。
  2. 多数のファイルを横断走査し、漏れのない洗い出しが必要か？
    → model: opus を採用。Explore サブエージェントを上書きし、深い探索と正確な引用を担保する。
  3. 一般的なコード実装や中規模の要約処理か？
    → model: sonnet を採用。速度と知性のバランスを活かす。

コード例1: 狭く深い調査用カスタムサブエージェント設定

原典ドキュメントや Web 検索結果から正確な事実のみを抽出するため、model: haiku を指定し、書き込み系ツールを制限したサブエージェント定義です。

---
name: researcher
description: 渡された一次資料やWeb検索から、正確な事実・数値・引用を狭く深く調査する
model: haiku
tools:
  - Read
  - Glob
  - Grep
  - WebSearch
  - WebFetch
disallowedTools:
  - Write
  - Edit
  - Bash
---
あなたは事実調査に特化したリサーチャーです。
提供されたコンテキストや検索結果から客観的な事実のみを抽出してください。
未確認の数値や推測を事実に混ぜず、確認できなかった項目は明示的に「未確認」と報告してください。

model: haiku を指定することで、トークン単価を最小限に抑えつつ、過度な創作を抑制したファクトチェックを実現します。disallowedTools でファイル編集を遮断し、要約テキストのみを返却させます。

コード例2: 広域網羅探索用カスタムサブエージェント設定

リポジトリ全体の横断探索において、組み込み Explore のモデルを model: opus に固定するためのサブエージェント定義です。

---
name: Explore
description: コードベース全体やドキュメント群を横断走査し、網羅的な分析を行う
model: opus
tools:
  - Read
  - Glob
  - Grep
disallowedTools:
  - Write
  - Edit
---
あなたはコードベース全体の広域走査を担当するアナリストです。
指定された条件に合致するすべての候補を漏れなく洗い出し、重複を排除して構造化してください。
引用を行う際は、原文の表記を1文字も改変せずに逐語で保持してください。

プロジェクト固有の .claude/agents/Explore.md（またはユーザー設定 ~/.claude/agents/Explore.md）に配置することで、環境設定にかかわらず常に Opus 5.5 の網羅性を発揮させます。

コード例3: 当ブログパイプラインにおける実物設定抜粋

ハーネス設計の注意点

モデルの性能を正しく引き出すため、以下のハーネス設計を推奨します。

  • 親セッションの advisor 透過課金の確認: サブエージェントを実行する親セッションで /advisor が有効化されていると、意図しない上位モデルの呼び出しが透過的に発生し、費用が急増する可能性があります。計測・自動化スクリプト実行時は親セッションの設定を確認してください。
  • 出力トークンを抑制するプロンプト設計: 出力トークン単価は入力の 5 倍であるため、長大なコピペをさせず、要約・箇条書き・差分情報のみを出力させるプロンプトを設計します。
  • フォールバックの明示指示: 「分からない場合は未確認と書く」という指示をプロンプトに明記することで、小型モデルの正確性を高めることができます。

よくある質問（FAQ）

Q. サブエージェントに安いモデル（Haiku 5.5）を使うとハルシネーションが増えるのではないですか？

A. 一概に増えるとは限らず、作業の型によってはむしろ減少する傾向が観察されました。

当ブログの実測では、原典が与えられた狭く深い事実確認において、Haiku 5.5 は誤り 0 件で未確認事項を正確に書き分けた一方、Sonnet 5.5 は届かない死んだ URL を根拠としたり原典外の数値を記載したりしました。小型モデルは過度な知識補完を行わず指示に忠実に従う傾向があると考えられ、局所的なファクトチェックでは安価なモデルのほうが正確な結果を得られる場合があります。

Q. Claude Code の Explore サブエージェントは環境変数でモデルを変更できますか？

A. 環境変数 CLAUDE_CODE_SUBAGENT_MODEL 単体では Explore サブエージェントのモデルは変更されず、親セッションのモデルが継承されます。

Explore のモデルを確実に指定するには、プロジェクト固有またはユーザー設定のサブエージェント定義ファイル（~/.claude/agents/Explore.md）で model を指定するか、Agent 呼び出し時に per-invocation パラメータ（model: opus や model: haiku）を明示的に指定する必要があります。

Q. サブエージェントの API コストを抑えるために最も効果的なプロンプト設計は何ですか？

A. 出力トークンの生成量を抑える設計に徹することです。

Claude の API 料金体系では全モデルで出力トークン単価が入力単価の 5 倍に設定されているため、不要な逐語引用やファイル全体のコピーをさせず、要約・意訳や構造化データのみを出力させるよう指示することで、コストを大幅に削減できます。

まとめ

本記事の実機検証から得られた、サブエージェント選定の具体的な指針は以下のとおりです。

  • モデルの順位は作業の型によって逆転する: 狭く深い事実確認では Haiku 5.5 が Sonnet 5.5 より正確であり、広域の網羅探索では Opus 5.5 が不可欠である。
  • 「安いモデル＝雑」という固定観念を捨てる: 局所的な抽出タスクでは Haiku 5.5 の指示忠実性と余計な補完をしない性質が有効に機能し、コストも大幅に削減できる。
  • 広域探索ではフロンティアモデルの文脈把握力に投資する: 全体空間からの漏れのない洗い出しや引用の完全性を担保するには、Opus 5.5 への投資が正当化される。
  • ハーネスの交絡要因を排除して実機ログで検証する: 親セッションの advisor 透過課金やサブエージェントのモデル解決仕様を確認し、カタログスペックだけでなく実務環境の実機ログに基づいて選定を行う。
