Haiku を指定したのに費用の72%が Opus だった ── 子の claude -p に波及する advisor 設定と modelUsage 監査

Claude Code の Advisor Tool（/advisor）とは、一次実行モデル（Executor）が自律作業を進める中で、方針策定や手詰まり時に上位モデル（Advisor）へ自動的に相談して知能ブーストを得るツール機能です。また modelUsage とは、Claude Code の実行ログにおいて、1回のセッションやコマンド実行内で実際に消費されたモデルごとの入力・出力・キャッシュ読み取りトークン数および Web 検索リクエスト回数等の内訳を示すデータ構造です。

LLM を組み込んだサブエージェントや CLI による自動処理では、コスト最適化のために claude -p --model claude-haiku-5-5 のように小型・安価なモデルを明示指定して実行することが一般的です。引数で安いモデルを指定している以上、請求や API 費用もそのモデルの単価で抑えられていると思い込み、実際の課金内訳を確認していない開発者は少なくありません。

しかし、当ブログの運営リポジトリ（非公開）における実機検証において、Haiku 5.5 を指定して実行した Web 調査タスクの総費用（$0.4434）のうち、実に 71.74%（$0.3181） が指定外の claude-opus-5-5 による課金であり、同時に実行した Sonnet 5.5 指定（$0.2814）よりも Haiku 指定の方が高額になるという逆転現象が観測されました。

その後の対照実験により、対話セッション側で有効化されていた /advisor の設定が、同一環境から起動された子の claude -p プロセスへ暗黙に波及していた公算が極めて高いと考えられます。設定ファイル（settings.json など）上に明記がない状態であっても、親セッションの実行時状態が子プロセスに引き継がれ、意図しない上位モデルの呼び出しとトークン課金を招くリスクが潜んでいます。

本記事では、この逆転現象が発生した実測ログを modelUsage の内訳から解剖し、親セッションの /advisor 無効化による対照実験の結果を提示します。その上で、CLI 引数のモデル指定を過信せず、実行ログの modelUsage を機械的に監査するアサーションの導入と、独立した端末セッションによる実行環境の分離という実務的な対策指針を解説します。

過去に サブエージェントに小型モデルを指定した際の検証 や モデル比較における作業特性と順位逆転の検証 を扱いましたが、本記事ではモデル指定の前提そのものが親の設定継承によって崩れる経路と、その監査手法に焦点を当てます。

検証環境と調査スコープ

本記事で提示する実測データと検証結果は、当ブログの運営リポジトリ（非公開）における実機検証セッション（2026年11月6日実施）で記録された一次計測ログに基づく客観的事実です。

検証環境

  • 機材・OS: Apple Silicon Mac（macOS）
  • 実行ツール: Claude Code（非対話ヘッドレス実行フラグ -p を使用）
  • 対象モデル:
    • Claude Haiku 5.5（モデル ID: claude-haiku-5-5）
    • Claude Sonnet 5.5（モデル ID: claude-sonnet-5-5）
    • Claude Opus 5.5（モデル ID: claude-opus-5-5）
  • 計測期間: 2026年11月6日（当ブログの運営リポジトリの検証セッション）

調査スコープ

本調査は、以下の 3 つの検証ステップに沿って実施しました。

  1. ステップ1（ベースライン計測）: 外部ツール呼び出しを行わない（--tools ""）テキスト抽出タスクにおける Haiku 5.5 と Sonnet 5.5 の単価比較。
  2. ステップ2（逆転現象の観測）: Web 調査タスク（WebSearch および WebFetch ツールを使用）における Haiku 5.5 実行と、Opus 5.5 課金の混入内訳の解剖。
  3. ステップ3（対照実験と検証）: 親セッションでの /advisor 無効化操作と、別タスクにおける並列再計測による Opus 課金消失の実証。

客観的事実と推測の境界

調査の透明性を保つため、一次計測ログから確実に言及できる事実と、推測・考察の境界を以下のように厳格に定義します。

  • 書けること（観測された事実）:
    • テキスト抽出タスクにおいて、Haiku 5.5 は Sonnet 5.5 の約 1/14 の費用（$0.0147 と $0.204）で完了したこと。
    • Web 調査タスクにおいて、Haiku 5.5 を指定した実行の総費用 $0.4434 のうち、$0.3181（71.74%）が claude-opus-5-5 の課金であり、Sonnet 5.5 指定（$0.2814）を上回ったこと。
    • 親セッションで /advisor を無効化した後の対照実験において、Haiku 5.5 指定実行の総費用が $0.1244 へ低下し、claude-opus-5-5 の課金が完全に消失（0件）したこと。
    • ~/.claude/settings.json などの設定ファイル上に advisor の明示的な記述が見当たらない状態であったこと。
  • 書けないこと（推測・未検証事項）:
    • Opus 5.5 が起動された契機が、Haiku 5.5 の自発的な判断なのかプロンプト内の特定指示によるものかの完全な内部推論機序。
    • Sonnet 指定実行で副次的に Haiku が呼ばれ、Haiku 指定実行で Opus が呼ばれた Claude Code 内部のモデルルーティングコード（非公開のため）。
    • 対照実験において、プロンプト差やセッション永続化設定差以外の要因が一切関与していないという数学的証明。
    • 親セッションから子プロセスへ設定が伝播した Claude Code 内部の具体的な実装コード。

Advisor Tool の課金構造と設定の階層

Claude Code や Anthropic API における Advisor Tool の仕組みと、会話履歴の転送に伴う課金構造について整理します。

Advisor Strategy（二刀流戦略）の概要

Anthropic は、タスクの大半を安価で高速な小型モデル（Executor: Sonnet や Haiku）が主導し、手詰まり時や重要局面でのみ大型モデル（Advisor: Opus）に助言を求める「Advisor Strategy」を提唱しています。Anthropic の公式ブログによると、BrowseComp ベンチマークにおいて Haiku + Opus Advisor の組み合わせは単体スコア（19.7%）の 2 倍以上となる 41.2% を記録し、Sonnet 単体比で 85% 低コストを達成したと発表されています1。

API 仕様と透過呼び出しの機序

Advisor Tool は、API レベルではベータ識別子 advisor-tool-2026-03-01、ツール型名 advisor_20260301 として提供されています2。

Executor が advisor ツールを呼び出す際、クライアントから送信される server_tool_use ブロックの input は常に空となります。これを受け取ったサーバー側は、これまでの会話トランスクリプト全体（システムプロンプト、ツール定義、過去のやり取り、ツールの実行結果、途中生成テキスト）を引用コンテキストとして Advisor モデルへ自動転送します2。

Advisor の応答は advisor_tool_result ブロックとして Executor へ返されますが、Advisor 側の思考ブロック（thinking）は破棄され、結論のみが Executor に渡されます2。また、仮に Advisor のサブ推論でエラーが生じた場合でも、API リクエスト全体は中断されず、Executor は助言なしでそのまま自律処理を続行する耐障害設計となっています3。

課金構造の落とし穴

この「会話履歴全体の自動転送」こそが、意図しないコスト急増の主因となります。

  1. トップレベル usage に現れない課金: Advisor の消費トークンは、レスポンスのトップレベルにある usage フィールドには合算されず、usage.iterations 配列内の advisor_message として別枠で記録されます24。単純な usage 集計ロジックでは見落とされやすい構造です。
  2. プロンプトキャッシュの既定無効: API 仕様上、Advisor 側のプロンプトキャッシュ設定 caching は既定で null（無効）となっています2。キャッシュが無効な状態では、Advisor を 1 回呼び出すたびに、それまでの全会話履歴が Advisor モデルの基本入力トークンとして満額課金されます。
  3. 圧倒的なモデル単価差: Anthropic の価格表によると、各モデルの基本単価は以下のとおりです5。
    • Claude Haiku 5.5: 入力 $0.10 / MTok（100K超は $0.50）、出力 $0.50 / MTok（100K超は $2.50）、キャッシュ読出 $0.01 / MTok（100K超は $0.05）
    • Claude Sonnet 5.5: 入力 $2.00 / MTok、出力 $10.00 / MTok、キャッシュ読出 $0.10 / MTok
    • Claude Opus 5.5: 入力 $4.00 / MTok、出力 $20.00 / MTok、キャッシュ読出 $0.20 / MTok

Opus 5.5 の入力単価は Haiku 5.5（100K以下）の 40 倍に達します。そのため、セッション後半でコンテキストが数十万トークンに膨らんだ段階で Advisor が 1 回でも呼び出されると、それだけで Haiku 数十回分の費用が一瞬で消費されることになります。将来の料金改定でドル額が変わる可能性もあるため、コスト管理においては金額だけでなく、各モデルが消費したトークン数とキャッシュ読み出しの有無を直接監査することが極めて重要です。

設定の階層とヘッドレス実行（claude -p）のリスク

Claude Code の対話環境では、/advisor コマンドを実行することで Advisor として使用するモデルの選択や有効化・無効化の切り替えが可能です6。

しかし、設定ファイル（settings.json など）による明示的な管理と異なり7、対話セッション内で行った /advisor 設定のランタイム状態が、同一環境で実行されるスクリプトや子の claude -p プロセスに予期せず波及することがあります。CLI 引数で --model claude-haiku-5-5 を指定していても、親のランタイム設定が引き継がれれば、Haiku がバックグラウンドで Opus Advisor を透過的に呼び出してしまうリスクが生じます。

実測1：なぜ Haiku 指定が Sonnet より高くなったのか ── modelUsage の解剖

当ブログの運営リポジトリにおける一次計測ログから、この現象が実際に発生したセッションを解剖します8。

ベースライン：テキスト抽出タスクでの単価比較

まず、ツール呼び出しを伴わない（--tools ""）原典キャッシュ 6 本（約 40KB）からのテキスト抽出タスク（企画A）において、Haiku 5.5 と Sonnet 5.5 を同一プロンプトで比較しました。

  • Haiku 5.5: 総費用 $0.0147（実行時間 70秒、事実抽出 60行、誤り 0件）
  • Sonnet 5.5: 総費用 $0.204（実行時間 51秒、事実抽出 96行）

費用比は約 1:13.9（約 1/14） となり、ツールや Advisor が介入しない環境では、モデル単価の差どおりの大幅なコスト圧縮が確認できました。

Web 調査タスクでの逆転現象

続いて、Web 検索ツール（WebSearch および WebFetch）を使用する調査プロンプトを claude -p で並列実行したところ、以下の結果となりました。

  • Haiku 5.5 指定: 総費用 $0.4434（実行時間 136秒、16ターン）
  • Sonnet 5.5 指定: 総費用 $0.2814（実行時間 44秒、7ターン）

安価なはずの Haiku 5.5 を指定した実行が、Sonnet 5.5 指定の約 1.6 倍の費用を要するという完全な逆転現象が発生しました。

modelUsage の解剖

当時、親セッションで /advisor が有効化されていたことから、Web 調査中の思考や方針策定において Opus Advisor が自動呼び出しされた公算が高いと考えられます。

実測2：/advisor 無効化による対照実験と「見えない設定波及」

この課金混入の原因を検証するため、親セッションで /advisor を無効化した上で対照実験を実施しました8。

対照実験の実施と結果

まず、Claude Code の親セッション上で /advisor コマンドを実行し、Advisor disabled の状態へ切り替えました。その上で、別の調査プロンプト（企画B: 並列テスト調査タスク）を用いて claude -p による並列計測を行いました。

  • Haiku 5.5 指定実行:
    • 総費用: $0.1244（実行時間 104秒、16ターン）
    • modelUsage: claude-haiku-5-5 のみ（$0.1244、入力: 227,706、出力: 30,810、キャッシュ読出: 171,398、Web検索: 7）
    • claude-opus-5-5 の課金は 0 件となり完全に消失
  • Sonnet 5.5 指定実行:
    • 総費用: $0.4208（実行時間 65秒、15ターン、Sonnet $0.3454 + Haiku $0.0754）

親環境で /advisor を無効化した結果、Haiku 5.5 指定実行における Opus 課金は完全に消え去り、費用は $0.1244 と Sonnet 5.5（$0.4208）の約 30% に収まりました。本来期待されていた単価抑制が正常に再現された形です。

「見えない設定波及」の観察事実

この実験において最も注目すべきは、設定の波及経路です。

検証セッション中に ~/.claude/settings.json、~/.claude/settings.local.json、.claude/settings*.json などの設定ファイルを走査（grep -rn -i advisor）しましたが、ファイル上に advisor に関する明示的な記述は見当たりませんでした8。

にもかかわらず、対話セッション内での無効化操作が、同一環境から起動された子の claude -p プロセスに即座に反映され、Opus 課金が停止しました。この事実は、設定ファイルに永続化されていないメモリ上・セッション上のランタイム状態や環境変数が、子プロセスへ透過的に引き継がれていたことを示唆しています。

親セッションの設定状態を意識せずに claude -p を実行すると、親のコンテキストが意図せず波及し、見えないコスト漏洩を招くリスクがあると言えます。

実務での対策：modelUsage の自動監査と実行環境の分離

親セッションからの予期せぬ設定波及やすり抜けを防ぐため、実務で導入すべき対策を解説します。

予防と検収の設計思想

システム設計において、障害対策には「予防」と「検収」の 2 つの側面があります。

  • 予防（原因の空間に対するアプローチ）: /advisor を無効化する、設定ファイルを確認する、プロンプトに禁止事項を書くなど。しかし、ツール内部の仕様変更や未把握の環境変数、セッション状態の引き継ぎなど、原因の空間は無数に存在するため、予防だけで全てのすり抜けを防ぎ切ることは困難です。
  • 検収（結果の空間に対するアプローチ）: 実行後に吐き出された modelUsage を機械的に検査し、「許可されていない上位モデル（Opus 等）が含まれていないか」という結果の性質をアサートします。原因が何であれ、結果の空間で検知すれば予期せぬ課金爆発を確実に検出できます。

対策1：modelUsage の自動監査スクリプト

Claude Code の非対話実行（-p）で --output-format json を指定して実行結果を JSON 形式で出力・保存し、実行ログ内の modelUsage をパースして許可モデル以外の混入を即座に検知・停止する監査スクリプトを用意します。なお、Sonnet 指定時に内部で Haiku が正規に混ざるケースもあるため、許可モデルリストには柔軟に複数モデルを指定できるようにします。

まず、ヘッドレス実行で modelUsage を含む JSON 出力をファイルへ保存し、監査スクリプトへ渡すコマンド例です。

コマンド: claude -p による JSON 出力の保存と監査スクリプトの実行

# ヘッドレス実行で JSON 出力を保存
claude -p "Web 調査タスクを実行してください" --model claude-haiku-5-5 --output-format json > result.json

# 監査スクリプトを実行してモデル混入を検証（Haiku のみを許可）
python3 scripts/audit-model-usage.py result.json claude-haiku-5-5

--output-format json オプションを指定することで、セッション終了時に modelUsage や消費トークン内訳を含む構造化 JSON が標準出力に出力されます。これをリダイレクトで保存した上で、後続の監査スクリプトに渡します。

続いて、出力された result.json を検証する監査スクリプトの本体です。

ファイル: scripts/audit-model-usage.py

import json
import sys

def audit_model_usage(json_file_path: str, allowed_models: list[str]) -> None:
    with open(json_file_path, "r", encoding="utf-8") as f:
        data = json.load(f)

    model_usage = data.get("modelUsage", {})
    violations = []

    print("=== Model Usage Audit ===")
    for model_name, usage in model_usage.items():
        input_tokens = usage.get("inputTokens", 0)
        output_tokens = usage.get("outputTokens", 0)
        cache_read = usage.get("cacheReadInputTokens", 0)
        web_search = usage.get("webSearchRequests", 0)
        print(f"Model: {model_name}")
        print(f"  Input: {input_tokens:,}, Output: {output_tokens:,}, CacheRead: {cache_read:,}, WebSearch: {web_search}")

        if model_name not in allowed_models:
            violations.append(model_name)

    if violations:
        print(f"\n[ERROR] Disallowed models detected in modelUsage: {violations}")
        sys.exit(1)
    else:
        print("\n[OK] All models are within allowed list.")

if __name__ == "__main__":
    if len(sys.argv) < 3:
        print("Usage: python3 audit-model-usage.py <result.json> <allowed_model_1> [allowed_model_2 ...]")
        sys.exit(2)
    audit_model_usage(sys.argv[1], sys.argv[2:])

このスクリプトを CI パイプラインや定期バッチの事後フックに組み込むことで、想定外の上位モデル課金が発生した際に即座に異常終了させることができます。

対策2：実行環境の分離という運用方針

claude -p による同一プロセスツリーでの子プロセス呼び出しは、親セッションの環境状態がどこから波及しているか特定しにくいリスクを伴います。

実務上の運用対策として、親セッションから直接子プロセスを起動するのではなく、独立した新しい端末セッションを作成し、クリーンな環境でエージェントを走らせる方針が有効です。筆者の環境では端末管理ツール（Orca）を採用していますが、一般的な環境であれば tmux や独立したサブシェル（env -i 等）、コンテナ環境での隔離実行が該当します。

ファイル: scripts/run-isolated-agent.sh

#!/usr/bin/env bash
set -euo pipefail

# 親セッションから子プロセスとして叩くのではなく、
# orca terminal create で独立した新しい端末セッションを作成して実行する
orca terminal create --command "claude -p 'Web 調査タスクを実行してください' --model claude-haiku-5-5"

orca terminal create の --command オプションを用いて独立した端末プロセスを立ち上げることで、親セッションのメモリ状態や対話セッション固有の設定が波及するリスクを低減できます。ただし、設定がディスク上の共通設定領域に保持されている場合は端末を分けても引き継がれる可能性があるため、環境分離だけで安心せず、対策1の modelUsage 監査と併用することが肝要です。

よくある質問（FAQ）

Q. claude -p —model claude-haiku-5-5 を指定したのに Opus の課金が発生するのはなぜですか？

A. 親セッションで有効化されていた Advisor Tool（/advisor）の設定が子プロセスに引き継がれ、Executor である Haiku が作業中に上位モデルである Opus を Advisor として透過的に呼び出した公算が高いと考えられます。Claude Code では CLI 引数で指定したモデル以外の設定が親環境から波及することがあり、Advisor が呼び出されると会話履歴全体が Opus の入力トークンとして課金されます。

Q. settings.json に advisor の記述がない場合でも、子プロセスに影響しますか？

A. 影響する可能性が極めて高いことが、対照実験の結果から示唆されています。対話セッションで /advisor を操作した場合、設定ファイル（settings 系ファイル）に明示的な変更が記録されていない状態であっても、同一環境から起動された子の claude -p プロセスにその状態が引き継がれ、上位モデルの課金が発生または停止しました。

Q. サブエージェントや claude -p の実行で意図しない上位モデルの課金混入を防ぐにはどうすればよいですか？

A. 推奨される対策は、実行環境の分離と実行後のログ検収です。-p による子プロセス呼び出しを避け、orca terminal create 等を用いた独立した端末セッションでエージェントを起動することに加え、実行ログの modelUsage を機械的にパースして許可モデル以外のトークン消費を検知するアサーションを CI や運用ハーネスに組み込むことが有効です。

まとめ

  • CLI のモデル指定だけではコストは確定しない: --model 引数で小型モデルを指定しても、親セッションの設定（/advisor 等）が波及して上位モデルの課金が混入することがあります。
  • コストの成否は modelUsage のトークン内訳で監査する: 合計金額や引数にとらわれず、ログの modelUsage で各モデルが消費した入力・出力トークン数を直接確認する検収が不可欠です。
  • Advisor Tool は会話履歴全体を上位モデル単価で消費する: Advisor の入力トークンは会話ログ全体が転送されるため、セッションが長引くほど Opus 単価での課金が急増します。
  • 予期せぬ設定波及は独立端末（環境分離）と検収で防ぐ: claude -p による同一環境での子プロセス実行を避け、orca terminal create 等で独立した端末セッションを立ち上げるとともに、実行ログの modelUsage を自動監査することが有効な対策となります。
