設定キー改名で「対象0件・正常終了」とウォーターマーク前進を防ぐ設計——旧キー残存をエラーで検知する方法

設定ファイルや環境変数のキー名を改名（リネーム）して「旧キーはもう読まない」と決めたとき、手元の端末では問題なく動いても、設定の更新が遅れた別の端末で定期バッチが静かに空振りを続けることがあります。しかも厄介なのは、ジョブがエラーで止まるのではなく「処理対象が 0 件だった」として正常終了（終了コード 0）を返し続け、処理済みの印（ウォーターマーク）だけが現在時刻へ進んでしまうケースです。

増分バッチにおける 「対象 0 件のサイレント成功」 とは、設定キーの改名や互換打ち切りによって処理対象の抽出結果が空になり、ジョブ自体はエラーを出さずに正常終了する一方で、処理済みの印（ウォーターマーク）だけが現在時刻へ前進し、その間の入力データを取りこぼす現象を指します。

私は個人で開発・運用しているツール集（claude-skills）の自動振り返り機構 dream（dream.py）で、まさにこの事故を踏みました。許可リストの設定キーを claudeskills.retro-repo から claudeskills.dream-repos へ改名した際、設定同期用の dotfiles リポジトリ（.gitconfig）が未更新だった別の端末では、最後の正常実行（2026-10-27T16:41:45+09:00）から復旧（2026-11-11T10:20:14+09:00）まで約 2 週間（14 日 17 時間）の空白が生じました。先行した環境変数欠落によるスキップ期間を除いた設定キー不整合の期間（2026-10-29T10:26:58+09:00 〜 2026-11-10T04:09:33+09:00 の 11 日 17 時間、約 12 日間）だけでも、11 回中 11 回の実行が allowlist=0 transcripts=0 のまま正常終了し、watermark.json の read_until（処理済み位置を示すタイムスタンプ）だけが先へ進み続けていたのです。

これまでにも、外部コマンドの取得失敗が「0件」に化ける問題を扱った過去記事 では失敗が正常系の「0件」に潰れる構造を、launchd の自動 deploy が起動前に失敗しログに何も残らなかった過去記事 では定期ジョブが人目につかず静かに止まる構造を整理してきました。今回の事例がさらに根深いのは、ジョブが「正常終了」した結果としてウォーターマーク（read_until）が現在時刻へ書き換わり、後から設定を直しても過去の入力が「処理済み」扱いで再処理されなくなる（状態が汚染される）点にあります。

設定キーを改名して旧キーの読み取りを打ち切る環境では、「旧キーだけが残っている状態」を空設定（0 件成功）に混ぜず、ジョブ本体の実行時に失敗として通知し、ウォーターマークの更新を止める設計 が欠かせません。

設定キー改名の翌日から 11 回連続で「0 件成功」し、ウォーターマークだけが進んだ原因

dream（dream.py）は、許可リストに登録されたリポジトリの過去の会話ログ（Claude Code や Codex のトランスクリプト）をバックグラウンドで走査し、日次レポート（daily/）の生成や改善候補の起票を行う仕組みです。2026 年 10 月 27 日に骨格実装として導入された設定キー claudeskills.retro-repo は、翌 10 月 28 日に claudeskills.dream-repos へ改名され、あわせてドキュメントにも「改名前のキーは読まない。以前のキーで登録済みの端末は dream-repos で打ち直す」と明記されました。

ところが、設定を管理する dotfiles リポジトリの .gitconfig には、10 月 27 日に登録した旧キー claudeskills.retro-repo の 12 行（12 リポジトリ分）が改名されないまま残っていました。この .gitconfig を参照していた未更新の端末では、新キー claudeskills.dream-repos が 0 件、旧キー claudeskills.retro-repo のみが 12 件という状態が発生します。

改名前最後の正常実行（2026-10-27T16:41:45+09:00 完了、allowlist=1 transcripts=8、candidates: sessions=8 起票=6）の後、未更新の端末では 10 月 28 日〜29 日未明にかけて環境変数 COMPANY_HUB の欠落による run: skip 4 回（および hook: skip 1 回）が起きました。環境変数の設定を直した直後の 2026-10-29T10:26:58+09:00 から 2026-11-10T04:09:33+09:00 までの約 12 日間（11 日 17 時間）、run: start に進んだ 11 回中 11 回 がすべて allowlist=0 transcripts=0 となり、失敗記録（last-failure.json）を残さないまま正常終了（run: done）しています。以下は、最終回となった 11 月 10 日の実行ログです。

引用元: 筆者の検証セッションの記録（2026-11-10）

2026-11-10T04:09:33+09:00 run: start allowlist=0 transcripts=0 matched=[]
daily: skip (許可リストに当たる会話記録のディレクトリが無い。.complete は付けない)
candidates: skip (読む会話が無い。起票済みで読まない会話 0 本)
2026-11-10T04:09:33+09:00 run: done

毎回 run: done で終わるため、裏で動いている watermark.json の read_until は 10 月 27 日の時刻（2026-10-27T06:41:00+00:00）から順次書き換えられ、最終的には 2026-11-10T03:09:33+09:00（UTC 2026-11-09T18:09:33.432751+00:00）まで前進していました。2026 年 11 月 14 日時点の現存ファイル（mtime 基準）で計測すると、停止区間（2026-10-27T15:41:06+09:00 〜 2026-11-10T03:09:33+09:00）に対象端末で更新された Claude の会話ログは 180 本（allowlist=0 ランが始まった 2026-10-29T09:26:58+09:00 以降に限っても 155 本、復旧直前の 2026-11-11T09:20:14+09:00 まで含めると 199 本。Codex のセッションは同期間 0 本）にのぼり、一度も走査されないまま「読み取り済み」の境界を通過していました。

なぜエラーにならずに通り抜けてしまったのか。理由は git config の終了コード仕様と、呼び出し元の空配列フォールバック、そして無条件のウォーターマーク更新の 3 つが噛み合ったことにあります。

公式の git-config ドキュメントが定めるとおり、git config の取得コマンドは設定ファイル自体が構文不正な場合（ret=3）とは区別して、指定したセクションまたはキーが存在しない場合に終了コード 1（ret=1）を返します（なお、--get-all は現行ドキュメントでは DEPRECATED MODES に分類され、新しい git config get --all が推奨されていますが、キー不在時に非ゼロを返す挙動は共通です）1。さらに、.gitconfig 内に使われなくなった旧キーが残っていても、構文自体は正当なためエラーにはなりません1。

修正前の dream.py では、新キーが存在せず returncode != 0 になったとき、空リストをそのまま返す実装になっていました。以下は修正前の dream.py の許可リスト取得関数の抜粋です。

引用元: 個人で開発しているツール集（claude-skills）の dream.py

def allowlist_values():
    """git config --global の複数値を (読む値, 不正で読まない値) に分ける。無ければ両方空"""
    r = subprocess.run(["git", "config", "--global", "--get-all", ALLOWLIST_KEY],
                       capture_output=True, text=True)
    if r.returncode != 0:
        return [], []
    vals = [v.strip() for v in r.stdout.splitlines() if v.strip()]
    return [v for v in vals if valid_spec(v)], [v for v in vals if not valid_spec(v)]


def allowlist():
    """git config --global の複数値。無い・不正な値は読まない（無ければ dream は何も読まない）"""
    return allowlist_values()[0]

そして呼び出し元の run() は、allowlist() が [] を返しても例外を投げず、daily と candidates を skip して try ... except 節を抜け、末尾のウォーターマーク更新へそのまま到達していました。以下は修正前の dream.py の run() 末尾の抜粋です。

引用元: 個人で開発しているツール集（claude-skills）の dream.py

        except Exception as e:
            record_failure(sdir, t, "run", e)
            return 1
        write_json(os.path.join(sdir, CODEX_WINDOW), {"read_until": until.isoformat()})
        write_json(wm_path, {"last_success": t.isoformat(), "read_until": until.isoformat()})
        log(sdir, "run: done")
        return 0

until は現在時刻 t からセトル時間（1 時間）を引いた時刻です。つまり「新キーが未設定（または不在）」という状態がエラーに分類されないまま try 節を正常完了したことで、毎回 watermark.json の last_success と read_until が現在時刻ベースで上書きされ、return 0 で正常終了していました。

Google SRE Book（Chapter 26: Data Integrity）が指摘するとおり、データの欠損や破損、長期の利用不能はユーザーから見ればいずれも区別がつかず、スキーマ変更や設定変更が重なる環境では、サイレントな欠損を早期に検知する仕組み（Early Detection）が必要になります2。とりわけウォーターマークを持つ増分ジョブでは、「0 件の正常終了」が単なる一時的な空振りにとどまらず、状態ファイルの時刻を進めることで「後から設定を直しても過去のデータを二度と読まない」という不可逆な取りこぼしに直結します。

診断コマンドだけでは止まらない：実行本体で旧キー残存をエラーにして印を止める設計

この問題の厄介な点は、人間が手元で叩く診断用の仕組みだけを改善しても、バックグラウンドの定期実行は素通りし続けることです。

実は事故が発覚する 5 日前の 2026 年 11 月 5 日、私は「失敗を空・0 件に化かさない」という方針のもと、dream.py に一度修正を入れていました。具体的には、会話記録のルートディレクトリが読めない場合に allowlist_report() が返す件数を 0 ではなく "未確認" に改め、診断用サブコマンド（show_allowlist()）で無効な設定値が見つかったときに skipped と表示して終了コード 1 で知らせるようにしました。

しかし、この修正は人間が明示的に叩く診断サブコマンドと表示処理だけが対象であり、裏で定期実行される run() 本体が allowlist() から空リスト [] を受け取って正常終了するパスは塞がれていませんでした。診断用サブコマンド側がどれだけ親切に警告を出せるようになっていても、無人のバックグラウンド実行パス自体にガードがなければ、異変に気づくまで空振りは止まりません。設定の妥当性検査は、必ずウォーターマークを更新する実行本体の入口に置く必要があります。

11 月 10 日、対象端末で直近 7 日間の振り返り状況を確認した際に 10 月 27 日以降のレポートが 1 件も生成されていないことからようやく事態に気づき、同日中に run() 本体へ失敗ガードを組み込みました。まず、改名前の旧キーを定数 OLD_ALLOWLIST_KEY = "claudeskills.retro-repo" として定義し、旧キーの設定件数を数える old_key_count() を追加しました。以下は修正後の dream.py からの抜粋です。

引用元: 個人で開発しているツール集（claude-skills）の dream.py

def old_key_count():
    r = subprocess.run(["git", "config", "--global", "--get-all", OLD_ALLOWLIST_KEY], capture_output=True, text=True)
    return len([v for v in r.stdout.splitlines() if v.strip()]) if r.returncode == 0 else 0

その上で、run() の冒頭で新キーの allowlist() が空かつ old_key_count() が 1 件以上ある場合に、RuntimeError を送出するように変更しました。以下は修正後の dream.py の run() 内の抜粋です。

引用元: 個人で開発しているツール集（claude-skills）の dream.py

            repos = allowlist()
            old = 0 if repos else old_key_count()
            if old:
                # 黙って allowlist=0 で成功にすると、ウォーターマークだけ進んで読み損ねた会話が戻らない
                raise RuntimeError("許可リストが改名前の %s にだけある（%d 件）。%s で打ち直す"
                                   % (OLD_ALLOWLIST_KEY, old, ALLOWLIST_KEY))

run() の中で RuntimeError が投げられると、前述の except Exception as e: 節に捕捉されて record_failure(sdir, t, "run", e) が実行され、return 1 で終了します。その結果、後続の write_json(wm_path, ...) へ到達せず、ウォーターマーク（read_until）の更新が止まります。さらに、記録された失敗状態は次回の SessionStart フック実行時にユーザーへ通知されるため、放置されたまま何日も空振りを続ける経路が断たれました。

事後復旧にかかった手作業と、戻らなかった 8 日分の日次レポート

一度誤って進んだウォーターマークを後から巻き戻す復旧作業は、事前にエラーで止める設計に比べてはるかに重い手間がかかりました。

翌 11 月 11 日、対象端末の dotfiles にある .gitconfig の旧キー claudeskills.retro-repo（12 行）を新キー claudeskills.dream-repos（12 行）へ置き換え（2026-11-11T10:20:14+09:00 の実行では allowlist=12 transcripts=19 で動作）、あわせて watermark.json を watermark.json.bak に退避した上で、read_until を事故発生前の 2026-10-27T06:41:00+00:00 へ手作業で書き戻しました（10:22:48）。このとき last_success を直近時刻（2026-11-11T10:20:14+09:00）のまま残したため、24 時間以内はスキップするゲートが働き、実際に巻き戻した範囲の再走査が走ったのは 2026-11-13T22:36:44+09:00 の実行となりました。

11 月 13 日の回収実行では transcripts=214（既処理分を除いた候補抽出 sessions=194、起票=62）が処理され、停止期間中に通過していた会話ログからの改善候補抽出自体は事後に回収できました。しかし、日次レポート（daily/）の生成対象は仕様上「直近 7 日間（today - 7 .. yesterday）」に限定されていたため、11 月 11 日〜13 日の復旧実行でも 2026-10-27 〜 2026-11-03 の 8 日分の日次レポートは生成対象期間から外れ、未生成のまま 残っています。「後からウォーターマークを巻き戻せば済む」と考えていても、下流に時間窓（スライディングウィンドウ）を持つ処理がある場合は完全には元に戻りません。

設定キー移行における 3 つの設計方針の比較と適用限界

設定キーを改名する際の移行設計は、「① 無警告の互換打ち切り（空配列フォールバック）」「② 旧キーへの無期限フォールバック維持」「③ 旧キー残存時の明示的失敗＋ウォーターマーク停止」の 3 つに大別でき、状態を持つ増分バッチでは ③ を選択すべきです。

設計方針移行漏れ端末での挙動ウォーターマーク・状態の整合性コードの保守コスト適したケース
① 無警告の互換打ち切り（空配列フォールバック）「対象 0 件」として正常終了し続ける（サイレント成功）破損する（未処理のまま read_until 等が前進する）低（新キーのみを参照）状態を一切持たず、かつ単一環境で設定とコードを同時デプロイできる場合のみ
② 旧キーへの無期限フォールバック維持旧キーの値を読んで動作し続ける維持される（ただし設定の移行漏れに気づけない）高（旧キーの読み取り分岐とテストを永続的に抱える）外部ユーザー向け公開 API・CLI など、利用者の設定更新を強制できない場合
③ 旧キー残存時の明示的失敗＋ウォーターマーク停止明示的にエラー終了し、通知される保護される（例外によりウォーターマーク更新が止まる）中（旧キー名の定数とエラー送出ガードのみ保持）複数端末・複数環境で運用する増分バッチやデータパイプライン全般

方針 ① はコードこそ最小ですが、設定同期が遅れた端末で「0 件成功によるウォーターマーク汚染」を引き起こします。一方、方針 ② は設定の移行漏れを隠蔽して技術的負債を固定化させるため、自己管理下の複数端末・複数環境では、旧キーの残存を検知して即座に失敗させ、ウォーターマークを守る方針 ③ が安全性と保守性のバランスに優れています。

この判断は、プロトコル設計や大規模 API の運用規律とも整合します。IAB（Internet Architecture Board）が公開した RFC 9413（Maintaining Robust Protocols）は、「送信するものには保守的に、受信するものには寛容に」という Postel の法則（ロバストネス原則）を無批判に適用し続けると、不備のある入力が許容され続けて欠陥が温存される「病的なフィードバックサイクル（pathological feedback cycle）」に陥ると指摘し、未規定の条件に対して曖昧さを許さず致命的エラー（fatal errors）を返す「不寛容（intolerance）」を選ぶことで問題を早期に表面化させるべきだと論じています3。設定キー不在を無条件に「空リスト []」として受け入れてしまう実装は、まさにこのフィードバックサイクルの罠そのものです。

一方で、不特定多数の利用者が接続する大規模システムでは、Kubernetes Deprecation Policy が定めるように、即時削除ではなく十分な移行期間（例: Beta API で導入後最低 9 か月または 3 マイナーリリース、GA API は同一メジャーバージョン内で削除不可）を設け、保存済みデータのデコード互換性を維持しながら、Warning ヘッダや監査アノテーション、メトリクス（apiserver_requested_deprecated_apis）や CLI の警告出力によって段階的に廃止を進めるのが標準的です4。つまり、外部公開システムでは「段階的警告＋移行期間」、自分が管理する複数端末ツールでは「旧キー残存時の即時エラー＋ウォーターマーク停止」と、管理境界に応じて使い分けるのが合理的です。

今回のガード実装に残る 2 つの適用限界

11 月 10 日に入れた old = 0 if repos else old_key_count() というガードは実用的である一方、意図的に残した、あるいは構造上すり抜ける 2 つの限界があります。

  1. 真の初期状態（未設定端末）との非区別: 新キー claudeskills.dream-repos も旧キー claudeskills.retro-repo も 0 件である「まだ一度も許可リストを設定していない端末」では、repos が空かつ old == 0 となるため、仕様どおり allowlist=0 で正常終了しウォーターマークが進みます。「未設定端末では静かにスキップさせたい」という要件とのトレードオフです。
  2. 部分移行（新旧キー混在）のスルー: old = 0 if repos else old_key_count() という短絡評価のため、新キーに 1 件だけ設定を追加し、旧キーに残りのリポジトリ設定が残っているような「部分移行」の状態では、repos が非空になって old_key_count() が呼ばれず、旧キー側の設定が黙って無視されます。部分移行まで完全に防ぐなら、repos の有無にかかわらず old_key_count() > 0 を常時検査してエラーにする設計が必要です。

前提が変われば結論はどう変わるか：一般のバッチ・データパイプラインへの展開

今回の事例は git config を使った個人ツールの複数端末運用でしたが、前提条件が変われば対策の置き場所も変わります。

たとえば、コンテナイメージ内に設定ファイルとコードが同梱され、CI/CD で単一環境へアトミックにデプロイされる構成であれば、コードと設定の世代ズレ自体が起きにくいため、デプロイ前の CI バリデーションだけで防げる場合が多くなります。しかし、dotfiles で複数端末に同期する開発ツール、各エンジニアのローカル環境で動く CLI、あるいは設定ストア（ConfigMap や Parameter Store、DB 等）とワーカーのデプロイが非同期な分散バッチでは、「コードだけ先に新しくなり、設定が旧キーのまま残る時間窓」が発生し得ます。この前提では、ジョブ実行時のランタイム検査が最後の砦になります。

一般的なアプリケーションやデータパイプラインへ今回の教訓を展開する場合、次の 2 つの軸で設計を見直すのが有効です。

軸①：設定スキーマの境界で「未知のキー（旧キー）」を拒否する

git config のように必要なキーだけを個別に取得（プル）する方式では、ファイル内に旧キーが残っていても気づけません。設定ファイルを JSON / YAML / TOML などの構造化データとして読み込む場合は、パーサーやバリデータの設定で「スキーマに定義されていない未知のキー」をエラーとして弾くのが確実です。

  • Pydantic（Python）: ConfigDict の extra パラメータは既定値が 'ignore'（未知のフィールドを黙って無視）であるため、そのままでは旧キーが残っていてもエラーになりません。extra='forbid' を指定することで、未定義のキーが渡された際に ValidationError（type=extra_forbidden）を送出できます5。
  • JSON Schema: オブジェクトの検証では既定で定義外のプロパティが許容されるため、additionalProperties: false（または allOf 等の合成スキーマを跨いで未評価プロパティを禁止する unevaluatedProperties: false）を明示することで、旧キーの混入をスキーマ違反として検出できます6。
  • Go 標準ライブラリ（encoding/json）: json.Unmarshal は既定で構造体のフィールドに一致しない JSON キーを黙って無視しますが、json.Decoder に対して DisallowUnknownFields() を呼び出すことで、未知のフィールドが含まれている場合にデコードエラーを返せます7。

軸②：入力異常や品質チェック失敗時にウォーターマークを進めない

ストリーム処理やデータパイプラインのフレームワークでは、「処理対象が 0 件のとき」や「品質チェックに失敗したとき」にチェックポイントやウォーターマークをどう扱うかが明確に分離されています。

  • Apache Flink のチェックポイントとウォーターマーク: Flink の Checkpointing は処理状態と入力位置を永続化する仕組みであり、execution.checkpointing.tolerable-failed-checkpoints（setTolerableCheckpointFailureNumber）の既定値は 0（チェックポイント失敗を許容せず即座にジョブをフェイルオーバーさせる）となっています8。また、イベント時間ウォーターマークは入力データに基づいて生成されるため、入力が 0 件（アイドル状態）のソースからはウォーターマークが前進せず、アイドル状態に対処したい場合には WatermarkStrategy に .withIdleness(Duration.ofMinutes(1)) 等を設定して対処できる設計になっています9。
  • Dagster の Asset Checks: Dagster では @asset_check デコレータで品質検査を定義でき、blocking=True（例: @dg.asset_check(asset=orders, blocking=True)）を指定すると、検査が失敗した際に下流アセットのマテリアライズ（更新・進行）を自動的にブロックできます10。

自作の増分バッチで watermark.json のような状態ファイルを更新する際も、これらと同様に「設定・入力ソースの健全性チェックを通過したか」を確認し、通過した場合にのみウォーターマークを前進させるゲートを設けるべきです。

よくある質問（FAQ）

Q. 設定キーを改名（リネーム）した際、古いキーへのフォールバックをすぐ削除すると何が起きますか？

A. 設定ファイルが未更新の端末や環境で、新キーの取得結果が「未設定（空配列や 0 件）」となり、ジョブがエラーを出さずに「対象 0 件で正常終了」し続ける現象が起きます。特にウォーターマーク（read_until 等の最終処理時刻）を持つ増分バッチでは、空振りのたびにウォーターマークだけが現在時刻へ前進するため、後から設定を修正しても過去の入力データが「処理済み」とみなされて取りこぼされます。

Q. バッチ処理で「本当に処理対象が 0 件のとき」と「設定ミスで 0 件になったとき」はどう見分ければよいですか？

A. 処理対象の抽出結果（0 件）だけを見るのではなく、その前段にある「設定の健全性」をジョブ本体の入口で検査して見分けます。具体的には、新キーが空のときに改名前の旧キーが残っていないかをチェックし、残存時は例外で停止させる方法と、Pydantic の extra='forbid' や JSON Schema の additionalProperties: false などで未知・廃止済みの設定キー自体をパース時に拒否する方法が有効です。

Q. 診断用のサブコマンド（設定確認コマンド）で警告を出していれば、ジョブ本体のチェックは不要ですか？

A. 不十分です。診断用のサブコマンドは人間が異変に気づいて手動で実行しない限り呼ばれません。バックグラウンドで定期実行されるジョブ本体（run() 等）が設定不整合を素通りしてウォーターマークを更新してしまうと、無人のまま取りこぼしが拡大するため、必ずウォーターマークを更新する実行パスの中にガードを組み込む必要があります。

まとめ

設定キーの改名に伴う「対象 0 件のサイレント成功」とウォーターマーク汚染を防ぐために、増分バッチや定期ジョブの設計では次の 4 点を点検してください。

  • 設定キー改名時の空配列フォールバックを放置しない: 新キー不在を単なる「対象 0 件（[]）」として正常終了させると、設定未同期の端末でウォーターマーク（read_until 等）だけが前進し、時間窓を持つ下流処理で回復不能なデータ欠落を招く。
  • 旧キーの残存検査は診断コマンドではなく実行本体に置く: 人間が叩く確認用コマンドだけで警告を出してもバックグラウンド実行は止まらない。ウォーターマークを進める run() の入口で旧キー残存を検知して例外を送出し、印の更新手前で失敗記録へ落とす。
  • 部分移行（新旧キー混在）の死角を意識する: 「新キーが空のときだけ旧キーを調べる」短絡評価では、新旧キーが混在した部分移行を見落とす。厳密に防ぐなら新キーの有無にかかわらず旧キーの存在自体をエラーにするか、Pydantic（extra='forbid'）・JSON Schema（additionalProperties: false）・Go（DisallowUnknownFields）等でスキーマ定義外のキーを入口で拒否する。
  • 設定・入力の健全性が確認できるまでウォーターマークを進めない: Flink のアイドル制御や Dagster の blocking=True と同様、自作バッチでも「検証通過」をウォーターマーク更新の必須条件として設ける。

バッチ処理やデータパイプラインの設計・運用改善、設定管理の仕組みづくりでお困りの際は、コンタクトフォーム よりお気軽にご相談ください。
