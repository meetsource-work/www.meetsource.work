正しい指摘が「別の文献に同じ事実がある」という理由で誤検出に降格されていた ── 所在の検査と事実の検査は別物

LLM を活用した自律執筆やコード生成のパイプラインでは、生成物のハルシネーションや不正確な記述を防ぐために、検証役（Verifier や LLM-as-a-Judge）を配置する多段構成が一般的になりつつあります。

しかし、検証役の過剰な指摘（偽陽性 / False Positive）を減らそうとして設けた「誤検出フィルタ」や「降格ルール」そのものが誤作動し、本来止めるべき正当な指摘を握りつぶしてしまう失敗も起こりえます。

自社のブログ自動生成システムでも、「正しい指摘が誤検出として降格され、誤った脚注がそのまま公開記事に残る」というインシデントが起きました。

この失敗が示しているのは、「世の中の事実関係が合っているか」という事実の検査と、「指定された文献の指定された場所に書いてあるか」という所在の検査を混同してはならないということです。

Citation Attribution（引用帰属）とは、生成された主張が指定された参照文献の内容から論理的に直接導出・検証可能である性質のことです。

以前の記事『サブエージェントの「高」判定を、そのまま信じない ── 一次情報で再評価して進行可を出した事例』1 では、上位判定処理が検証役の警告を慎重に精査する重要性を論じました。しかし、その判定基準を誤ると、公開記事『「取得成功」判定が文字化けを見逃す ── URL取得ゲートの死角と決定論的フォールバック』2 で発生したように、原典に無い所在を示す脚注を世に出してしまうことになります。本記事では、この失敗の顛末と、そこから得られたパイプライン設計の教訓を共有します。

何が起きたか ── 正しい指摘が「誤検出」として握りつぶされた日

自社で運用しているブログ自動執筆パイプラインには、設計書の事実関係を懐疑的な読者の視点で事前検証する検証工程があります。この工程では、事前に取得・保存した原典の本文（本文キャッシュ）を検証役に読ませて、脚注の主張と照合させています。

ある日の検証プロセスにおいて、検証役を務めるサブエージェントが、ある技術記事の草案に対して「RFC 9110 Section 8.3.1 のキャッシュ本文欠落」という指摘を行いました。脚注は charset 省略時のデフォルト規定（旧 ISO-8859-1）の廃止を RFC 9110 §8.3.1 の内容として挙げているのに、渡された本文キャッシュにはその記述が見当たらない、という指摘です。

ところが、検証役の指摘を取りまとめる上位の判定処理（オーケストレーター）は、この指摘を「誤検出」として降格し、パイプラインの進行を許可してしまいました。

当時の検証記録には、降格の理由として次の文言が残されていました。

RFC 9110（STD 97）のキャッシュは抽出ツールの範囲により Section 6.4 付近のみ取得されていたが、RFC 7231 Appendix B（中略）に旧デフォルト ISO-8859-1 削除の事実が完全に記録されており、RFC 9110 Section 8.3.1 はその後継仕様として正しく引用されているため事実関係の誤りではない。

つまり、「RFC 7231 という別の文献に同じ事実が書かれており、RFC 9110 はその後継仕様なのだから、事実関係として間違っていない。したがって、該当記述が見当たらないという指摘は検証役の過剰反応（誤検出）である」と解釈したのです。

しかし、後日のパイプライン振り返りにおいて、RFC 9110 の全文（10,785行）を取り直して精査したところ、驚くべき事実が判明しました3。

Section 8.3.1（Media Type）にも Section 8.3.2（Charset）にも、charset の既定値廃止に関する記述は一切存在しなかったのです。全文 10,785 行の中で ISO-8859-1 という文字列が出現するのは、フィールド値の歴史的背景を解説した 1,599〜1,600 行目と、参考文献一覧の 9,533 行目だけでした。

一方、旧デフォルトの削除は、RFC 7231 Appendix B（5,069行目）に明記されています4。

The default charset of ISO-8859-1 for text media types has been
removed; the default is now whatever the media type definition says.

検証役の「RFC 9110 Section 8.3.1 に記述がない」という指摘は完全に正しく、上位判定処理による「後継仕様だから事実関係の誤りではない」という降格判断こそが誤りだったのです。結果として、公開された記事の脚注には「Section 8.3.1 における Content-Type メディアタイプ定義と、charset 省略時のデフォルト規定（旧 ISO-8859-1）廃止の仕様」という、原典に存在しない所在が記載されたまま読者の目に触れることになりました。

手元でこの原典照合を再現したコマンドと実行ログは次のとおりです。

# RFC 9110 全文（10,785行）の取得と ISO-8859-1 出現箇所の確認
curl -s -o /tmp/rfc9110.txt https://www.rfc-editor.org/rfc/rfc9110.txt
grep -n -i 'ISO-8859-1' /tmp/rfc9110.txt

# RFC 7231 Appendix B における既定文字セット削除規定の確認
curl -s -o /tmp/rfc7231.txt https://www.rfc-editor.org/rfc/rfc7231.txt
grep -n -A 1 'The default charset of ISO-8859-1' /tmp/rfc7231.txt

1599:   Historically, HTTP allowed field content with text in the ISO-8859-1
1600:   charset [ISO-8859-1], supporting other charsets only through use of
9533:   [ISO-8859-1]
5069:   The default charset of ISO-8859-1 for text media types has been
5070-   removed; the default is now whatever the media type definition says.

所在の検査と事実の検査は別物 ── 問いのすり替えが起きる構造

なぜ上位の判定処理は、検証役の正しい指摘を「誤検出」と誤認してしまったのでしょうか。その本質的な原因は、判定処理の中で発生した 「問いのすり替え」 にあります。

読者が技術記事の脚注をクリックしてリンク先の文献を開く目的を考えてみてください。読者が求めているのは、「その文献の、そのページ・その節に、著者が述べている根拠が本当に書かれているか」を自分の目で確かめること（検証可能性: Verifiability）です。

このとき、検証役と上位判定処理の間で交わされていた「問い」に決定的なズレが生じていました。

  • 検証役が発していた問い: 「指定された文献（RFC 9110 §8.3.1）に、その主張（charset 廃止）が存在するか？（＝ 所在の検査）」
  • 上位判定が答えてしまった問い: 「世の中にその事実が存在するか？ 別の文献（RFC 7231）にあるから主張としては合っている（＝ 事実関係の検査）」

問いが「所在」から「世の中の真偽」へとすり替わったことで、「指定された文献に記述がない」という致命的な所在エラーが、「世の中に存在する事実だから問題ない」と不可視化されてしまったのです。

この現象は、学術的な自然言語処理や引用評価の研究でも厳密に議論されています。

Google Research が提案した AIS（Attributable to Identified Sources）フレームワーク5 は、生成された文が特定された情報源に支えられているか（帰属）を測る枠組みです。論文は発話の「事実性（factuality）」を判定することを避け、事実性を評価するには情報源の質を見るような別の評価手法を AIS と組み合わせる必要がある、という立場を取っています。

また、Princeton NLP が開発した引用付きテキスト生成のベンチマーク ALCE（Automatic LLMs’ Citation Evaluation）67 においても、文単位で文献が主張を含意（entail）しているかを測る Citation Recall と並び、不要な引用や無関係な文献を引いていないかを測る Citation Precision を測定しています。ELI5 データセットでは、最良のモデルでも 50% の割合で引用による裏付けが完全ではなかったと報告されています。

さらに、Future AGI による引用評価ルーブリックの分析8 では、実務における典型的な死角として 「The right document, wrong page or wrong claim（文献自体は合っているが、指定されたページや節に主張が存在しない）」 という失敗パターンが警告されています。今回のインシデントは、まさにこのパターンに該当していました。

Michael Brenndoerfer 氏が論じているように9、引用の本質は読者に対する検証可能性（Verifiability）を提供し、システムへの信頼を確立することにあります。別の文献に事実があるからといって、間違った文献へのリンクを正当化することは決してできません。

多段検証において混同されがちな 2 つの品質基準は、以下のように検査の対象と読者価値が根本から異なります。

観点事実関係の検査（Factuality）所在・引用帰属の検査（Citation Attribution）
検証の問い「その主張は、世の中の客観的事実として真か？」「その主張は、指定された文献の該当箇所に書かれているか？」
判定の対象主張内容そのもの（世界の真偽）主張と引用元テキストとの論理的対応関係（含意・所在）
典型的な欠陥ハルシネーション、偽情報の生成誤帰属（Misattribution）、原典不一致、偽りの裏付け
読者への影響誤った知識や前提を信じ込んでしまう脚注を辿っても根拠を確認できず、信頼が失墜する
「別文献にある」の意味主張の正しさを補強する正当な根拠所在エラーを解消する答えには一切ならない

事実がいくら正しくても、読者が提示されたリンクを辿って記述を見つけられなければ、その記事の検証可能性はゼロになります。

誤検出削減の裏にあるトレードオフ ── 偽陽性と見落としの境界線

なぜパイプラインの設計者は、検証役の指摘を安易に降格するルールを作ってしまうのでしょうか。

その背景には、実務で避けがたい「誤検出削減の強い圧力」があります。LLM-as-a-Judge や自動検証エージェントは、時に過度に保守的で重箱の隅をつつくような指摘を大量に出力します。これらをすべてブロッカーにしてパイプラインを停止させると、人間や修正エージェントの手戻りコストが跳ね上がります。

その結果、「多少の食い違いは中へ降格して進行可にする」「別の文献に似た記述があれば良しとする」といった妥協的なフィルタを設ける誘惑に駆られます。

もちろん、厳密な仕様検証が求められる技術ドキュメントやコード生成ではなく、即時性が最優先される会話ボットやカジュアルな要約など、読者検証可能性の優先度が低いユースケースであれば、所在検査の厳格化は過剰な手戻りコストを生むトレードオフになり得ます。

しかし、公開成果物の検証可能性を担保すべきパイプラインにおいて、誤検出（偽陽性 / False Positive）を減らすためにフィルタや降格条件を安易に緩める操作は、本来止めるべき本物の欠陥を見逃す「見落とし（偽陰性 / False Negative）」のリスクと完全に表裏一体です。

さらに深刻なのは、メトリクスの歪みです。正当な指摘を「誤検出」の枠組みへ放り込んでしまうと、検証役の真の精度（False Positive Rate）の測定が狂い、プロンプトやモデルの健全な改善サイクルが機能しなくなります。自社の企画ごとの検証記録 103 件を走査したところ、「別の文献に同じ事実がある」を理由に誤検出として降格した事例は今回の 1 件だけでした。ただし数えられるのは誤検出として記録された降格だけで、記録されないまま素通りした見落としはこの数に含まれません。

LLM-as-a-Judge の信頼性をどう確保するか（一貫性の向上やバイアスの緩和）はサーベイ10の中心的な問いです。LLM-as-a-Judge が評価するのは出力の妥当性という一層に限られるという整理11や、ジャッジの判定を少量の人手ラベルと突き合わせて一致度を測る手法12も示されています。降格ルールも同じく、「何を誤検出とみなし、何をブロッカーとして残すか」の境界を、自分のパイプラインで明示的に決めておく必要があります。

よくある質問（FAQ）

Q1: 事実は正しいのに、なぜ別の文献を理由に指摘を降格してはいけないのか？

A1: 読者が脚注を検証する行為は「その文献のその場所」を起点とするためです。別の文献に事実が存在していても、読者が開いた原典に記述がなければ「虚偽の引用」と受け取られ、記事全体の信頼性が失われます。事実の正しさを理由に指摘を握りつぶすのではなく、出典を正しい文献へ差し替えるべきです。

Q2: 本文キャッシュが欠けている場合、Verifier の指摘はどう扱うべきか？

A2: 推測で「キャッシュ欠落による誤検出」と決めつけて降格してはなりません。まずは原典の全文を取り直して決定論的に記述の有無を確認し、確認できない場合は指摘事項として残して出典を修正するのが安全です。

検証パイプラインの降格条件を再設計する ── 2つの修正ルール

このインシデントを受け、自社パイプラインでは 2 段階の是正措置を実施しました。

第 1 段階: 記事成果物の修正

公開記事とその草案から RFC 9110 への言及を除去し、正しく廃止規定が書かれている RFC 7231 のみで支える形に修正しました。同期検査スクリプトを実行し、公開記事と草案の間に不一致が 0 組であることを確認して修正を完了させました。

第 2 段階: 検証スキルの降格ルールの改定

検証工程の運用手順に、以下の 2 つの降格禁止ルールを明文化しました。

  1. 「別の文献が同じ事実を支える」ことは降格理由にならない: 指摘が問うているのが「その出典の本文に主張があるか（所在）」である場合、事実が別の文献で正しいことは答えになりません。所在の誤りは、誤検出として捨てるのではなく、出典の差し替えや削除で閉じる局所修正として扱います。
  2. 「本文キャッシュの欠け」を理由に推測で降格しない: キャッシュが原典の一部しか保存していない疑いがある場合は、想像で格下げする前に原典を取り直して該当箇所を精査します。取り直せなければ降格せず、未確認として指摘事項に残します。

改定した検証ルールの該当箇所は次のとおりです（社内の管理番号と内部ツール名は伏せています）。

**次の2つは降格の理由になりません**（「RFC 9110 §8.3.1 のキャッシュ本文に主張が無い」という正しい指摘が下の2つを理由に降格され、原典に無い所在を示す脚注のまま公開された）:
- **「別の文献が同じ事実を支える」** — 指摘が問うているのがその出典の本文にその主張があるか（所在）なら、事実が別の文献で正しいことは答えになりません。所在の誤りは、出典の差し替え・削除で閉じる指摘として扱います（局所修正で閉じるなら `## その場で解消した指摘` へ）。
- **本文キャッシュの欠け** — キャッシュが原典の一部しか保存していない（抽出範囲の都合など）、または保存されていないために主張が見つからない場合は、降格する前に原典を取り直して該当箇所を読み、その本文で判定します。取り直せなければ降格せず、確かめられなかったものとして `## 指摘事項` に残します。

将来的に LLM のコンテキスト長がさらに拡大し、キャッシュ抽出ツールを介さず常に原典の全文を直接参照できるようになれば、「キャッシュ欠落」に起因する摩擦は減少するかもしれません。

しかし、「別の文献にあるからいいだろう」という問いのすり替えは、モデルの性能向上だけでは解決しません。検証ルールとして明示的にガードレールを敷き続ける必要があります。

まとめ ── 誤検出フィルタを点検する

検証役の指摘を格下げする操作は、パイプラインのノイズを減らす便利な道具に見えますが、一歩間違えれば、原典に無い所在のような誤りを素通りさせる抜け穴になります。

健全な多段検証パイプラインを運用するために、以下の 4 つの命題を現場の判断基準として提案します。

  • 所在の検査と事実の検査を明確に分離する: 読者が脚注に求めるのは「世界の真理」ではなく「その文献のその場所に根拠があるか」という検証可能性です。
  • 「別文献にある」を理由に所在指摘を降格しない: 別の文献に事実があるなら、指摘を誤検出として捨てるのではなく、出典をその文献へと差し替える修正を行うべきです。
  • キャッシュ欠落を推測で片付けない: 情報源のテキストが手元にないときは、想像で格下げせず、原典を取り直して決定論的に白黒をつけます。
  • 誤検出の削減は見落としのリスクと背中合わせである: 降格ルールを緩めるほど偽陰性（本物の欠陥の見逃し）が増えます。自社の誤検出フィルタが正当な指摘を握りつぶしていないか、定期的に点検する姿勢が不可欠です。

AI エージェントを活用した多段検証パイプラインの構築、LLM-as-a-Judge の精度改善、ハルシネーションや引用精度の品質ゲート設計に関するご相談は、コンタクトフォーム よりお気軽にお問い合わせください。
