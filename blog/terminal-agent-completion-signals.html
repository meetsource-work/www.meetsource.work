ラベルが進んだのにコミットが無い ── 端末越しの AI エージェント自動化で、完了を何で判定するか

GitHub Issue のラベルが期待どおりに貼り替わったため監視スクリプトが終了したにもかかわらず、端末画面をのぞき込むと、エージェントはまだ git commit を実行している最中でした。10 秒も待たずに次のステージを起動していたら、未コミットの変更を抱えたまま別端末が動き出すところでした。

端末越しのエージェント自動化における完了判定とは、別の端末で動く AI エージェント CLI のステージが、成果物を残した状態で終わったことを、監督側が外から確かめる処理です。つまり「エージェントが手を止めた」ではなく「やるべきことが記録に残った」を確かめる処理です。

筆者はこのブログの運営リポジトリ（非公開。以下、運営リポジトリ）で、企画から調査、設計、執筆、校閲までをステージごとに分けて自動実行する仕組みを動かしています1。監督役の Claude Code が、端末とワークツリーを統合する基盤である Orca（orca terminal wait / orca terminal read / orca terminal send）で新しい端末を開き、Antigravity CLI（agy）を起動してスキル名を送り、Python の監視スクリプト stage.py が GitHub Issues のラベルと端末画面を見張る構成です1。

2026 年 11 月 13 日（UTC）の自動化セッションの記録（以下、セッション記録）で、ある記事を企画から校閲まで順に回した際、単一信号による判定で 2 つの破綻に直面しました1。1 つは Issue のラベルが git commit より先に進み、未コミットのまま次ステージへ先走りかけたこと。もう 1 つは、親エージェントがサブエージェントの完了を待つ間も入力欄が空いて tui-idle（Orca が入力欄が空いたと判定した状態）になり、待機と停止を画面から区別できなかったことです1。

そこで筆者は、完了判定を「ラベルの変化＋ターン終了＋コミットの確認」の 3 点の組に組み直し、tui-idle が続いたときは閾値を延ばすのではなくエージェント本人に状態を尋ねる催促を 1 回だけ送り、2 回目は人間に渡す運用に改めました。以下では、2 つの観測記録と改修したコードをもとに、そう組み直した理由と残ったトレードオフを述べます。

ラベルが進んだ時点で、端末ではまだ git commit が走っていた

Issue のラベルは「ステージが終わった」ことではなく、「エージェントがラベルを付け替えた」ことしか示しません。運営リポジトリの企画ステージで使う手順書自体が、手順 9 でラベルの貼り替えを指示し、報告前のコミットを手順 11 に置いています。ラベルを状態の記録に使い、成果物は Git コミットで残す設計では、ラベルが先に進むのは手順どおりの動きです。

なお、GitHub 自身も Issue のサイドバーにコーディングエージェントのセッション状態（queued / working / waiting for review / completed）を表示する仕組みを提供しており、Issue 上にはラベルとは別に作業の進み具合を表す状態が存在します2。

セッション記録にある企画ステージの自動実行では、14:31:23Z に作業を開始してから 2 分 24 秒後の 14:33:47Z に、ラベル一致を条件にしていた当時の作業用監視スクリプトが exit code 0 で終了しました1。ところが直後の 14:33:50Z に端末画面を確認すると、Issue ラベルはすでに期待どおり付いている一方で、画面の末尾では git add と git commit が実行中のままでした1。

目的: ラベル一致で監視スクリプトが終了した直後の端末画面の状態を示します。

引用元: 筆者の自動化セッションの記録（2026-11-13、UTC）

labels: ['blog:planned'] OPEN
...
> /blog-plan #335
● Bash(git add specs/blog-posts/ai-agent-false-positive-completion/ && git add -u...) (ctrl+o to expand)
⣟  Running command...

この時点で監督は未コミットのまま次のステージを起動せず、直後の 14:33:56Z に作業用の stage.py をその場で修正し、14:33:59Z にターン終了とコミットの完了を確認してから次の調査ステージへ進みました1。つまり未コミットのまま先走ったのではなく、画面を確認したことで先走りかけたのを止めた形です。

目的: ラベル一致の後もエージェントのターン終了まで待つよう組み直した監視ロジックを示します。

引用元: 運営リポジトリの stage.py（後でスキルとしてまとめた版）

    if (want and want in ls) or st == "CLOSED":
        # agy はコミットより先にラベルを進める。ターン終了まで待つ
        for _ in range(5):
            wait_idle(120000)
            if not any("Running" in l for l in screen()[-8:]):
                break
            time.sleep(20)
        break

ここで wait_idle は orca terminal wait --for tui-idle を呼ぶ関数、screen() は orca terminal read --screen で取得した画面末尾行を返す関数です。"Running" は agy の実行中表示に合わせた文字列であり、CLI が違えば変わります（後の章で再訪します）。ループで待つのは最大 5 回までで、Running が残っていてもループを抜けます。この待機だけでターン終了を保証するわけではなく、最終的な判定は後段のコミット確認に置いています。また、コード中の「agy はコミットより先にラベルを進める」というコメントは当時の監督側の理解であり、実態としては前述のとおり手順書の順序に由来する動きでした。

後でスキルとしてまとめた運用手順（以下、運用手順）では、監視スクリプト終了後の完了条件として、git log --oneline -1 に当該ステージのコミットが存在すること、および git status --short が空であることの確認までを明記しています1。

サブエージェントを待つ間も入力欄は空く：閾値を上げても、待機と停止は画面から区別できなかった

agy は、親エージェントがサブエージェントの完了通知を待つ間もプロンプトの入力欄が空き、Orca からは tui-idle と判定されます1。非同期の待ちで入力欄が空いて見える現象自体は、Monitor やバックグラウンドの Bash 実行を例に 端末画面スクレイピングの記事 で扱ったため、ここでは繰り返しません。同記事で触れた催促は、待っていただけのエージェントへ不要な催促を送ってしまった側の事例でした。

これに対し、同じ記事の校閲ステージ（15:13:25Z 開始）では逆の局面が起きました。当時の作業用スクリプトは、画面末尾 15 行が 2 回連続で変化しなければ STALLED（筆者の監視スクリプトが「画面が idle のまま変わらない」と判断して監視を打ち切るときの出力で、Orca の公式状態ではありません）を出して終了する作りでした。開始から 3 分 1 秒後の 15:16:26Z、監視スクリプトは 1 回目の STALLED で停止しました1。

目的: 1 回目の STALLED 出力時に端末画面へ出ていた待機メッセージを示します。

引用元: 筆者の自動化セッションの記録（2026-11-13、UTC）

STALLED (idle, screen unchanged)
...
  proofreader と reader-reviewer の校閲結果を待っています。
  proofreader からの指摘（13件）を受領しました。引き続き reader-reviewer の完了を待っています。

画面の末尾には、校閲用サブエージェントの完了を待っている旨が表示されていました。当時の監督は早すぎる打ち切りと判断し、15:16:40Z に作業用スクリプトを編集してラベル待ちステージの閾値を画面不変 10 回に引き上げ、15:16:43Z に同じ端末の再監視を始めました1。

目的: ラベルを待つステージだけ画面不変の閾値を 10 回に引き上げた停止判定を示します。

引用元: 運営リポジトリの stage.py（後でスキルとしてまとめた版）

    cur = screen()[-15:]
    still = still + 1 if cur == prev else 0
    prev = cur
    # agy はサブエージェント待ちでも idle になるので、ラベルのあるステージは長めに見る
    if still >= (10 if want else 2):
        print("STALLED (idle, screen unchanged)")
        break

この抜粋は、観測当日に閾値を 10 へ上げた後の形を取り込んだ運用版です。画面が tui-idle のままなら wait_idle はすぐ返るため、ループ 1 周の所要時間はほぼ抜粋外の time.sleep(30) に等しくなります。閾値 10 回は 5 分前後の猶予にすぎず、実際に再監視開始から 5 分 22 秒後（校閲ステージ開始から 8 分 40 秒後の 15:22:05Z）に再び STALLED で打ち切られました1。

そこで開始から 8 分 50 秒後（15:22:15Z）、監督は orca terminal send を使って、状態を確認し、終わっていれば続け、失敗していれば再委任するようエージェントへ催促を 1 回送りました1。すると 40 秒後の画面には次の応答が出ました1。

目的: 1 回の催促に対してエージェントが返した応答と再委任の記録を示します。

引用元: 筆者の自動化セッションの記録（2026-11-13、UTC）

● Agent(reader-reviewer: Reader and Structure Reviewer)(次のファイルを Read で読...) (ctrl+o to expand)
  前回の reader-reviewer サブエージェントは未実行のまま停止していたため終了し、新たに reader-reviewer
  を再委任しました。完了通知を待っています。

この再委任の後、催促から 4 分 56 秒後（校閲ステージ全体では 13 分 47 秒後の 15:27:12Z）にステージは完走しました1。

ここで見落とせないのは、1 回目の STALLED（開始 3 分 1 秒時点）で委任先がすでに止まっていたのか、それとも正常稼働中に閾値 2 回で早すぎる打ち切りをしたのかを、記録からは切り分けられない点です。委任先が未実行のまま止まっていたという点も、サブエージェント側の状態ログが残っているわけではなく、催促に対する親エージェント本人の申告によるものです。ただ、どちらの状態にあるかを画面の tui-idle は区別してくれません。そのため、閾値を 2 から 10 に上げても、待機と停止を見分ける手段にはなりませんでした。

「画面の idle 表示は会話ターンの状態であって、タスク全体の完了ではない」という線引きは、tmux 上のエージェントを監視する他のツールでも共有されています。たとえば tmux-agent-pulse の README は、idle 表示は会話の状態を示すものであってプロジェクトの完了を示すものではないと明記し、内部の子エージェントを親ペインの一部として扱っています3。tmux-ccm もバージョン 0.13.0（2026 年 11 月 5 日）で、親のターン終了後にバックグラウンドエージェントが稼働する間、ウィンドウ表示が IDLE と BUSY の間で往復しないよう修正しました4。また Synapse の README は、detached な tmux セッションではスピナーがアニメーションしないため、思考中のペインでも画面が 10 秒以上バイト単位で変化しないことがあり、静穏さだけでは思考中と完了を区別できないと指摘しています5。

こうした理由から運用手順では、閾値を延ばし続けるのではなく、ラベルを待つステージで STALLED が出て画面末尾が「〜の完了を待っています」と出ているときは、エージェント本人へ 1 回だけ「完了通知が届いていない。状態を確認し、終わっていれば続行、失敗していれば再委任」と尋ねることにしました。2 回目も止まった場合は、画面末尾を添えて人間に判断を仰ぎます1。

3 つの信号が示すもの・示さないもの

ラベルはラベルが変わったことを、tui-idle は入力欄が空いたことを、それぞれ正しく示していました。外れたのは、それを「ステージが終わった」「止まった」と読んだ側です。

信号示すもの示さないもの今回の観測
Issue のラベルエージェントがラベルを付け替えたことコミットが済んだこと付け替えの時点で、端末ではまだ git commit が実行中だった
端末の tui-idle（入力欄が空いた）親エージェントの会話ターンが止まっていることサブエージェントを待っているのか、止まっているのか閾値を 2 回から 10 回に上げても、本当の停止と区別できなかった。催促 1 回に対し、エージェントが委任先の停止を申告した
git log / git status --short成果物が記録に残ったことエージェントのターンが終わったかラベル・ターン終了と組み合わせて完了条件にした

成果物を実物で確認する原則は、完了の偽陰性の記事 で「報告より実物を見る」として扱いました。今回の事例では、その実物確認が未着手を見落とす偽陰性だけでなく、ラベルがコミットより先に進む側の歯止めにもなっています。

そこで監視から次ステージ起動までの完了条件は、次の組み合わせに組み直しました1。

  • 期待した Issue ラベルが付いている（外部の状態）
  • tui-idle で、画面末尾 8 行に実行中表示（agy なら Running）が無い（ターン終了）
  • git log --oneline -1 に当該ステージのコミットがあり、git status --short が空（成果物）
  • ラベルを待つステージで画面不変の打ち切り（STALLED）が出て、画面末尾が「〜の完了を待っています」なら、エージェントに 1 回だけ状態を尋ね、2 回目は人間に渡す（停止の切り分け）

メリットの裏にあるトレードオフと適用限界

3 点の信号を組み合わせる設計にも、割り切りと限界が残っています。

第 1 に、Running 文字列によるターン終了判定は CLI 依存 です。画面照合を完全に無くしたわけではなく、agy の実行中表示に合わせて "Running" を探しています。CLI ごとに実行中表示は異なるため、後の運用スクリプトでは agy に "Running"、Claude Code に "esc to interrupt" のように判定文字列を持ち分けています。対象 CLI の表示が変われば追随が要ります。

第 2 に、観測の母数が小さい 点です。ラベルがコミットより先に進んだのを確認したのは企画ステージの 1 回だけで、全ステージのうちどの割合で起きるかは測っていません。待機と停止の取り違えも、校閲ステージの 1 回（STALLED 2 回）での観測です。組み直した完了条件と催促運用の長期的な成功率や停止率も、まだ計測していません1。

想定される反論についても、現時点の判断を整理しておきます。

  • 「閾値をもっと上げればよいのでは」: 待機と停止を画面から区別できない以上、閾値を上げても打ち切りを遅らせるだけです。猶予を長くするほど、本当に委任先が止まっていたときの発見が遅れます。実際に閾値を 10 回へ上げた回でも、2 回目の発見は開始 8 分 40 秒後でした1。
  • 「催促は待機中のエージェントの邪魔にならないか」: 既存記事の事例では、待っていただけのエージェントへ催促を送っていました。今回の運用手順に書いた催促文は「完了通知が届いていない。状態を確認し、終わっていれば続行、失敗していれば再委任」と、待機中でもそのまま待ちを続けられる問い方にしています。それでも催促を自動で繰り返すと待機中の作業を邪魔する問題に戻るため、自動催促は 1 回に限りました1。
  • 「催促も自動化すれば人間は要らないのでは」: 2 回目の停止では画面末尾を添えて人間に渡す設計にしています。この設計で実際に何回人間に判断が渡ったかは計測していないため、人手介入の削減効果まではここでは主張できません。

前提が変われば結論はどう変わるか

監視側が端末画面を読まざるを得ないのは、エージェント CLI が端末の外へ状態を構造化して出していないからです。構造化イベントが取れる環境では、ターン終了やバックグラウンド待ちの判定は画面スクレイピングに頼らずに済みます。

たとえば Claude Code の Stop フックの入力ペイロードには background_tasks 配列が含まれ、公式ドキュメントは「セッションが終わった」と「バックグラウンドの作業に起こされるのを待って一時停止している」をフック側で区別するためだと説明しています6。今回画面上で起きた待機と停止の取り違えは、この区別が TUI 画面へ出てこないことから生じています。

また、Codex の codex app-server は JSON-RPC 2.0 で turn/completed 通知を送り、status として completed / interrupted / failed を返します7。Gemini CLI もヘッドレス実行の stream-json 出力に result イベントを持ち、status: 'success' | 'error' で成否を返します8。端末プロトコル側でも、プログラム自身が idle / working / done / blocked / error / clear といった状態をエスケープシーケンスで知らせる OSC 7501 が提案されています9。ただし Claude Code の公式ドキュメントは、tmux の中では端末本体ではなく tmux の対応を確認するため allow-passthrough が効かず、利用する場合は tmux の外でセッションを起動するよう案内しています10。

それでも残る論点があります。構造化イベントへ移っても、ターンの終了と成果物の永続化（コミット）は別のイベント です。ラベルがコミットより先に進んだのと同じ構造は、「ターンは終わったがコミットはされていない」という形で残りえます。成果物を git で確かめる 3 点目の条件は、通知が構造化されても外せません。

さらに、構造化イベントにも順序の罠はあります。Codex の Python SDK では、turn/start の RPC 応答が返る前に turn/completed 通知が到着するとルーターが破棄してしまい、完了待ちが止まる不具合が報告されています11。

今後、各 CLI の出力差を吸収するアダプターや、Orca のように端末とワークツリーを一体で扱う基盤が前提になれば、監視スクリプトが画面の文字列を読む部分は減っていくでしょう。ただし、期待した成果物がリポジトリに残ったかを確かめる責任は、引き続き監督側に残ります。

よくある質問（FAQ）

Q. AI エージェント CLI を別の端末で順に回すとき、ステージの完了は何で判定すればよいですか？

A. 1 つの信号ではなく、外部の状態（Issue のラベルなど）、ターン終了（入力待ちで実行中表示が無い）、成果物（当該ステージのコミットがあり、作業ツリーが空）の 3 点がそろったときを完了とします。筆者の環境ではラベルがコミットより先に進んだため、ラベルだけでは未コミットのまま次へ進むところでした。

Q. AI エージェントの端末が idle 表示なのに、作業が終わっていないのはなぜですか？

A. idle は親エージェントの会話ターンが止まっていることを示すだけで、サブエージェントやバックグラウンドの作業を待っている状態も含むからです。待っているだけのこともあれば、待っている相手が止まっていることもあります。

Q. AI エージェントがサブエージェントを待っているのか止まっているのか、外からどう見分けますか？

A. 筆者の環境では、画面からは見分けられませんでした。閾値を上げても打ち切りが遅れるだけでした。実際には、状態を確認し、終わっていれば続け、失敗していれば再委任するようエージェントに 1 回促したところ、委任先は未実行のまま止まっていたと答えて再委任し、完走しました。この経験から、催促は 1 回に限り、2 回目も止まったら人間に渡す手順にしています。

まとめ

  • Issue のラベルは「エージェントがラベルを付け替えた」ことしか示さない。筆者の環境では、ラベルが付いた時点で端末ではまだ git commit が実行中だった
  • 端末の idle 表示は、サブエージェントを待っているのか止まっているのかを区別しない。閾値を上げることは打ち切りを遅らせるだけで、区別の手段にはならない
  • 待機と停止の切り分けは、エージェント本人への 1 回の催促に置き、2 回目は人間に渡す
  • 完了は「ラベル＋ターン終了＋コミット」の 3 点の組で判定する。3 点目の成果物の確認は、構造化イベントに移っても外せない
