pytest-xdist が macOS で遅い原因と切り分け方法 ── setproctitle と launchservicesd の仕組み

macOS 上で pytest-xdist を使ってテストを並列実行しているのに、ワーカー数を増やしても期待どおりに速くならないことがあります。自分のテストコードに重い計算や I/O が見当たらないにもかかわらず、Activity Monitor や ps を見ると launchservicesd が CPU を消費しているケースです。

pytest-xdist における setproctitle 起因の速度劣化とは、任意依存パッケージの setproctitle（プロセスの表示名を書き換えるライブラリ）が導入された環境でワーカーがテストごとにプロセス名を更新し、macOS のシステムデーモンである launchservicesd（アプリケーションの起動や名称変更の通知を仲介するバックグラウンドプロセス）への通知ブロードキャストが連鎖して CPU 負荷と実行時間が増大する現象です。

空のテスト 2000 件を pytest -n 8 で実行した筆者の実機計測では、setproctitle が入っているかいないかだけで wall time が約 3.6〜4.8 倍（4.19〜4.94s 対 0.94〜1.15s）異なりました。なお、macOS 上で並列テストが遅くなる別の事例として、opendirectoryd / XProtect の競合と Git の自動保守が原因になったケースもありますが、あちらは unittest の並列実行に伴うものであり、setproctitle は関係しない別機構の問題です。

本記事では、3 往復の交互比較実験と単一プロセス実験の実測データをもとに、なぜ pytest-xdist と setproctitle の組み合わせで launchservicesd の負荷が跳ね上がるのか、誤認しやすい環境変数 PYTEST_CURRENT_TEST との違い、そして手元の環境で影響を切り分けて対処するやり方を整理します。

pytest-xdist が macOS で遅い原因とは何か ── 3 者の絡む仕組み

pytest-xdist・setproctitle・launchservicesd の 3 者がどのようにつながっているかを、各プロジェクトの実装と外部の検証記録から追っていきます。

pytest-xdist 側の挙動：1 テストあたり 2 回の呼び出し

pytest-xdist v3.8.0 の src/xdist/remote.py では、setproctitle を任意依存として読み込む構造になっています1。

  • 35〜40 行目で from setproctitle import setproctitle を try / except ImportError で読み込み、未導入時は何もしないフォールバック関数を定義しています1。
  • 66〜71 行目の worker_title(title: str) -> None 内で setproctitle(title) を呼び出し、例外が出ても握りつぶします1。
  • WorkerInteractor.run_one_test（228〜234 行目）では、テスト実行の直前に worker_title("[pytest-xdist running] %s" % item.nodeid) を、直後に worker_title("[pytest-xdist idle]") を呼び出します1。

つまり、1 テストあたり 2 回（2000 件のテストなら計 4000 回）setproctitle() が呼ばれます。この連携は、長時間かかるテストやハング時の状態を top や ps で把握しやすくするための "bonus goodie" として導入された経緯があります2。

なお、公式に「無効化機能がない」と明記されているわけではありませんが、少なくとも xdist/remote.py 内に setproctitle の呼び出しを抑止するオプションや環境変数による分岐は見当たらず、実装構造上は setproctitle が環境に導入されていれば無条件に呼ばれる形になっています1。

setproctitle と launchservicesd の挙動：macOS 固有の通知ブロードキャスト

setproctitle（py-setproctitle）側の src/spt_status.c を見ると、set_ps_display() は argv 領域を書き換えたあと、#ifdef PS_USE_DARWIN の分岐で darwin_set_process_title() を無条件に呼び出します3。一方、Linux 環境（PS_USE_PRCTL）では prctl(PR_SET_NAME, ...) と argv の書き換えを行うだけで、macOS のような Launch Services への IPC 呼び出しは存在しません3。

macOS 向けの src/darwin_set_process_name.c では、初回実行時に LSApplicationCheckIn でプロセスを Launch Services に登録し、以降は呼び出しごとに LSSetApplicationInformationItem を実行して表示名を更新します4。py-setproctitle の Issue #170 での報告によると、この呼び出しのたびに launchservicesd が全 Launch Services クライアントへ kLSNotifyApplicationNameChanged と kLSNotifyApplicationInformationKeyChanged の 2 件の通知をシステム全体へブロードキャストします5。環境変数による opt-out も同 Issue で議論されていますが、2026年11月14日時点では Open のまま未実装です5。

他環境での深刻化事例と類似事象

後述する筆者の実測（2000 件・-n 8）ではデスクトップのフリーズには至りませんでしたが、外部ではワーカー数や更新頻度によって深刻な UI ハングが起きた事例が報告されています。

  • Jochen Wersdörfer 氏の事例: pytest-xdist の実行中にデスクトップ全体がフリーズし、lsappinfo listen で計測したところ 1 分間に 11,773 件の application-name 通知（うち 11,769 件が 2 つの pytest ワーカー由来）が送出されていたと報告されています6。
  • BenchBox の事例: mutmut の推移的依存によって setproctitle が環境に混入し、2 ワーカーで毎秒 200 回以上の更新が走った結果、launchservicesd が 200%+ CPU・約 900 MB RSS、runningboardd が約 50% CPU に達し、WindowServer が飢餓状態になったと記録されています7。
  • 他ツールでの同型問題: Ray でもタスクごとの setproctitle 更新により Apple Silicon (M4) 上で WindowServer がハングする問題が報告され8、Launch Services への IPC 呼び出しをスキップしてローカルスレッド名のみを設定する修正がマージされました9。Node.js 等が利用する libuv でも、uv_set_process_title による同型の Launch Services 通知ストームが報告されています10。

PYTEST_CURRENT_TEST との違い

プロセス実行中のテストを把握する仕組みとして PYTEST_CURRENT_TEST がありますが、これはプロセスタイトルを書き換える機構とは別物です。pytest の公式ドキュメントにあるとおり、PYTEST_CURRENT_TEST はテストの setup / call / teardown 各ステージで os.environ へテスト名を設定する環境変数であり、argv や Launch Services には触れません11。

実際、筆者が社内で残していた初期の検証メモでも、誤って PYTEST_CURRENT_TEST を無効化する案を対策候補に挙げていましたが、実機検証の段階で機構と無関係であると気づき訂正しています。

実機ベンチマーク：3 往復交互比較と単一プロセス実験

ここからは、筆者が 2026年11月10日に実施した 2 つの実機実験の結果と、そこから言える事実と、断定できない点（留保）を分けて示します。

実験 A：pytest -n 8（空のテスト 2000 件）の 3 往復交互比較

外部要因やキャッシュの影響を均すため、setproctitle 有り（with）と無し（without）の 2 つの仮想環境を交互に 3 ラウンド実行し、各ラン前後の launchservicesd 累積 CPU 時間差分と wall time を比較しました。

目的: setproctitle 有り／無しの 2 つの仮想環境を交互に実行し、ps -Ao pid,cputime,comm の差分から launchservicesd の CPU 増分と wall time を記録します。

引用元: 筆者の検証記録（2026年11月）の run.py

"""setproctitle の有無で pytest-xdist 実行中の launchservicesd CPU 時間を比べる。

usage: python3 run.py <venv-with> <venv-without> <testdir> <rounds>
"""
import subprocess, sys, time

def lsd_cpu():
    out = subprocess.run(["ps", "-Ao", "pid,cputime,comm"], capture_output=True, text=True).stdout
    for line in out.splitlines():
        if line.endswith("/launchservicesd"):
            t = line.split()[1]  # [[dd-]hh:]mm:ss.cc
            parts = t.replace("-", ":").split(":")
            secs = 0.0
            for p in parts:
                secs = secs * 60 + float(p)
            return secs
    raise SystemExit("launchservicesd not found")

def run(venv, testdir):
    c0, t0 = lsd_cpu(), time.monotonic()
    r = subprocess.run([f"{venv}/bin/python", "-m", "pytest", "-q", "-p", "no:cacheprovider",
                        "-n", "8", testdir], capture_output=True, text=True)
    wall, dc = time.monotonic() - t0, lsd_cpu() - c0
    tail = r.stdout.strip().splitlines()[-1] if r.stdout.strip() else r.stderr[-200:]
    return wall, dc, r.returncode, tail

with_v, without_v, testdir, rounds = sys.argv[1], sys.argv[2], sys.argv[3], int(sys.argv[4])
for i in range(rounds):
    for label, v in (("with", with_v), ("without", without_v)):
        wall, dc, rc, tail = run(v, testdir)
        print(f"round={i+1} setproctitle={label:7} rc={rc} wall={wall:6.2f}s launchservicesd_cpu_delta={dc:6.2f}s | {tail}", flush=True)

実行結果（筆者の検証記録における実測出力）:

round=2 setproctitle=with    rc=0 wall=  4.53s launchservicesd_cpu_delta=  4.34s | 2000 passed in 4.22s

round=3 setproctitle=without rc=0 wall=  1.15s launchservicesd_cpu_delta=  0.42s | 2000 passed in 0.99s

解説: -p no:cacheprovider で pytest 側のキャッシュを無効化したうえで、time.monotonic() による wall time と ps による launchservicesd の累積 CPU 時間差分を 1 ラウンドごとに交互記録しています。

実験 B：pytest-xdist を外した単一プロセスでの切り分け

pytest-xdist のワーカー間通信やプロセス起動コストが主因ではないことを確かめるため、pytest-xdist を外した単一プロセスで setproctitle() を 0 回と 2000 回呼ぶ比較を行いました。

目的: pytest-xdist を介さず、単一プロセス内で setproctitle() を指定回数ループ実行したときの wall time と launchservicesd の CPU 増分を測ります。

引用元: 筆者の検証記録（2026年11月）の spt.py

import subprocess, sys, time
from setproctitle import setproctitle
def cpu():
    for l in subprocess.run(["ps","-Ao","cputime,comm"],capture_output=True,text=True).stdout.splitlines():
        if l.endswith("/launchservicesd"):
            s=0.0
            for p in l.split()[0].replace("-",":").split(":"): s=s*60+float(p)
            return s
n=int(sys.argv[1]); c0=cpu(); t0=time.monotonic()
for i in range(n): setproctitle(f"title {i}")
print(f"calls={n} wall={time.monotonic()-t0:.2f}s launchservicesd_cpu_delta={cpu()-c0:.2f}s")

実行結果（筆者の検証記録における実測出力）:

calls=0 wall=0.00s launchservicesd_cpu_delta=0.11s
calls=2000 wall=1.49s launchservicesd_cpu_delta=1.86s

解説: setproctitle(f"title {i}") を 2000 回呼ぶだけで wall=1.49s かかり、launchservicesd の CPU 増分が 1.86s 発生しています。これにより、負荷源が pytest-xdist の並列通信ではなく setproctitle() 呼び出し自体にあることが裏付けられました。

ただし、実験 B は n=0 と n=2000 を各 1 回ずつしか計測していないため、n=0 でも 0.11s 増えている背景ノイズのばらつき幅は不明です。また、実験 A の CPU 増分（4.30〜4.92s）と実験 B（1.86s）の差が、pytest-xdist の 1 テスト 2 回呼び出し（計 4000 回）によるものか、8 ワーカー並列呼び出しによる競合オーバーヘッドかは、このログからは切り分けていません。

macOS で setproctitle の影響を切り分けて対処するやり方

手元のプロジェクトで pytest-xdist の並列テストが遅いと感じた場合は、次の手順で原因を切り分けられます。

1. 環境に setproctitle が混入していないか確認する

pytest-xdist は setproctitle を必須依存にしていないため、mutmut のような別パッケージの推移的依存として意図せず入っていることがあります7。まずはテスト実行用の仮想環境で、次のコマンドを実行して導入有無とバージョンを確認します。

目的: テスト実行用の仮想環境に setproctitle がインストールされているかとその場所を確認します。

python -c "import setproctitle; print(setproctitle.__version__, setproctitle.__file__)"

解説: ModuleNotFoundError が出れば未導入であり、本記事の事象には該当しません。バージョンとパスが表示された場合は、プロジェクトで使っている依存関係の確認コマンド（パッケージマネージャの依存ツリー表示など）で、どのパッケージから引き込まれているかを辿ります。

2. 有り／無しの交互計測で影響割合を把握する

テストスイート全体の遅さのうち、setproctitle と launchservicesd が占める割合を知りたい場合は、一時的に setproctitle を外した検証用の仮想環境を作り、先ほどの run.py のように有り／無しを交互に数ラウンド実行して wall time の差を比べます。

3. 外せない場合の回避策と注意点

他の依存関係から setproctitle をアンインストールできない場合、テストコード側で単純に import xdist.remote して worker_title を書き換えても効きません。pytest-xdist のワーカーは execnet 経由で xdist/remote.py のコードを __channelexec__ というモジュール空間で実行するため、通常の import で読み込んだモジュールオブジェクトとは別物になるためです67。

回避策としては、conftest.py の pytest_configure フック内で __channelexec__ フレームにある worker_title を何もしない関数に差し替える手法が、Jochen Wersdörfer 氏の検証記事や BenchBox のドキュメントで紹介されています67。なお、本記事ではこの回避コード自体の動作検証は行っていないため、具体的な実装例と適用時の注意点は一次情報（67）を参照してください。

よくある質問（FAQ）

Q. PYTEST_CURRENT_TEST 環境変数を無効化すれば launchservicesd の負荷は下がりますか？

A. 下がりません。PYTEST_CURRENT_TEST は pytest がテスト実行中に os.environ へ設定する環境変数であり、setproctitle によるプロセス名書き換えや Launch Services への IPC 呼び出しとは無関係な別の機構です11。

Q. pytest-xdist を使わなければ、setproctitle による launchservicesd の負荷は起きませんか？

A. いいえ、pytest-xdist を使わない単一プロセスでも、setproctitle() を呼べば launchservicesd の CPU 負荷は発生します。単一プロセスで setproctitle() を 2000 回連続呼び出しした実験でも launchservicesd の CPU 増分が 1.86 秒発生しました。並列実行時に顕在化しやすいのは、pytest-xdist がテスト 1 件ごとに 2 回 setproctitle() を呼び出し1、複数ワーカーから同時に高頻度で実行されるためです。

Q. テストコードで import xdist.remote して worker_title を上書きすれば回避できますか？

A. その方法では回避できません。pytest-xdist のワーカーは execnet 経由で __channelexec__ というモジュール空間でコードを実行するため、通常の import xdist.remote で読み込んだモジュールオブジェクトを書き換えてもワーカー側の実行には反映されないためです67。回避する場合は conftest.py の pytest_configure 内で __channelexec__ 側の worker_title を差し替える手法が報告されています67。

まとめ

  • macOS で pytest-xdist の並列テストが期待どおり速くならない場合、任意依存の setproctitle が 1 テストあたり 2 回プロセス名を書き換え、launchservicesd への通知ブロードキャストを引き起こしている可能性があります。
  • setproctitle 有り／無しの仮想環境を交互に計測する比較実験では、空のテスト 2000 件（pytest -n 8）で実行時間に約 3.6〜4.8 倍の差（4.19〜4.94s 対 0.94〜1.15s）が出ました。
  • 単一プロセスでの setproctitle() 2000 回呼び出しでも launchservicesd の CPU 増分が 1.86 秒生じており、負荷の主因は並列通信ではなく setproctitle() 自体の macOS 実装にあります。
  • PYTEST_CURRENT_TEST は環境変数でありプロセス名書き換えとは無関係なため、これを無効化しても問題は解決しません。
  • まずは環境に setproctitle が推移的依存として紛れ込んでいないかを確認し、外せない場合は conftest.py での __channelexec__ 差し替えなどの回避策を検討するのが現実的です。
