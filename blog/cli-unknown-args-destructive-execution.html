エージェント向け自作 CLI の最低限の契約 ── 未知の引数は exit 2、--help は副作用なし

開発現場で新しいコマンドや慣れないツールを前にしたとき、私たち人間は使い方を確かめるために反射的に --help や -h を叩きます。Linux や UNIX のコマンドライン環境において、ヘルプオプションは当然備わっているべきものという暗黙の前提が広く共有されています。これは Claude Code などの AI エージェントにとっても例外ではありません。エージェントもまた、与えられた環境やツールの使い方を探索する過程で、頻繁に --help を実行して使用法を把握しようと試みます。

しかし、業務の自動化や開発支援のために急ごしらえで作られた自作 CLI スクリプトでは、引数のパースが簡易的な sys.argv の手動解釈で済まされがちです。特に「引数を取らないサブコマンド」において、余分な引数の存在を検査せずに放置してしまうケースが後を絶ちません。

筆者の開発現場において、まさにその盲点が引き金となったヒヤリハットが発生しました。AI エージェントが Git worktree を整理する自作ツールの使い方を確認しようと --help を付与して実行したところ、ヘルプを表示するどころか、worktree の削除サブコマンド本体がそのまま走り出したのです。

エージェント向け自作 CLI における引数安全契約 とは、未知の引数や不正なオプションが指定された場合に直ちに終了コード 2 で処理を中断し、--help が指定された場合はいかなる副作用（ファイルの作成・変更・削除やプロセスの起動・停止など）も伴わずに使用法（usage）を表示して正常終了する、入力検証の防御原則です。

GNU Coding Standards では、--help が指定された場合は他の引数を無視して通常の機能を実行してはならないと定められており 1、コマンドラインインターフェースの設計指針である clig.dev でも、--help は他のフラグを無視してヘルプを表示すべきであると提唱されています 2。

幸いこのときは削除対象となる worktree が存在せず、実害には至りませんでした。しかし、「たまたま消す対象が無くてセーフだった」という結果オーライ（事後検収）に甘えてはなりません。Git worktree やバックグラウンドプロセスの強制終了といった不可逆な破壊操作を伴うツールにおいて、事後検収は一度の失敗で破綻します。安全を担保すべきなのは実行結果の検収ではなく、実行境界における決定論的な入力予防契約です。

本記事では、実務で発生したヒヤリハットの一次実測ログと修正・再修正の diff をもとに、未知の引数を無視する CLI に潜む構造的危険性を検証し、AI エージェント時代に自作 CLI が備えるべき 3 つの安全契約を提示します。

使い方を見ようと —help を付けたら破壊処理が走りかけた瞬間

事の発端は、筆者が開発中の別プロジェクトにおいて、Claude Code を用いた自動化の検証を行っていた 2026-10-26 のセッションでした。

エージェントに対してバックグラウンド作業の片付けを促した際、エージェントは自作のオーケストレーションツール（dispatch.py）に含まれる sweep サブコマンド（不要になった Git worktree や作業端末セッションをクローズして削除するコマンド）の使い方を確認するため、コマンドラインから以下のコマンドを実行しました。

コマンド実行ログ 引用元: 筆者の検証セッションの記録（2026-10-26）

D=$(ls -d ~/.claude/plugins/cache/nqounet/claude-skills/*/ | sort -V | tail -1)skills/dispatch/scripts/dispatch.py; python3 "$D" --help 2>&1 | head -20; python3 "$D" sweep --help 2>&1 | head -20

前半の python3 "$D" --help は、スクリプト全体の docstring（ヘルプメッセージ）を期待どおりに出力しました。しかし、後半の python3 "$D" sweep --help はヘルプを出力せず、サブコマンド sweep の本体処理がそのまま実行されたのです。

ターミナルには、以下のログが出力されました。

keep task-1f7a92af: PR #69 のマージ待ち（main に無い patch 1 件）
keep task-8cc7b743: PR #67 のマージ待ち（main に無い patch 1 件）

この実行時、該当リポジトリには 2 つの Git worktree が存在していましたが、いずれもプルリクエストのマージ待ち状態であったため、スクリプトの内部ロジックにより「keep」と判定されました。そのため、worktree の削除や端末の終了といった破壊的な処理は実行されず、実害は免れました。

エージェントはその直後のターンで、以下のように報告しました。

なお、最初に sweep --help を打ったところ、ヘルプではなく sweep そのものが実行されました。結果は上と同じ「keep」2 件で、消えたものはありません。

エージェント自身も、コマンド出力から「ヘルプではなく本体が実行された」という異常出力を検知し、後続のターンでその旨を報告しています。しかし、問題はその約 2 分後でした。プルリクエストのマージが完了した後に通常の dispatch.py sweep を実行したところ、今度は 2 件の worktree が実際に削除（removed）され、紐づいていた 4 つの端末セッションが終了されたのです 3。

もし最初の --help 実行時に、マージ済みの worktree や完了判定となるタスクが存在していた場合、当時のコード構造上はヘルプを表示することなく、作業中の worktree や端末セッションが即座に消去されてしまうところでした。「消えるものが無くて良かった」という事後的な偶然によって救われたに過ぎなかったのです。

コードに潜んでいた穴と最初の修正：—help 先行分岐と exit 2 ガード

なぜ、sweep --help でヘルプが出ず、本体処理が走ってしまったのでしょうか。

原因は、dispatch.py の main() 関数における引数解釈の構造にありました。このスクリプトでは、外部ライブラリを使わずに sys.argv を手動スライスして引数を処理していました。

go や drive、watch といった引数を必須とするサブコマンドでは、len(args) による引数長の検査が行われていました。しかし、追加の引数を必要としないはずの finish や sweep の分岐では、残りの引数の有無が一切検査されていなかったのです。そのため、末尾に未知のフラグや --help が渡されてもそれを完全に無視し、本体関数 cmd_sweep(dry) を呼び出す構造になっていました。

「引数を取らないサブコマンドだから引数チェックは不要だろう」という思い込みが、余分な引数をすべてサイレントに無視して破壊処理を実行する重大な穴を生んでいたのです。

この問題に対処するため、直ちに最初の修正コミットが行われました。修正の骨子となったのは以下の 3 点です。

  1. -h / --help の先行判定: main() の冒頭で引数リストに -h または --help が含まれているかを最優先で検査し、サブコマンドの処理に入る前にヘルプを出力して終了コード 0 で正常終了させる。
  2. 引数長検査と exit 2 による拒絶: finish および sweep の分岐において、len(args) != 1（サブコマンド名以外の引数が存在する場合）は標準エラー出力（stderr）に使用法（usage）を出力し、終了コード 2 で即座に処理を停止する。
  3. 単体テストによる契約の固定: test_dispatch.py にテストクラス CliArguments を新設し、モックを用いて sweep --help や未知の引数が渡された際に本体関数が一切呼び出されないことを機械的に保証する。

diff:dispatch.py 引用元: 自作CLIスクリプト（dispatch.py）の修正コミット

+    if "-h" in args or "--help" in args:
+        print(__doc__)
+        return 0

+            if len(args) != 1:
+                print("usage: dispatch.py sweep [--dry-run]", file=sys.stderr)
+                return 2

この修正によって、未知の引数が渡された場合は即座に終了コード 2 で停止し、--help が渡された場合は本体を実行せずにヘルプを表示する構造が整いました。

さらに、この安全契約が将来のコード変更で崩れないよう、単体テストによって本体関数の未実行を検証するテストケースが追加されました。

python:test_dispatch.py 引用元: 自作CLIテストスイート（test_dispatch.py）のテストコード

class CliArguments(unittest.TestCase):
    def test_help_precedes_parsing_and_never_runs_commands(self):
    def test_extra_arguments_do_not_run_finish_or_sweep(self):

テストでは、モックを用いて cmd_sweep や cmd_finish が決して呼び出されないこと、および終了コードが期待どおり 0 または 2 になることが厳格に検証されました。

さらなる落とし穴：共通オプション事前除去が招いたすり抜け

これで自作 CLI の引数処理は安全になったかに見えました。しかし、数日後に別の不具合報告が寄せられました。手動引数パースには、さらなる落とし穴が潜んでいたのです。

dispatch.py の main() 関数では、サブコマンド分岐に入る前段で、スクリプト全体で共通して使えるオプションとして --model や --effort などのフラグを検索し、del args[i:i + 2] を使って引数リストから事前に取り除く処理を行っていました。

これが思わぬすり抜けを引き起こしました。

本来、--model や --effort はエージェントを起動する一部のサブコマンド（go や drive）でのみ有効なオプションであり、sweep や finish には無関係なオプションです。しかし、もしエージェントや人間が dispatch.py sweep --model opus のように誤ってオプションを付与して実行した場合、前段の共通処理によって --model とその値が args から事前に削除されてしまいます。

その結果、サブコマンド判定に到達した時点では len(args) が 1 に戻ってしまい、せっかく導入した len(args) != 1 のガードをすり抜けて cmd_sweep() 本体が実行されてしまっていたのです。

「共通オプションだから手前で一括して取り除いておく」という安易な前処理が、サブコマンドごとの引数検証を骨抜きにしていました。

このすり抜けを塞ぐため、再修正コミットが行われました。

diff:dispatch.py 引用元: 自作CLIスクリプト（dispatch.py）の再修正コミット

-            if len(args) != 1:
+            if len(args) != 1 or claude_flags:

再修正では、事前除去を行う前に claude_flags = "--model" in args or "--effort" in args によってオプションの存在をフラグとして保持するようにしました。そして、finish および sweep の検査条件を if len(args) != 1 or claude_flags: へと強化し、不要なフラグが付与されている場合も確実に usage を出力して終了コード 2 で停止するように改善しました。

また、スクリプトの docstring にもサブコマンドごとの引数契約を明文化し、「--model / --effort を取るのは go / drive だけ。finish / sweep に付けると usage を出して exit 2（本体は実行しない）」という旨が明確に規定されました。

手動で sys.argv を加工・スライスするアプローチは、共通オプションのハンドリングやオプションの出現順序によって容易にガードをすり抜けてしまいます。穴を塞いだつもりでも別の経路からすり抜けが発生するという事実は、手動引数パースの構造的な限界を物語っています。

自作 CLI が守るべき3つの防御契約

実務でのヒヤリハットと再修正の経験から、自作 CLI（特に破壊的操作を伴うツール）が守るべき契約は以下の 3 つに集約されます。

契約 1: --help / -h は副作用を持たずに usage を表示して正常終了（exit 0）する

GNU Coding Standards では、--help オプションが指定された場合、プログラムは通常の機能を実行してはならず（should not perform its normal function）、呼び出し方法を簡潔に出力して正常終了すべきであると明確に定めています 1。clig.dev においても、-h や --help はヘルプ以外の意味を持たせてはならず、末尾を含めいかなる位置に渡された場合でも他のフラグを無視してヘルプを表示すべきであるとされています 2。

サブコマンドの実行ロジックや破壊的処理に入る前に、ヘルプオプションの有無を決定論的に捕捉し、本体処理を一切走らせずに exit 0 で終了させることが鉄則です。

契約 2: 未知の引数・オプションはサイレントに無視せず exit 2 で停止する

POSIX.1-2017 のユーティリティ規約では、未認識のオプションが渡された場合、標準エラー出力に診断メッセージを出力し、非ゼロの終了ステータスで終了しなければならないと規定されています 4。さらに Python の標準ライブラリである argparse では、未認識の引数が渡された場合、デフォルトで stderr に使用法を出力し、ステータスコード 2 で終了する仕様になっています 5。

ここで重要なのは、単なる一般的な失敗を表す exit 1 ではなく、構文・引数エラーを表す exit 2 を返すことです。これにより、呼び出し元のスクリプトや AI エージェントに対して「実行に失敗した」のではなく「コマンドの構文やオプションの指定方法に誤りがある」という明確な境界シグナルを伝達できます。

契約 3: 破壊的操作には --dry-run を用意し、引数解釈の契約を単体テストで保証する

clig.dev では、ディレクトリの削除などの破壊的な変更を伴う操作に対して、事前に影響を確認できる --dry-run（-n）の提供を推奨しています 2。

そして何より重要なのは、引数パースの挙動をコード上の工夫だけで終わらせず、単体テストによって固定することです。「--help を付けたときに本体関数が呼ばれないこと」「未知の引数を付けたときに本体関数が呼ばれず exit 2 になること」をモックを用いてテストすることで、将来のリファクタリングやすり抜けの再発を機械的に防止できます。また、サブコマンドの管理が複雑化する場合は、独自のスライス処理に頼るのではなく、PEP 389 で標準化されたサブパーサー機構などの体系的なパーサーの活用を検討すべきです 6。

引数解釈方式の比較

手動での引数スライスと、標準ライブラリ（argparse など）を用いた引数解釈の違いを整理すると、以下のようになります。入力境界の安全性を担保するうえでは、手動スライスによる場当たり的なガードよりも、標準パーサーによる宣言的な制約が圧倒的に優位です。

比較項目手動引数解釈（sys.argv スライス）標準ライブラリ（argparse）
未知の引数・オプションの処理明示的な長さ・フラグ検査を書かない限りサイレントに無視されやすいデフォルトで未認識の引数を検知し、stderr に usage を出して exit 2 で停止
--help / -h のハンドリングサブコマンド分岐の前に個別の先行分岐を書かないと本体処理が走る自動で action='help' が設定され、本体処理を実行せず exit 0 で終了
共通オプションの事前除去del args[...] などの手動除去により引数長検査をすり抜ける穴が生まれやすいサブパーサー（add_subparsers）によりサブコマンドごとの許容引数が厳格に分離される
実装行数・手軽さ手軽に書けるが、安全ガードを足すほど肥大化・複雑化するパーサーの定義が必要だが、引数の追加・変更に対して安全な構造を保ちやすい（ただし parse_known_args や略称設定などの設定次第ですり抜けが起きる余地はある）
テスト容易性・堅牢性手動ループの分岐漏れやすり抜けを単体テストで網羅的に塞ぎ続ける必要があるライブラリ自体の引数検証機構に任せられるため、ツール固有のコマンドロジック検証に集中可能

このよう​​に、手動スライスでは安全ガードを追加するたびに実装が複雑化し、すり抜け穴が残りやすくなります。一方、argparse などの検証機構を備えたライブラリを活用することで、未知の引数の拒絶や --help の先行表示を宣言的に実装できます。

以下は、argparse を用いてこれらの契約を満たす最小限の CLI テンプレートです。

python:safe_cli_template.py

import argparse
import sys


def cmd_sweep(dry_run: bool) -> int:
    if dry_run:
        print("[dry-run] 不要なリソースをスキャンしました（削除は行いません）")
    else:
        print("不要なリソースを安全に削除しました")
    return 0


def main(argv: list[str] | None = None) -> int:
    parser = argparse.ArgumentParser(
        prog="safe_cli",
        description="エージェント向け自作ツールの安全な CLI テンプレート",
    )
    parser.add_argument(
        "-n",
        "--dry-run",
        action="store_true",
        help="実際の変更を行わずに実行内容を表示する",
    )

    subparsers = parser.add_subparsers(
        dest="subcommand",
        title="subcommands",
        description="利用可能なサブコマンド一覧",
    )

    # sweep サブコマンドの定義（追加の引数は受け付けない）
    parser_sweep = subparsers.add_parser(
        "sweep",
        help="不要なリソースを一括でクリーンアップする",
    )

    args = parser.parse_args(argv)

    if args.subcommand == "sweep":
        return cmd_sweep(dry_run=args.dry_run)

    parser.print_help(sys.stderr)
    return 2


if __name__ == "__main__":
    sys.exit(main())

このテンプレートでは、safe_cli sweep --help を実行すれば本体処理を実行することなく exit 0 でヘルプが表示され、safe_cli sweep --unknown のように未知の引数が渡された場合は自動的に stderr に usage が出力されて exit 2 で停止します。

想定される反論への客観的検討

現場でこうした防御契約を導入しようとすると、しばしば以下のような反論が寄せられます。

  • 反論 1：自分しか使わない小さな使い捨てスクリプトに、終了コード 2 や単体テストまで書くのは大げさではないか？
    • 検討: 自分しか使わないツールであっても、それを操作するのが AI エージェントになった瞬間、前提は根本から変わります。エージェントは高速に自律的な試行錯誤を行い、推測によってフラグを補おうとします。「今回はたまたま消える対象が無かった」という事後検収の結果オーライは、不可逆な破壊の前では一度の失敗で破綻します。不可逆な処理を伴うツールであるならば、結果ではなく入力境界での決定論的な予防こそが不可欠です。
  • 反論 2：AI エージェントは賢いのだから、プロンプトやドキュメントを丁寧に整えれば正しい引数だけを叩いてくれるのではないか？
    • 検討: プロンプトによる指示は常に確率的です。未知の環境や曖昧な指示に直面したエージェントは、環境を認識するために探索行動（probe）に出ます。自然言語のプロンプトだけに依存した安全設計は脆く、実行境界である CLI ツール自身が決定論的なガードを提供しなければなりません。

エージェント協業時代におけるコマンドライン契約の再考

AI エージェントが開発現場の日常的なパートナーとなるにつれ、CLI ツールに求められる前提も大きく変化しています。

人間は、ツールの使い方が分からないときにドキュメントやマニュアルをじっくり読んでから慎重にコマンドを入力することが多いでしょう。しかしエージェントは、環境やツールの仕様を確かめるために、積極的に「コマンドを叩いて標準出力や標準エラー出力を観察する（プローブ動作）」を行います。

エージェントにとって、コマンドの終了コードとエラー出力は、環境の状態を正しく把握するための最も重要なフィードバックループです。

もし自作 CLI が未知の引数をサイレントに無視して実行してしまうと、エージェントは終了コード 0 を正常終了シグナルとして受け取るため、指定したオプションが無効化されたことに気付かず、意図と異なる前提のまま後続タスクを実行してしまいます。その結果、誤った前提の上に後続の自動化タスクを次々と組み立ててしまい、問題の検知が大幅に遅れることになります。

逆に、未知の引数に対して直ちに exit 2 と明快な usage が返されれば、エージェントは「引数の構文エラーが発生した」と正確に認識し、即座に正しいオプションへと自己修復を試みることができます。

ツールの起動確認や仕様確認において --help の存在を盲目的に過信しない慎重さも大切ですが、提供するツール側としては、POSIX ユーティリティ規約 7 や clig.dev 2 が培ってきた標準的な契約を忠実に守り続けることが求められます。広く共有されたプロトコルを裏切らないインターフェースを提供することこそが、自律型 AI エージェントとの安全で堅牢な協業を支える土台となるのです。

前提が変われば結論はどう変わるか：構造化プロトコルと推論能力の進化

では、今後の技術進化によって開発環境の前提が変わった場合、この結論はどう変わるでしょうか。

第一に、Model Context Protocol（MCP）などのツール連携プロトコルが標準化され、CLI のテキスト入出力ではなく JSON-RPC などを介した構造化されたツール呼び出しが主流になった場合です。呼び出し形式がシェル引数からスキーマ定義されたオブジェクトに移行したとしても、「未知のプロパティをスキーマ検証で拒絶する」「副作用を伴う操作の前にドライランを用意する」という防御契約の原則は全く同じ形で存続します。インターフェースの層が変わるだけで、境界における入力検証の重要性は揺らぎません。

第二に、将来のフロンティア LLM の推論能力やコンテキスト理解が飛躍的に向上した場合です。どれほどモデルが賢くなったとしても、自然言語プロンプトによる指示は本質的に確率的です。確率的な知能と協業するシステムであるからこそ、不可逆な破壊操作の手前には決定論的な防御壁（未知入力の拒絶と --help の副作用ゼロ）が不可欠であり続けます。モデルの賢さに甘えてツールの境界契約を緩めることは、安全設計の本末転倒と言えます。

よくある質問（FAQ）

Q. 自作 CLI で未知のオプションが渡されたとき、なぜ終了コード 2 で終了すべきなのですか？

終了コード 2 は、Python の argparse においてコマンドライン引数の構文エラーやコマンドの誤用時にデフォルトで返される標準的な終了ステータスです 5（POSIX ユーティリティ規約においても、未認識のオプションに対しては非ゼロの終了ステータスを返すことが義務付けられています 4）。サイレントに無視して実行したり、単に汎用エラーを表す exit 1 で終了するのではなく exit 2 を返すことで、AI エージェントや呼び出し元スクリプトに対して「引数の指定方法に誤りがある」という明確な境界シグナルを伝え、破壊的処理の誤爆を防ぎつつ安全な再試行やリカバリを促すことができます。

Q. —help オプションで破壊的な本体処理が走ってしまうのを防ぐには、どのような実装が必要ですか？

サブコマンドのディスパッチや引数スライスの前段で -h または --help の存在を最優先で検出し、コマンド本体のロジックを一切呼び出さずに使用法（usage）を表示して即座に終了（exit 0）させます 1。手動で sys.argv を解釈する場合は共通フラグの事前除去によるすり抜けを防ぐか、argparse などの標準ライブラリを用いてサブコマンドごとに独立したパーサーを定義し、デフォルトで --help が安全に処理される構造を採用します。

まとめ

AI エージェントが自律的にコマンドを実行する時代において、自作 CLI の引数パースの手抜きは致命的なヒヤリハットに直結します。本記事で提示した重要な判断基準は以下のとおりです。

  • 引数を取らないサブコマンドでも引数長を必ず検査する: 余分な引数や --help をサイレントに無視して本体を実行する穴を放置してはならない。
  • -h / --help は副作用を持たずに usage を表示して exit 0 で終了させる: サブコマンドの判定や破壊的操作に先立ち、最優先でヘルプを処理する。
  • 未知のオプションや余分な引数は exit 2 で即座に停止させる: 一般的なエラー（exit 1）でお茶を濁さず、構文エラー（exit 2）を返すことでエージェントに明確な自己修復シグナルを渡す。
  • 手動の引数事前除去（スライス）によるすり抜け穴を警戒する: 共通オプションを手前で削除すると引数長検査が無力化するため、フラグの存在を保持して検証するか標準ライブラリを活用する。
  • 事後検収の結果オーライに依存せず入力境界の決定論的契約と単体テストで担保する: 「消えるものが無くてセーフだった」という偶然に甘えず、モックを用いたテストで本体未実行を機械的に保証する。
