AI エージェントの多段パイプラインで起きる「完了の偽陽性」とは？承認ログと検収を分離する設計

AI エージェントに計画・実装・承認の多段パイプラインを組ませるとき、人間が最初に警戒するのは「実際には作業していないのに完了と報告する嘘」です。当ブログでも過去に、証跡の提示を義務づけて未実施報告を防ぐ設計 や、逆向きにエージェントが未開始と報告しながら実際には作業を終えていた 完了の偽陰性への対処 を取り上げました。

しかし実務では、ファイルもコミットも、さらに「✅ 承認（修正なし）」という承認ログまですべて揃っているのに、中身を開けるとモデルの謝罪文だったという別の事故が起きます。完了の偽陽性（False Positive） とは、AI エージェントの多段パイプラインにおいて、実行や承認のログ上は「成功・承認済み」と記録されているにもかかわらず、実際の成果物の中身が未完成やエラー報告、謝罪文など、期待された要件を満たしていない状態を指します。

この事故は、プロンプトの指示を増やしたり、人間の承認ステップを挟んだりするだけでは防げません。段の出力をファイルへ書き込む前に構文などの性質を機械で確かめる「決定論的検証」と、「承認の記録（プロセスの通過）」と「成果物の検収（中身・品質の確認）」を別物として切り離す設計が必要です。

承認ログは「修正なし」、中身は AI の謝罪文だった実例

この問題は机上の空論ではなく、私自身が自作エージェントの実験で踏み抜いた事故から見えてきたものです1。2026年2月、個人で開発していたタスク実行ツール（以下、実験ツールA）を使い、Perl モジュール生成用の実験リポジトリ（以下、実験リポジトリA）で JSON-RPC 2.0 の値オブジェクト（Request / Response / Error / Notification）を実装させるタスクを 3 回連続で実行しました。

実験ツールAでは、上流の計画フェーズ（3 件）に上位の推論モデルを、各実装ステップ（保存された記録で 14 件）に軽量・高速なモデルを割り当てていました。実行後に残された 4 件のエピソード記録（3 タスク目のみ 9 秒差で 2 件記録）を確認すると、4 件すべてが「結果: ✅ 承認」「ユーザーフィードバック: 承認（修正なし）」と記録されていました。

ところが、実際に生成・コミットされたファイルの中身を開くと、実態はまるで異なっていました。保存されていた実装ステップ 14 件のうち 4 件で、実装を担当したモデルが Perl コードではなく AMBIGUITY:（ツールが利用できないなどの曖昧性・エラー報告）を返していたのです。

実際に Notification.pm としてコミットされたファイルの中身を確認します。このコードは、実験リポジトリA に残された実物（全 3 行）の逐語引用です。

引用元: 実験リポジトリA（非公開）の Notification.pm

再度申し訳ありません。利用可能なツールについて誤解しているようです。`write_file` や `run_shell_command` が直接利用できないため、指示されたファイルの作成や変更を実行できません。

AMBIGUITY: `write_file` および `run_shell_command` ツールが利用できないため、新しいファイルを直接作成したり、既存のファイルを変更したりすることができません。このため、指示された実装ステップ（`lib/JSONRPC/Notification.pm` および `t/04_notification.t` の作成）を実行できません。ツールの利用可能性について、追加の指示が必要です。

Notification.pm には Perl コードが 1 行も含まれておらず、自然言語の謝罪文とツール不足の報告だけがモジュールファイルとしてコミットされていました。さらに Error.pm（224 行）のファイル先頭にも「run_shell_command ツールが利用できないため…」という報告と AMBIGUITY: が書き込まれており、Request.pm や Response.pm には、先頭に File: ... や Markdown のコードフェンス、末尾に use Test::More; を含むテストコードがそのまま混入していました（コミットされた .pm ファイルと実装ステップの応答がバイト単位で一致することを 6 組確認しています）。

なぜ AMBIGUITY: の報告がファイル書き込みをすり抜けたのでしょうか。当時の実験ツールAの実装（runner.ts）では、モデルの応答が特定の接頭辞で始まる場合のみ書き込みをスキップする処理を入れていました。

引用元: 実験ツールA（非公開）の runner.ts

    // AIの回答が AMBIGUITY: で始まる場合は、ファイルへの書き込みをスキップする
    if (text.trim().startsWith('AMBIGUITY:')) {
      console.warn(`⚠️ Skipped applying changes because AI reported ambiguity.`);
      return { text };
    }

このコードは、応答の先頭行が AMBIGUITY: で始まるケースだけを想定していました。保存された 4 件の AMBIGUITY: 応答のうち 3 件は先頭がこの文字列だったためスキップされ、残る 1 件の Error.pm（3 タスク目の step_1）は 1 行目にツール不可の説明が置かれて 3 行目に AMBIGUITY: が現れたため判定を素通りしました。さらに、Notification.pm を生成したステップの初回実行時（リトライ時にメタデータが上書きされ、リトライ時は AMBIGUITY: 先頭で上書きがスキップされたため初回分だけが残存）も同様に 1 行目が謝罪文で 3 行目が AMBIGUITY: だったため、そのままファイルへ書き込まれていました。

さらに、承認ログの仕組みを後から確認したところ、実験ツールAの承認コマンド（review.ts）には、実験開始の約 23 分前に追加された非対話の自動承認オプション（-y, --yes）と、対話プロンプトで y を入力する 2 通りの経路がありました。どちらの経路でも .pm ファイルの構文や中身を検査する処理は一切なく、episode.ts は実行の成功フラグだけを見て「✅ 承認」「承認（修正なし）」という文言を無条件で書き出す仕様になっていました。なお、当日の 4 件の承認ログが自動承認オプションで記録されたか、人間が対話で承認したかは当時の実行ログが残っておらず確定できませんが、いずれの経路であっても中身を検証しない仕組みだった点に変わりはありません。

なぜ「承認の記録」は成果物の中身を保証しないのか

この事故は特定のツールや古いモデルに限った話ではなく、多段パイプラインが抱える 3 つの構造的な要因が重なって起きています。

1. LLM の出力エラーと表層的な文字列判定の脆さ

プログラムの関数であれば、前提条件を満たせないときに例外を投げて異常終了します。しかし LLM はツールが利用できないと判断したときでも、例外を投げずに自然言語の謝罪文や説明文を正常な応答として返します。文法的に正しいが意味や形式が期待と異なる出力は「セマンティックエラー」と呼ばれ、スキーマ検証などの出力ガードレールで防ぐ必要があると指摘されています2。今回の謝罪文混入は Perl として構文エラーになる点で厳密には異なりますが、プロセスが異常終了せず期待外のテキストが次段へ流れる構造は共通しています。

また、LLM エージェントはルールに違反していても操作の成功をハルシネーションすることがあります3。実験ツールAのように「特定の失敗文字列（AMBIGUITY:）で始まる出力を弾く」という表層的なチェックは、モデルが前置きを 1 行足すだけで簡単に突破されます。

2. 承認ステップの形骸化と承認疲労

「承認ステップが存在すること」と「判断が存在すること」は同じではありません4。Anthropic の報告では、手動の権限確認プロンプトに対してユーザーが承認疲労（Approval Fatigue）に陥り、実際にはプロンプトの 93% がそのまま承認されている実態が挙げられています5。また同社の別調査でも、経験を積んだユーザー（750 セッション時点）は新規ユーザー（50 セッション未満）の約 20% に対して 40% 超のセッションで full auto-approve を有効にする傾向が報告されています6。

変更対象の差分や検証結果が見えない低コンテキストな承認要求が繰り返されると、人間は確認作業を単なる「ゴム印承認（Rubber-stamping）」として処理するようになります478。自動承認フラグを使うか人間がボタンを押すかにかかわらず、検収の裏付けを持たない承認ログは「承認の通過」という事実しか保証しません。

3. 予防と検収の混同と過剰な自律性

OWASP の LLM06:2025（Excessive Agency）は、過剰な機能・過剰な権限・過剰な自律性が、曖昧または予期しない出力による誤った変更を引き起こすリスクを指摘しています9。ここで重要になるのが、「予防」と「検収」の設計対象の違いです。

原因の空間に対して設計する予防（たとえば「AMBIGUITY: で始まる出力を弾く」）は、失敗パターンの種類が無限にあるため、どれだけ条件を足しても必ず漏れが生じます。一方で、結果の空間に対して設計する検収（たとえば「Perl として構文が通るか」）は、成果物が満たすべき性質の数だけ検査を書けば閉じます。多段パイプラインの完了判定は、どちらの空間を検査しているかによって信頼性が大きく変わります。

方式検証の対象（空間）謝罪文混入への耐性運用負荷・承認疲労主なリスク
承認ログのみ（従来型）プロセスの通過記録低い（無検証で通過）高い（または形骸化）ゴム印承認・自動通過による完了の偽陽性
表層フィルタ（先頭文字列一致等）特定の失敗パターン（原因の空間）低い（前置き 1 行で突破）中程度想定外の出力形式への取りこぼし
決定論的検収ゲート＋承認分離成果物の必須性質（結果の空間）高い（構文・スキーマ等で遮断）低い（機械検証後に人へ渡す）意味的妥当性の見落とし（後述の限界）

表層的な文字列フィルタに頼るのではなく、成果物が満たすべき結果の空間を決定論的に検査し、承認ログとは別レイヤーで管理する必要があります。

AI エージェントの多段パイプラインに組み込む 2 つの決定論的対策

完了の偽陽性を防ぐためにパイプラインへ組み込むべき対策は、次の 2 点です。

対策 1: ファイル書き込み・コミット前の決定論的検証

プロンプトや Markdown のルール文書に「コード以外は出力しない」「謝罪文を書くな」と追記しても、それは LLM にとって「制約」ではなく「推奨事項」に過ぎず、守られないリスクが残ります310。エージェントの挙動を確実に縛るには、ツール実行の前後やファイル書き込み処理の直前に、構文チェッカ（perl -c）や Linter、スキーマ検証など、pass/fail を決定論的に返すスクリプトを組み込みます。

たとえば Claude Code を利用している場合、PostToolUse フックを使い、.pm ファイルが書き込まれた直後に perl -c を実行する仕組みを作れます11。次のスクリプトは jq と perl を使用し、構文エラーがあれば終了コード 2 と標準エラー出力を返してエージェントへ差し戻します。

ファイル: .claude/hooks/check-perl-syntax.sh

#!/bin/bash
set -euo pipefail

input=$(cat)
file_path=$(jq -r '.tool_input.file_path // empty' <<<"$input")

if [[ -z "$file_path" || "$file_path" != *.pm || ! -f "$file_path" ]]; then
  exit 0
fi

if ! err=$(perl -c "$file_path" 2>&1); then
  echo "Syntax error in $file_path: $err" >&2
  exit 2
fi

exit 0

作成したスクリプトには実行権限（chmod +x .claude/hooks/check-perl-syntax.sh）を付与し、.claude/settings.json の PostToolUse フックへ登録します11。

ファイル: .claude/settings.json

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          {
            "type": "command",
            "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/check-perl-syntax.sh"
          }
        ]
      }
    ]
  }
}

PostToolUse はファイル書き込み自体が完了した後に発火しますが、終了コード 2 を返すことで標準エラー出力の内容がモデルへフィードバックされ、次のターンで謝罪文の残存や構文エラーを自己修正させる契機になります11。もしファイルへの書き込み自体やコミットを未然に止めたい場合は、パイプラインの書き込み関数内で一時ファイルに対して perl -c を通すか、Git の pre-commit フックで同様に非ゼロ終了させる構成を採ります。

対策 2: 「承認の記録」と「成果物の検収」の分離

もう 1 つの対策は、承認ログを成果物の品質保証として扱わないことです。承認ログはあくまで「承認プロセスを通過した」という履歴にとどめ、構文チェックや型検査、自動テストなどの決定論的検収は別のゲートとして設けます。

可逆な修正や形式エラーは結果の空間を見る機械的検収で拾って自動的に差し戻し、異常が解消しないときだけ処理を停止して人間へ通知します。そのうえで、人間の確認や承認は「決定論的検証をすべて通過した成果物」に対してのみ要求する設計にすれば、設計意図や要件との整合といった機械で検証できない判断だけに人間の集中力を温存できます47。

メリットの裏にあるトレードオフと適用限界

決定論的検証と承認分離の導入は万能ではなく、運用上のトレードオフと適用限界を把握しておく必要があります。

検証失敗によるリトライ連鎖とコスト増

perl -c や Linter 自体の実行時間は一瞬ですが、モデルが「ツールが使えない」と誤認したまま謝罪文を返し続ける状態で機械的エラーを繰り返し差し戻すと、無駄なリトライが連鎖してトークン消費と待ち時間が膨らみます。決定論的検証を組み込む際は、「同一の構文エラーや検証失敗が一定回数連続したら停止して人間にエスカレーションする」という上限設計（サーキットブレーカー）をセットで設ける必要があります。

非コード成果物への適用方法

設計書や Markdown 記事のような自然言語の成果物には、プログラミング言語の構文チェッカをそのまま適用できません。しかし、出力形式に応じた決定論的チェックへの置き換えは可能です。たとえば JSON 出力であればスキーマ検証2、Markdown であれば必須見出しの有無や、AMBIGUITY:・「申し訳ありません」といったメタ報告パターンの検査に置き換えることで、同様の素通りを防げます。

構文が通っても「正しい実装」とは限らない

決定論的検証は「最低限の形式を満たしていない不良品」を遮断するための床であり、仕様やビジネスロジックの正しさまで保証するものではありません。実際、実験リポジトリAの Request.pm では末尾にテストコードが混入していましたが、Perl の構文としてエラーにならなければ perl -c 単体では通過してしまいます。

また、Anthropic が報告した分類器モデルによる確率的なガードレール（Claude Code の auto mode）でも、実セッションで記録された過剰動作（n=52）に対する見逃し率は 17%（誤検知率は 0.4%、合成データ流出テスト n=1,000 の見逃し率は 5.7%）とされています5。決定論的な構文・形式チェック、確率的なレビュー、自動テストを多層で組み合わせる前提を崩さないことが重要です。

前提が変われば結論はどう変わるか

今後、モデルのツール呼び出し精度やエージェント基盤のツール認識が向上すれば、「利用可能なツールを誤認してテキストで謝罪文を返す」といった初歩的な失敗は減っていくと考えられます。

また、開発者がツールに習熟するにつれて、アクションごとの事前承認を減らし、自律実行させたうえで必要に応じて割り込む運用（Human-on-the-loop）へ移行する傾向も見られます。Anthropic の調査では、経験ユーザー（750 セッション時点）の full auto-approve 利用率が 40% を超える一方、ユーザーによるターンあたりの割り込み率（interrupt rate）も初期（約 10 セッション時点）の約 5% から 750 セッション時点の約 9% へ上昇しています6。

しかし、技術や運用スタイルが進化しても、「LLM は失敗時に例外ではなく自然言語のテキストを返しうる」「承認プロセスの通過記録と成果物の実体は別物である」という構造自体は変わりません。むしろ人間が事前承認を減らして自律実行を広げるほど、中身を見ないまま承認ログだけが残るリスクは高まります。そのため、結果の空間を機械的に検査する決定論的検収ゲートをパイプラインに常設し、人間は異常時の介入と最終判断に集中する設計の重要性は、今後さらに高まっていきます。

よくある質問（FAQ）

Q. AI エージェントの「完了の偽陽性」とは何ですか？

A. 実行ログや承認履歴の上では「完了」「承認済み」と記録されているにもかかわらず、実際の成果物が未完成であったり、AI の謝罪文やエラー報告がそのまま書き込まれていたりする状態を指します。人間のチェックをすり抜けて、壊れた成果物が次段へ渡るため、手戻りや品質低下の原因になります。

Q. 承認ログが「承認済み」なのに成果物が壊れるのはなぜですか？

A. 多くのパイプラインでは、承認ステップが「処理が成功フラグを返した」「人間または自動フラグが承認を通した」というプロセス通過だけを記録しており、成果物の中身を検証していないためです。さらに、頻繁な確認プロンプトによる承認疲労（ゴム印承認）や、先頭文字列一致のような脆いエラー判定が重なると、不良品がそのまま通過します。

Q. LLM が謝罪文をファイルに書き込むのを防ぐにはどうすればよいですか？

A. ファイルへの書き込み直前やコミット前に、言語の構文チェッカ（例: perl -c）、Linter、スキーマ検証などの決定論的検証をフックとして組み込むのが最も確実です。プロンプトでの禁止指示や特定のエラー文言の除外ではなく、成果物が満たすべき形式を機械的に判定し、不合格なら非ゼロの終了コードでブロックしてエージェントへ差し戻します。

まとめ

  • 多段パイプラインでは、ファイル・コミット・承認ログの 3 点が揃っていても、成果物の中身がモデルの謝罪文やエラー報告である「完了の偽陽性」が起きます。
  • 「AMBIGUITY: で始まる出力を弾く」といった原因の空間を絞る表層的なガードは、モデルが前置きを 1 行添えるだけで容易に突破されます。
  • ファイル書き込み前やコミット前に構文チェック・スキーマ検証などの決定論的検証（結果の空間の検査）を挟み、不合格時は非ゼロ終了でブロックする設計が不可欠です。
  • 承認の記録（プロセスの通過履歴）と成果物の検収（品質・妥当性の保証）は別物として分離し、人間は機械的検証を通過した後の判断に集中する運用へ切り替える必要があります。

AI エージェントを組み込んだ開発パイプラインの設計や、決定論的検証・品質ゲートの導入についてお悩みの方は、ぜひ コンタクトフォーム よりお気軽にご相談ください。
