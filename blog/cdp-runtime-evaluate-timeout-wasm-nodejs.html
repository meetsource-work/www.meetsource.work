#cdp#wasm#nodejs#ブラウザ自動化

Chrome 拡張で長い試行を回すと、CDP が45秒で切れる ── 同じ Wasm を Node から呼んで推移表を最後まで取った

ブラウザ自動化ツール（Puppeteer、Playwright、Chrome 拡張機能、Claude in Chrome など）を用いて、Web アプリケーション上で長時間のシミュレーションや連続した検証試行を実行していると、およそ 45秒（45,000ms）前後で突然コマンドが異常終了し、呼び出し元への戻り値の返却が途絶する壁に突き当たることがあります。

Chrome DevTools Protocol（CDP）の Runtime.evaluate タイムアウトとは、ブラウザのデバッグ接続経由で実行された JavaScript の評価が所定の時間制限（ツール既定で 45 秒など）を超過した際にクライアント側で通信が切断される現象であり、非同期スクリプトであっても全体の実行時間が単一コマンドの待機上限を超えることによって発生します。

このタイムアウトに対して「タイムアウト設定を延長する」「処理の合間に待機（sleep）を挟む」といった対症療法を試みても、一度切断された evaluate のインメモリ戻り値（途中の推移配列など）は回収できません。どれほど画面が最後まで進んでいても、長時間の検証ループはそこで止まってしまいます。

この問題に対する確実な解決策は、同一の Rust/Wasm ソースから wasm-bindgen --target nodejs を用いて Node.js 実行環境へ計算責務を物理的に分離し、推移表の全ステップをヘッドレスに完走させたうえで、最終状態（終端値）をブラウザ画面の描画値と突き合わせることです。ブラウザは「画面の描画と最終確認」、重い計算は「Node.js 上の Wasm」と責務を物理的に分離し、終端値が画面と一致するかを照合する方がはるかに堅牢です。

本記事では、自作の Web 経営シミュレーションゲーム（以下、プロジェクトA）における実務検証ログに基づき、CDP タイムアウトの発生メカニズムと、Wasm のマルチターゲット出力を活用した検証アーキテクチャを解説します。

CDP のタイムアウト制約とレンダラ無応答のメカニズム

なぜブラウザ内で重い処理を回すと 45 秒前後で通信が切れてしまうのか、その内部仕様とアーキテクチャ的要因を整理します。

Runtime.evaluate のプロトコル仕様

Chrome DevTools Protocol（CDP）における Runtime.evaluate は、指定したコンテキスト内で JavaScript 式を評価するための基本コマンドです1。

このコマンドは expression、awaitPromise、returnByValue、timeout などのパラメータを持ち、デバッガクライアントがブラウザ内の状態を取得・操作する際の標準的なトランスポートとなっています。Chrome 拡張機能から CDP を利用する場合は、chrome.debugger API の sendCommand を通じてブラウザプロセスへコマンドが送信されます2。

Chromium のマルチプロセスアーキテクチャと IPC

Chromium は、全体の UI や拡張機能セッションを管理する Browser Process と、各タブの Web コンテンツを描画・実行する Renderer Process が物理的に分離されたマルチプロセスモデルを採用しています3。

デバッグコマンドは Browser Process からプロセス間通信（IPC: Mojo）を経由して該当タブの Renderer Process へ配送されます。Renderer Process 内部では Blink レンダリングエンジンが動作しており、JavaScript の実行はレンダラのメインスレッド上でタスクとしてスケジューリングされます4。

クライアント側タイムアウトと「副作用の非同期完走」の不可逆性

長時間にわたるシミュレーション処理では、UI の更新を伴いながら数十期〜数百期に及ぶループ処理を実行します。各ステップの合間に await sleep(...) を挟んでメインスレッドへの配慮を行っていたとしても、処理全体を単一の Runtime.evaluate コールの中で非同期待機させている場合、全体の所要時間は容易に数十秒に達します。

クライアント側の自動化ツール（Chrome 拡張など）は、単一の evaluate 呼び出しに対して所定の時間上限（本検証環境では 45,000ms = 45秒）を超えて応答がない場合、通信タイムアウト例外を発行して Promise 待機を強制的に打ち切ります。この際、エラーメッセージには定型文として The renderer may be frozen or unresponsive が付与されます。

しかし、ここで極めて重要なのは 「クライアント側で通信がタイムアウトしても、レンダラプロセス側で実行中のスクリプト自体がキャンセルされるわけではない」 という点です。ブラウザ側ではバックグラウンドでスクリプトが走り続け、計算自体は最後まで完走します（副作用の非同期完走）5。

問題の本質は、切断された evaluate 呼び出しの Promise はクライアント側ですでに破棄されているため、計算が完了した後にスクリプトが末尾で返そうとしていたインメモリの配列データ（推移ログなど）は二度と受け取れない という不可逆性にあります。

ブラウザ内実行でのタイムアウトと戻り値欠落の観測

プロジェクトAの開発サーバー上で、実際に 50 年分（1,250期）のシミュレーションループを Chrome 拡張から実行した際の挙動を観察しました6。

このスクリプトでは、各期の進行と DOM 操作の合間に await sleep(15) や await sleep(40) を挟んでいましたが、50 年分の累積実行時間が 45 秒の上限を超過したため、戻り値の文字列化（log.join('\n')）の直前で通信が打ち切られました。

実行環境の分離（ブラウザ内 vs Node.js ヘッドレス）の比較

タイムアウトへの対策として、自動化ツールのタイムアウト設定値を延長するというアプローチが真っ先に検討されがちです。たとえば Puppeteer には protocolTimeout（デフォルト180秒）を引き上げる設定が存在し7、タイムアウト時の回避策として言及されることがあります8。

しかし、Playwright の公式ドキュメントでも言及されているように、テストの不安定さ（flaky）への対処として低レベルのタイムアウトを安易に引き上げる運用は推奨されません9。長時間の同期的あるいは擬似同期的な処理をブラウザのメインスレッド上で回し続けることは、メモリ消費の肥大化やレンダラプロセスのクラッシュリスクを伴い、本質的な安定性をもたらさないためです。

ブラウザの CDP 経由で重い計算を実行するアプローチと、同一ロジックを Node.js に切り出してヘッドレスに実行するアプローチには、実行モデルと安定性の面で明確なトレードオフが存在します。

比較項目ブラウザ内実行（CDP Runtime.evaluate）ヘッドレス直接実行（Node.js + wasm-bindgen）
実行スレッドレンダラメインスレッド（UI描画・DOMと共有）独立した Node.js プロセス
タイムアウト制約あり（クライアントツールの通信制限: 45秒〜数分で強制切断）なし（プロセスの実行完了まで無制限）
UI・描画オーバーヘッド高（DOM更新や再描画要求が割り込む）ゼロ（UI描画なし、計算に専念）
推移データ回収の確実性低（タイムアウト時にインメモリ戻り値が全喪失）確実（標準出力やファイルへ即時ストリーム保存）
50年計算の所要時間約45秒以上（タイムアウト到達）数秒以内（瞬時に完走）
適した役割画面描画の最終確認、DOM・CSS・イベント検証長期シミュレーション、大量データ試行、推移表の取得

したがって、ブラウザ自動化ですべてのシミュレーション計算を抱え込むのではなく、計算処理を Node.js に逃がし、ブラウザは最終状態の描画確認に特化させる責務分離が極めて合理的です。

wasm-bindgen によるマルチターゲット出力と Node 実行

Rust で記述されたロジックを WebAssembly にコンパイルしている場合、wasm-bindgen のマルチターゲット出力機能を用いることで、ブラウザ向けと Node.js 向けのバインディングを同一ソースから簡単に作り分けることができます。

wasm-bindgen のマルチターゲット機能

wasm-bindgen は --target オプションによって生成する JavaScript ラッパー（シム）の形式を切り替えることができます10。

  • --target web: ブラウザ環境向けの ES モジュールを出力
  • --target nodejs: Node.js 環境向けの CommonJS モジュールを出力

Rust 側の計算コアが DOM 操作やブラウザ固有のグローバルオブジェクト（web-sys など）に依存せず、純粋なステートマシンやドメインロジックとして完結していれば、同一のコンパイル済み Wasm バイナリ（wasm32-unknown-unknown）からコマンド 1 つで Node.js 向けモジュールを生成できます10。

Node.js 向けバインディングのビルド

以下のコマンドにより、リリースビルドされた Wasm バイナリから Node.js 用のバインディングを出力します。

引用元: プロジェクトA（非公開）の検証作業ログ（hands-on-log.md §3）

wasm-bindgen --target nodejs --out-dir $S/wasm-main target/wasm32-unknown-unknown/release/trillion_wasm.wasm

このコマンドにより、$S/wasm-main 配下に Node.js の require で直接ロード可能な JavaScript シムと Wasm ファイルが生成されます。実行時は、生成された Wasm モジュールのエントリポイントを環境変数 WASM で指定してスクリプトを呼び出します（例: WASM=$S/wasm-main/trillion_wasm.js node play2.js）。

台本スクリプト play2.js による推移表の取得

Node.js 環境から Wasm を直接呼び出し、ブラウザで実行したのと全く同一の施策シーケンスを適用して 5 年ごとの推移表を出力するスクリプト play2.js を作成しました。

引用元: プロジェクトA（非公開）の検証台本 play2.js（検証作業ログより抜粋）

const st = () => JSON.parse(w.state());

const tax = m => Object.entries(m).forEach(([k, v]) => tryDo(() => w.setTaxRate(k, v)));
const half = { agriculture: 50, inn: 75, tavern: 100, smithy: 50 };
const out = [];
const snap = y => { const s = st(), p = s.population; out.push(`${y}年 人口${p.total}（子${p.childMale + p.childFemale} 成${p.adultMale + p.adultFemale} 老${p.elderMale + p.elderFemale} 冒${p.adventurers}） 収容${s.capacity.carrying} 国庫${s.treasury}`); };
snap(0);
for (let y = 1; y <= 50; y++) {
  if (y === 1 || y === 26) tax(half);
  if (y === 11) tax({ agriculture: 0, inn: 0, tavern: 0, smithy: 0 });

    const s = st(); if (s.treasury < 8000) break;
    if (s.freeWallCapacity < 6) { tryDo(() => w.expandWall()); continue; }
    for (const f of ['housing', 'water', 'agriculture', 'sanitation']) tryDo(() => w.build(f, 1));
    if (y >= 26) { tryDo(() => w.build('tavern', 1)); tryDo(() => w.build('inn', 1)); }
  }
  w.advance(25);
  if (y % 5 === 0) snap(y);
}
console.log(out.join('\\n'));

総人口だけでなく、年齢層別の詳細内訳、収容人口、国庫残高に至るまで、すべての数値が 1 の位まで完全に一致していました。

ただし、ここで確認できたのはあくまで「50年目の最終状態の一致」である点には留意が必要です。ブラウザ内実行において 1年目から 49年目までの途中スナップショットの回収に失敗しているため、途中の各期すべてで同一の遷移を辿っていたことまでは厳密に検証できていません。

それでも、同一のシード値と施策シーケンスを与えた結果として終端値が完全に一致した事実は、ヘッドレスな推移検証スクリプトがブラウザ内の挙動を高い忠実度で再現できている強力な裏付けとなります。

検証台本のリポジトリ管理と運用の知見

この検証プロセスを通じて、検証用スクリプトの管理方法に関する重要な運用上の知見が得られました。

一時スクリプト作り捨ての反省

調査やデバッグの最中、開発者は作業用の一時ディレクトリ（scratchpad など）に play.js や play2.js といったスクリプトを作成して場当たり的に実行しがちです。

しかし、検証スクリプトを作り捨ててしまうと、後続のセッションや別の開発者が同じ検証を再現できなくなります。また、異なる施策パターン（方針 A と方針 B）による推移の比較を行いたい場合にも、スクリプトをゼロから書き直さなければならず、検証資産が組織に蓄積されません。

実行台本（playthrough）としてのコミット管理

この反省に基づき、プロジェクトAでは「プロトタイプを遊ぶ台本をコミットする（方針ごとの推移表）」という課題（Issue）が起票され、長期シミュレーションの振る舞いを確かめる台本そのものをリポジトリ内でバージョン管理する方針へと昇格しました。

一時的な scratchpad でスクリプトを作り捨てて検証を回すと、後から結果の比較や再検証ができなくなるため、長期推移を確かめる実行台本（playthrough）そのものをリポジトリにコミットして管理すべきです。

実行台本をコードベース内に固定しておけば、CI パイプラインや定期テストに組み込むことで、Wasm 側のロジック変更時に「50 年後の経済バランスが意図せず破綻していないか」をいつでも自動検証できる恒久的なテスト資産となります。

よくある質問（FAQ）

Q. CDP のタイムアウト値を延長すれば、ブラウザ内だけでも長時間のシミュレーションは完走できるのではないでしょうか？

A. タイムアウト値を引き上げれば通信切断自体は一時的に先送りできますが、根本的な解決にはなりません。シミュレーション全体の所要時間が長引くほど、DOM 更新やタイマー待機が重なってクライアントツールのセッションが不安定になり、ブラウザクラッシュのリスクも高まります。Playwright の公式ドキュメントでもテストの不安定さ（flaky）を理由にした低レベルタイムアウトの延長は避けるべきとされており、計算負荷の高い処理そのものをブラウザ外へ切り出すのが健全な設計です。

Q. ブラウザ向けにビルドされた Wasm は、どのようなプロジェクトでもそのまま Node.js で動作しますか？

A. Wasm の計算コアが DOM 操作やブラウザ専用 API（web-sys など）に依存していない純粋なロジックであれば、そのまま動作します。wasm-bindgen の --target nodejs オプションを指定することで Node.js の CommonJS モジュールとしてインポート可能なバインディングが生成されます。UI とロジックが密結合している場合は、計算に関わるステートマシンやコアエンジンを独立したクレートやモジュールとして分離しておくことが前提条件となります。

まとめ

本記事の検証から得られた知見を以下の命題にまとめます。

  • CDP 45秒タイムアウトの本質は単一コマンドの待機上限超過である: ブラウザ自動化ツール経由で長時間のシミュレーションを実行すると、非同期処理であっても全体の所要時間がクライアント側の待機上限（45秒）を超過し、通信が切断される。
  • 対症療法（タイムアウト延長・待機）ではインメモリの戻り値は救えない: 切断された evaluate 呼び出しの Promise は破棄されるため、後から待機して画面が更新されていても、途中の推移配列などは回収できない。
  • 計算と画面確認の責務を物理的に分離する: 同一の Rust ソースから wasm-bindgen --target nodejs でヘッドレス実行環境を構築し、重い試行や推移取得は Node.js で高速に完走させる。
  • 画面描画値との終端突き合わせで正しさを証明する: Node.js で算出した終端値（最終期の値）をブラウザ画面の描画値と照合することで、ブラウザ描画の健全性と計算ロジックの一致を両立して担保する。
  • 実行台本は作り捨てずリポジトリにコミットする: 一時的なスクリプトではなく、長期シミュレーションを再現可能な台本としてリポジトリで管理し、継続的な品質検証資産とする。
