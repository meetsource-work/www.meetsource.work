別モデルに1回レビューさせれば足りるのか。観点を分けたレビューを重ねると、同じ指摘が増えるだけなのか、別の欠陥が出てくるのか。AI エージェントの役割定義やスキル定義を変えた1つの変更に、別モデルの単発レビューを2巡、観点を分けた2軸レビューを1巡当てて、返ってきた指摘を数え直しました。

本記事でいう 2軸レビュー とは、差分を「リポジトリに文書化された規約に沿っているか（Standards）」と「元の Issue・仕様を忠実に実装しているか（Spec）」の2つの観点に分け、別々のサブエージェントに並列で見させるレビューです1。

結果を先に書きます。私の Claude Code セッション（以下「私のセッション」）が現物と突き合わせて実在と判定した指摘は、6件 + 4件 + 14件 = 24件でした。そのうち、2つの軸が同じ欠陥を指していた組は3組（指摘の数では6件）で、3組とも3巡目の2軸の間でした。同じ巡に並べて比べられたのは3巡目の2軸だけで、その14件のうち6件が同じ欠陥を指していたことになります。もう1件、1巡目の別モデルが指摘していた、差分の外にある設計文書のカタログ未記載を、私のセッションは範囲外として退けており、この指摘は3巡目に拾い直されています。

対象は実行可能なコードではなく、AI エージェントが読んで従う役割定義・スキル定義・用語集・ADR（設計判断の記録）を変えた1つの変更です。変更の中心は、連載記事を査読する判定役（lead-reviewer）の新設でした。その連載では「中堅層（mid-level）の読者は多くの場合決裁権を持たない」という仮説を実験として確かめようとしており、判定役がこの仮説を前提として持つと、答えを知った側が実験を査読することになります。以下で「仮説の漏洩」と呼ぶのは、この仮説が判定役に届いてしまう欠陥です。

2つの軸が同じ欠陥を指していたのは3組だった

ここでいう同じ欠陥とは、同じ時点の、同じ箇所の、同じ仕組みの欠陥です。重なりは、4つのレビュー出力のどの2つの間でも数えました。ただし前の巡の指摘を直してから次の巡を当てているので、巡をまたいで同じ欠陥が指されるには、前の巡で指摘された欠陥が直されずに残っている必要があります。本件でその例は、次の節で扱う設計文書のカタログ欠落の1件だけで、私のセッションが空振りとして24件から外したため、3組には入っていません。実在と判定した24件の指摘のうち、2つの軸が同じ欠陥を指していたのは3組（6件）で、どれも3巡目の2軸の間でした。同じ巡に並べた2軸の14件で見ると、6件が重なっていたことになります。

全24件の一覧ではなく、重なりの3組と、重なりを確かめた単独の指摘を並べた抜粋です。

1巡目の指摘を、私が範囲外として退けた1件

1巡目の agy は、差分に含まれない設計文書の「カタログ未記載」を指摘していました。私のセッションの照合記録には、その設計文書のカタログ更新は「別タスクで扱う範囲」と書いてあります。私のセッションはこれを理由に、空振りに数えました。agy の指摘の原文は記録に残っていないので、書けるのは「同じ設計文書のカタログ未記載を指摘していた」までです。何が欠けていると指摘したのかは分かりません。なお、agy 1巡目の依頼文には、観点の1つとして「SSOT違反」を入れていました。

3巡目の Standards 軸は、同じ設計文書について、カタログにレビュアーが載っていないことを挙げました。私のセッションはこれを実在と判定し、3巡目の修正で、設計文書のパスとカタログを直しています。変更ファイルにも、その設計文書が入っています。

整理すると、記録から言えるのは次のことです。範囲外として退けた文書が、同じ変更の中で直されました。3巡目に、1巡目の判定を誤りと認める発言は残っていません。また、Standards 軸が挙げたレビュアー2体のうち continuity-reviewer は変更前からあるもので、範囲外という判断にも一理あったことは事実です。

突き合わせる側が外部の「高」判定を、一次情報で正しく格下げした例は、サブエージェントの「高」判定を、そのまま信じない に書きました。今回の1件は、その逆に、範囲外として退けた文書が同じ変更の中で直された例にあたります。

コードレビューの研究と照らすと、何が言えるか

以下の研究の対象はコードで、別ファイルの文書の追従漏れを測ったものではありません。そのうえで、本件と照らせる範囲を引きます。

ICML 2025 の論文4 は、産業用の C++ コードを対象に、レビューへ渡す文脈の切り出し方を比べています。著者のまとめでは、差分や親関数だけを入力にする方式は効果が低く、文脈をより細かく切り出すと重要なバグを含みやすくなります。最も長い文脈を与えた方式が、一段短い方式を全体として下回った理由について、著者は長い文脈でのモデルの能力低下によると推測しています。切り出し方ごとに、ほぼそれぞれの方式だけが当てた事例もありました。

AACR-Bench5（査読前の論文）は、複数言語のコードの PR を対象に、指摘に要る文脈を差分・ファイル・リポジトリの3段に分けています。著者のまとめでは、エージェント型以外の手法は、要る文脈が広がるほど再現率が落ちます（表には例外があります）。エージェント型（Claude Code で実装）は、著者によれば全体として逆の傾向を示します。ただし全体の再現率は低く（たとえば Claude-4.5-Sonnet で 10.10%）、著者は、外部の依存にとらわれて差分の中の目立つ問題を見落とす可能性を挙げています。

SWR-Bench6（FSE 2026 掲載）は、実際のレビューコメントを生成させる評価です。著者によれば、既存のツールは、バグのような機能的な欠陥のほうが、古くなったドキュメントのような非機能的な問題より検出しやすいといいます。ここでのドキュメントは、コード内のコメント等を指します。

本件では、差分の外にある設計文書のカタログ未記載を、agy が1巡目で指摘していました（私のセッションの照合記録による）。agy はリポジトリを読める状態でした。ただし、それが当たった理由だとは言えません。同じ巡に、agy がリポジトリ固有のルールを読まずに一般論を出したと私のセッションが判定した指摘も、別にあるからです。研究が示す「差分の外は拾いにくい」傾向と本件は、対立しません。「拾えたかどうか」と「拾った指摘を採ったかどうか」は、別の段でした。

私の感想として書くと、レビューを入れたかどうかより、そのレビュアーに何を読ませたかで、拾える欠陥の種類が決まって見えました。1つの変更での観察なので、因果までは言えません。

1つの変更で言えること・言えないこと

  • 母数は1つの変更・3巡です。対象はコードではなく、エージェントが読む文書です
  • 「実在」「空振り」は私のセッションの判定で、機械的に照合した記録は5件だけです。空振りの判定が外れていた例が1件あります
  • agy と2軸は、モデルと渡したものが同時に違うので、差の原因を分けられません。agy の中のモデルは記録にありません
  • 2軸レビューは、agy の2巡で直したあとの差分を見ています。同じ差分に3つを同時に当てた比較ではありません

私の感想を書くと、3巡にわたって実在の欠陥が出続けたこと自体が、レビューの精度より、レビューされる側の設計に構造の問題が残っていた合図だったと思います。この変更では、検証中の仮説が漏れる経路が、断定・理由文・必読ファイルと形を変えて3巡残っていました。経路ごとに別の欠陥として数えているので、前の節の「同じ欠陥」の定義とは食い違いません。経路の詳細は 前回の記事 にあります。

よくある質問（FAQ）

Q. 観点を分けたレビューを重ねると、同じ指摘が増えるだけではないですか？

A. この変更では、同じ指摘も別の欠陥も出ました。同じ巡に並べて比べられたのは3巡目の2軸だけで、その14件のうち6件（3組）が同じ欠陥を指していました。一方、2軸レビューは、それまでの agy の2巡には無かった指摘（記事本文を査読する段階で話数が取れない欠陥など）も挙げています。1つの変更での観察で、どの構成でも同じになるとは言えません。

Q. 2軸レビューの Standards と Spec は何が違いますか？

A. Standards はリポジトリに文書化された規約に沿っているかを見る観点、Spec は元の Issue・仕様を忠実に実装しているかを見る観点です1。2つを別々のサブエージェントに並列で見させ、結果も軸ごとに分けて報告します。この変更では、書き上げた記事本文を査読する段階で話数が取れないという欠陥を挙げたのは、Spec 軸だけでした。

Q. 差分だけを見るレビューは、差分の外の問題を拾えないのですか？

A. コードを対象にした研究では、入力を差分に絞ると全体の検出が落ちること4や、エージェント型以外の手法では指摘に要る文脈が広がるほど検出が落ちる傾向5が、著者のまとめとして報告されています。ただしこの変更では、別モデルが差分の外にある設計文書のカタログ未記載を1巡目で指摘していました（私のセッションの照合記録による）。それを範囲外として退けたのは、突き合わせた私の側でした。

まとめ

  • 別モデルの単発レビューに観点を分けたレビューを足すと、この変更では、同じ指摘も別の欠陥も出ました
  • 実在と判定した24件の指摘のうち、2つの軸が同じ欠陥を指していたのは3組（6件）で、どれも同じ巡に並べた2軸の間でした。その2軸の14件で見ると6件が重なっています
  • 書き上げた記事本文を査読する段階（Phase 4）で話数が取れない欠陥は、2巡目の agy と Standards 軸の出力には無く、Spec 軸だけが挙げました
  • 差分の外にある設計文書のカタログ未記載は、1巡目の agy が指摘していましたが、突き合わせた側が範囲外として退けました。3巡目の Standards 軸が拾い直し、同じ変更の中で直されています
  • 重なった3組はどれも、同じモデルで渡した資料だけが違う2軸の間でした。agy と2軸の差は、モデルの差とも資料の差とも言えません
  • 私の感想では、レビューを入れたかどうかより、そのレビュアーに何を読ませたかで、拾える欠陥の種類が決まって見えました。1つの変更での観察で、因果は言えません
